# JIT 缺陷预测系统

在 **提交（commit）粒度** 预测一次代码提交是否引入缺陷，输出风险概率并排序，供代码评审员优先审阅高风险提交。

| 项 | 内容 |
|---|---|
| 课题 | 即时软件缺陷预测（JIT — Just-in-Time Defect Prediction） |
| 课程 | 2026-2027-1 软件开发与测试综合实训 |
| 小组 | 想到什么取什么 |
| 数据源 | Apache ActiveMQ（单仓库，固定在某一版本） |
| 系统定位 | **建议性预警**，不做 CI 强制拦截 |
| 代码仓库 | GitHub（私有，结题前视课程要求决定是否转公开） |

**核心链路**

```
ActiveMQ 仓库 → 抽提交信息 → SZZ 打标 → Kamei 14 项特征
   → 按时间切分训练 → 模型文件 → 预测接口 → 前端三个页面
```

## 一、四条线与两个角色

四条线各自独立，**写代码时不要动别人目录里的文件**。

| 线 | 目录 | 干什么 | 交出什么 | 负责人 |
|---|---|---|---|---|
| 数据与模型 | `data_model/` | 拉数据、SZZ 打标、抽 Kamei 14 项特征、训 2–3 个经典模型、评估 | 带标记样本集、特征数据、模型文件、评估报告 | **蒋励** |
| 后端与接口 | `backend/` | 建库表、预测接口、查询接口、解释模块、鉴权与输入校验 | 接口文档、数据库表、鉴权与校验代码 | **吕建江** |
| 前端与可视化 | `frontend/` | 三个页面（风险列表 / 提交详情 / 趋势看板）、图表、对接后端 | 原型、页面、图表、联调记录 | **刘帅华** |
| 工程化与协作 | `infra/` `.github/` | GitHub 仓库配置、分支规范、PR / Issue 模板、CI 流水线、缺陷管理、**PR 审阅** | 仓库规范、PR / Issue 模板、CI 配置 | **苏哲勋** |
| 文档与契约（**全员公共**） | `docs/` `openspec/` | 协作规范、范围边界、三条契约、原型、需求与设计文档、周报 | 契约、文档、周报 | 全员公共，**蒋励统稿** |

> `docs/` 与 `openspec/` 是**全员公共**的，任何人都可以改，**但同样走 PR** —— 公共是所有权，不是免审权。

### 两个 Scrum 角色

| 角色 | 负责人 | 职责 |
|---|---|---|
| 项目负责人（Product Owner） | **苏哲勋** | 定做什么、先做什么、每个功能点怎么算做完 |
| 流程负责人（Scrum Master） | **蒋励**（组长） | 及时讨论、卡住的事有人处理、流程别漏 |

### 三条硬规矩

1. **时间序切分**：训练集与检验集按提交时间先后切（前 70% 训练、后 30% 检验），**不许随机抽**。
   原因：`EXP`、`NUC` 等特征与时间相关，随机切分等于让模型提前看到未来，测出的准确率是假的。
2. **合并前必须由非作者审阅**：`main` 分支受保护，禁止直接推送。本项目统一由**苏哲勋**审；他自己的 PR 由**蒋励**审（详见 `docs/collaboration.md` 第 3.3 节）。
3. **改代码同步改规格**：规格与代码不一致，视为缺陷。

## 三、开发环境

Python 版本统一 **3.12.x**，依赖清单统一（各线 `requirements.txt`）；**环境管理工具各人自选** —— conda、venv、uv 都行，不要求环境同名。

会造出「本地能跑、别人跑不了」的是**版本与依赖不一致**，不是工具不一致，所以要锁的是前两者。

```bash
python -m venv .venv && source .venv/Scripts/activate   # 或用 conda / uv，任选一种
python -V                                               # 必须是 3.12.x
```

**第一次上手请按 `docs/onboarding.md` 走一遍**（约 20 分钟），里面还有 OpenSpec CLI 的安装与四个自检命令。数据集、模型文件、密钥**一律不入库**；`.venv/`、`venv/` 也已被 `.gitignore` 排除。
