# 并发负载复测（2026-11-16，孤立环境）

对应 issue #230。目标：区分「冷启动尖峰」与「稳态 p95」，并验证启动预热是否消除首轮超 500ms。

## 环境

- 只启动后端（`uvicorn app.main:app`，127.0.0.1:8000）与本机 MySQL；**未启动前端 dev server**。
- 数据：`jit_demo` 现有预测；`load_test.py` 取列表首条的 `commit_hash` / `model_name` 打 `POST /api/predict`。
- 命令：`cd backend && python scripts/load_test.py --users N --requests M`（httpx 线程池，`trust_env=False`）。
- 机器：Windows 11，同一台开发机；未做 CPU 绑核，后台无其它本项目进程。

**判读**：服务刚启动后的第一轮 p95 明显高于后续（1386ms vs 39ms）；同一进程内从第二轮起恢复。根因是首个预测请求承担 SHAP 解释器初始化，不是持续性性能缺陷。issue 里「10 并发首次 694ms」属同一现象。

## 修复后（启动预热默认模型 + SHAP）

`app/model_registry.warmup()` 在 lifespan 加载模型后对默认模型跑一次 `predict_proba` + `explain`。

## 结论

1. **首轮尖峰已消除**：10 并发首轮 p95 由 694/1386ms 降到 **369.6ms**，三轮均在 500ms 内。
2. **20 并发是边界**：三轮 p95 436–563ms，其中一轮略超 500ms；吞吐约 22 req/s，错误率 0%。如实登记，不宣称 20 并发达标。
3. 500ms 靶子按 10 并发稳态口径成立；若验收采用 20 并发，需要单独优化（模型/解释器并发度或机器规格），不在本次修复范围。
4. 前端未启动，排除了同机 dev server 干扰；所有轮次均为同一后端进程内实测。
