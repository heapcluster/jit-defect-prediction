# 四类测试交付说明与记录格式

> 状态：组织方式与记录格式说明，**不是测试通过报告**。实际结果、截图、覆盖率与签名必须对应同一提交和真实运行。课程细则见 [`test-assessment-guide.md`](test-assessment-guide.md)，功能与接口入口见 [`../../README.md`](../../README.md)，交付物现状见 [`../test/overview.md`](../test/overview.md)。

## 交付责任与顺序

| 顺序 | 测试类型 | 实施与结果提供 | 文档汇总 / 人工审核 | 必交证据 |
|---|---|---|---|---|
| 1 | 单元 | `蛋神的蛋-2` 统筹；各模块代码作者提供本线用例与运行结果 | `sober-1` 整理说明；用例作者复核 AI 来源与核心断言 | 测试代码、命令与输出、当前提交的覆盖率 HTML 与截图、来源与 Prompt 记录（如使用 AI） |
| 2 | 集成 | `neon-1` 统筹；前后端双方联调，模型负责人提供权重与特征口径 | `sober-1` 整理接口报告；双方确认请求/响应一致 | 按运行时 `/openapi.json` 列端点、四类场景结果、跨模块链路、截图/日志及缺陷链接 |
| 3 | 系统 | `neon-2` 组织真实环境与完整业务流程，各模块负责人配合定位 | **neon 人工编写计划、总结并签字**；`sober-1` 只整理证据与检查缺项 | 环境、执行记录、端到端与非功能结果、缺陷与复测证据 |
| 4 | 验收 | `neon-3` 组织用户视角演示，产品与各模块负责人确认需求 | **neon 人工编写验收方案、报告并签字**；`sober-1` 只整理证据与检查缺项 | OpenSpec Scenario 对照、实际演示记录、通过/失败/未执行及后续处理 |

后一步引用前一步的同一提交 SHA、环境和证据链接，不能拿旧版本的绿灯或截图填本次结果。测试用例来源须逐条标注 `[手写]`、`[AI生成]` 或 `[AI生成-人工修改]`；来源无法确认时写「待核」，由作者确认。AI 生成的核心业务断言须人工逐条复核。

## 单元测试说明记录格式

由各线作者实跑后填写，可复制到各线的测试说明或 PR 描述；`sober-hub` 只汇总真实输出。

| 字段 | 填写要求 |
|---|---|
| 测试提交 / 环境 | SHA、Python/Node 版本、隔离测试库或 Mock 说明 |
| 测试范围 | 核心函数或模块、对应 OpenSpec Requirement / Scenario |
| 用例设计 | 正常、边界、异常；输入、预期与核心业务断言；外部依赖如何隔离 |
| 执行证据 | 运行命令、用例通过/失败/跳过数、失败复现步骤 |
| 覆盖率 | 行与分支覆盖率、HTML 产物或 CI artifact 链接、截图；注明未覆盖关键路径 |
| AI 审核 | 每条来源标签、Prompt 路径（如有）、人工复核人及修改点 |

代码入口：`backend/tests/`、`data_model/tests/`、`frontend/tests/`、`infra/tests/`。后端测试需要隔离 MySQL 测试库；覆盖率报告必须与本次 SHA 一致。课程的 80% 行覆盖率是评分依据，CI 目前只归档报告，不把该值当自动合入门槛。

## 集成接口测试报告记录格式

接口清单以本次运行的 `/openapi.json` 为准，契约按 [`../api/`](../api/) 的对应页面核对；不要把课程截图里的通用 `/api/upload`、`/api/history` 当成本项目接口。

| 端点 / 场景 | 来源标签 | 输入与前置 | 预期状态码、字段、业务断言 | 实际结果 / 截图或日志 | 执行人 / 缺陷链接 |
|---|---|---|---|---|---|
| `<METHOD /api/path>` 正常 | 待填写 | 待填写 | 待填写 | 待实测 | 待填写 |
| 同端点缺参 | 待填写 | 待填写 | 待填写 | 待实测 | 待填写 |
| 同端点非法参数 | 待填写 | 待填写 | 待填写 | 待实测 | 待填写 |
| 同端点边界值 | 待填写 | 待填写 | 待填写 | 待实测 | 待填写 |

跨模块至少登记一次「特征抽取 → 模型推理 → 落库 → API 查询 → 前端展示」的真实链路，并记录一个并发场景。双方核对 `X-API-Key`、错误信封、字段类型、可空值与模型选择。浏览器与 API 的实际执行结果另附截图/录屏；待执行不能写成通过。

## 系统与验收：人工编写清单

以下只列交接时必须提供的材料，**不代写系统测试计划、系统测试总结、验收方案或验收报告**。这些正式文件应由 `neon` 根据实际测试亲自编写、判断并签名，`sober-hub` 仅检查链接、版本与缺项。

- 系统计划：目标、范围、环境与数据、用例与责任人、非功能测量方法、进入/退出条件、风险与回滚。
- 系统总结：实际执行日期和 SHA、通过/失败/未执行数、端到端证据、性能/安全/可靠性/易用性结果、缺陷及复测、人工结论与签名。
- 验收方案：用户角色与场景、对应 OpenSpec Requirement / Scenario、现场步骤、明确的通过标准、参与者与签名方式。
- 验收报告：逐场景实际结果、截图或录屏、未满足项、处置决定、负责人签名与日期。

## 缺陷处理边界

测试方**只负责发现、复现、写清五要素并提交 issue，不负责修复**；修复归模块 owner，口径裁定归评审，验收结论归人工。一单一缺陷，重复项合并到证据最全的保留单。完整规则见 [`../test/defect-handling.md`](../test/defect-handling.md)，issue 草稿与历史单更新文本见 [`../test/issues/`](../test/issues/)。
