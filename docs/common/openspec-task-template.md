# OpenSpec `tasks.md` 统一模板（2026-10-13 起强制）

> 起因：**2026-10-13 课堂反馈** —— ① openspec 各人写法不一、格式不统一；② 每份 `tasks.md` 末尾**必须有一个「测试和验证」板块**，确保 propose 真正落地。
> 适用范围：`openspec/changes/**/tasks.md`（含 archive 存量，见 §4 回溯登记）。
> 关联：`openspec/config.yaml` `rules.tasks`、`docs/common/openspec-rules.md`、`docs/common/test-strategy.md`、`docs/common/test-plan.md`。

## 1. 文件头（固定四行，缺一即不合规）

```markdown
# <change-id> — 任务清单

> 提案：`proposal.md` ｜ 设计决策：`design.md` ｜ 规格：`specs/<capability>/spec.md`
> 负责人：<线> <姓名>（线取 model / backend / frontend / repo）｜ 创建：<YYYY-MM-DD> ｜ 状态：未开始 / 进行中 / 已验收 / 已归档
> 用户故事：<对应用户故事编号，如 A2-3；附加功能写 G1-x；纯工程化写「无（工程化）」>
> 统一格式见 `docs/common/openspec-task-template.md`；**本文件末的「测试与验证」为强制板块，缺失视为提案不完整。**
```

## 2. 任务正文格式

- 一级小节用 `## N. <阶段名>（<用户故事 / 里程碑>）`，**N 从 1 起连续编号，不跳号**。
- 任务项用 `- [ ] N.M <动作> — <交付物>`；勾选用 `- [x] N.M`。
- **每个任务必须是可验收的交付单元**：写清「跑什么命令 / 看什么文件 / 得到什么结果」，禁止「优化一下」「完善功能」这类不可验收表述。
- 跨线任务必须写明**交付给哪条线、以什么形式交付**（文件名 / 接口 / 数据产物）。
- 证据写**仓库内可核验的相对路径**；飞书链接只作补充，不作唯一证据。
- 实际实现与提案不一致时（改文件名、换技术、砍范围），**在任务项内就地订正并说明原因**，不许静默偏离（例：frontend 实为 `.js` 而非 `.ts`）。

## 3. 强制板块：「测试与验证」（放在文件最后，永远存在）

```markdown
## 测试与验证（强制板块）

> 分层口径见 `docs/common/test-strategy.md`：**单元测试**由写代码的人自己做、
> **集成测试**在大版本合并后做、**验收测试**在交付时做，非功能验证并行。
> 铁律：**勾了 tasks ≠ 功能合格，必须有可复现的运行证据。**

### 1. 单元测试（本 change 新增/改动代码的作者负责）
| 项 | 内容 |
|---|---|
| 覆盖对象 | <函数 / 类 / 组件，逐项列> |
| 测试文件 | `<相对路径>` |
| 用例数与结果 | <n> 条 ｜ <passed / failed> |
| 复现命令 | `<可直接粘贴执行的命令>` |
| 正向用例 | <至少一条，写具体输入 → 期望输出> |
| 异常 / 边界用例 | <至少一条，课程明确要求，写具体触发条件 → 期望输出> |

### 2. 集成测试（大版本合并后，由负责合入的一条线组织）
| 项 | 内容 |
|---|---|
| 集成范围 | <本 change 与哪些既有能力 / 接口 / 数据流对接> |
| 测试文件 | `<相对路径>` |
| 用例数与结果 | <n> 条 ｜ <passed / failed> |
| 复现命令 | `<命令>` |
| 关键断言 | <跨模块契约：字段名 / 错误码 / 幂等性 / 时序> |

### 3. 验收测试（交付时，按 `specs/<cap>/spec.md` 的 Scenario 逐条走）
| 项 | 内容 |
|---|---|
| 验收依据 | `specs/<capability>/spec.md` 的 SHALL/MUST 条目 + Scenario 编号 |
| 用例数与结果 | <n> 条 ｜ <passed / failed> |
| 复现命令 / 步骤 | `<命令或演示脚本>` |
| 证据归档 | `<证据文件相对路径>` |

### 4. 非功能验证（本 change 触及则必填，否则写「本 change 不触及」）
| 维度 | 是否触及 | 证据 |
|---|---|---|
| 性能 | <是/否> | `<backend/scripts/evidence/*.md>` |
| 安全 | <是/否> | <鉴权 / 边界输入 / 信息泄露用例与结果> |
| 可靠 | <是/否> | <幂等 / 降级 / 空数据用例与结果> |
| 易用 | <是/否> | <三态 / 提示文案联调记录> |

### 5. 已知缺口与后续计划
| 缺口 | 原因 | 归属 | 计划时间 |
|---|---|---|---|
| <未跑成 / 未覆盖的项> | <客观原因，不许写「忘了」> | <线+姓名> | <日期或 Sprint> |
```

## 4. 存量回溯登记规则（2026-10-13 执行）

- **已归档的 5 份**：只补「测试与验证」板块，**不改动原有任务勾选与正文**，板块标题下注明「2026-10-13 回溯补录，按实际已发生的验证写实」。
- **进行中的 2 份**（`frontend-integration`、`feature-addons-sprint3`）：补齐板块，且缺口必须如实列出（如前端三页面尚未 lint/build 实跑、未联调）。
- 回溯补录**只记已发生的验证**；当时没做的，写进 §5 已知缺口，**不许倒填**。

## 6. PR 审阅时的 openspec 检查清单（把关人：苏哲勋）

> 2026-10-13 组长指派：每人写完自己的 openspec 后，由**苏哲勋统一把关风格与格式**（他负责 PR 审阅与仓库管理）。
> **原则：把关不代改** —— 查出问题写清缺哪节，打回给撰写人自己改；**只管增量**，存量 7 份已于 2026-10-13 补齐，不回头重排。

### 6.1 逐份检查（一个 PR 里每份 `tasks.md` 都过一遍）

| # | 检查项 | 不合规的典型样子 | 处置 |
|---|---|---|---|
| 1 | 文件头四行齐（提案/负责人/用户故事/模板指引） | 缺「用户故事」行、或没有指向模板的说明 | Request changes，指出缺哪行 |
| 2 | 一级小节 `## N.` 从 1 连续编号，不跳号 | 直接 `## 1.` 跳到 `## 3.` | 打回 |
| 3 | 任务项形如 `- [ ] N.M <动作> — <交付物>` | `- [ ] 优化模型`（不可验收） | 打回，要求写成可验收单元 |
| 4 | 每个任务是**可验收交付单元** | 「完善一下」「调调参」 | 打回 |
| 5 | 跨线任务写明交付给哪条线、以什么形式 | 「交给后端」但没说什么文件/接口 | 打回 |
| 6 | 证据是**仓库内相对路径** | 只贴飞书链接、或裸文件名 `dataset_stats.md` | 打回，要求补全路径 |
| 7 | **末尾有「测试与验证」板块，五节齐** | 整节缺失，或只有「已测试」两个字 | 打回（`config.yaml` 已立为强制） |
| 8 | 测试板块每节有**可复现命令** | 只写「跑了一下没问题」 | 打回 |
| 9 | 「已知缺口」如实、不空表 | 五节全填「无」但代码明显没测 | 打回，要求写实 |
| 10 | 勾选状态与证据一致 | `- [x]` 但对应测试文件不存在 | 打回（**勾了 ≠ 合格**） |

### 6.2 一致性抽查（每 PR 抽 1 份深查）

- 抽一份 `specs/<cap>/spec.md`，把每条 SHALL/MUST 对回 `tasks.md` 的测试板块：**是否有测试或验收证据能点回去**。点不回去 = Request changes。
- 查该 change 的 `proposal.md` 是否显式写了「不做什么」。
- 查 `design.md` 是否只记决策与取舍，没有复制 proposal 内容。

### 6.3 结论写法（留 PR 记录，课程证据）

- **Approve**：十项全过 + 抽查通过。
- **Request changes**：逐条写「缺第几项 / 缺哪一节 / 哪个证据路径点不开」，**不代改**。
- **Comment**：仅建议、不阻塞。

> 若同一类格式问题在 3 个以上 PR 反复出现，先回来改**本模板**（把规则写得更可执行），而不是每次口头打回。

## 5. 归档前自检（archive 前逐条打勾）

1. `tasks.md` 是否含完整的「测试与验证」板块，且三层测试各有可复现命令？
2. `specs/<cap>/spec.md` 的每条 SHALL/MUST 是否都有对应测试或验收证据？
3. 测试命令是否在 CI 或 `docs/common/test-strategy.md` §4 的入口里能跑通？
4. 证据文件是否已归档到 `backend/scripts/evidence/` 或 `data_model/reports/`，路径是否可点？
5. 已知缺口是否已同步到看板与周报？
