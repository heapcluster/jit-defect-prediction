# 软件缺陷预测 Web 系统测试考核说明

> **适用项目**：基于前后端分离架构的软件缺陷预测 Web 系统
>
> **考核内容**：单元测试、集成测试、系统测试、验收测试
>
> **总分**：100 分（单元测试 25 分 + 集成测试 25 分 + 系统测试 30 分 + 验收测试 20 分）
>
> **AI 辅助政策**：鼓励使用大模型辅助测试生成与执行，但须标注来源并提供提示词

***

## 一、总体考核框架

### 1.1 测试权重分配

| 测试类型 | 权重 | 核心考察目标 |
| --- | --- | --- |
| 单元测试 | 25% | 后端核心算法/逻辑的正确性验证能力 |
| 集成测试 | 25% | 前后端接口契约和模块间协作的验证能力 |
| 系统测试 | 30% | 端到端业务流程与非功能质量的验证能力 |
| 验收测试 | 20% | 从用户视角验证系统是否满足业务需求的确认能力 |

每类测试从**测试要求、质量度量、交付物、评分细则**四个维度进行规定。

### 1.2 AI 辅助测试政策

**鼓励使用的场景**：

- 使用大模型（如通义灵码、GitHub Copilot、ChatGPT 等）辅助生成单元测试用例代码
- 使用大模型辅助生成集成测试脚本（如 pytest + requests 测试代码、Postman 请求模板）
- 使用大模型辅助编写系统测试用例文档（含正向、反向、边界场景的设计建议）
- 使用大模型辅助生成验收测试用例初稿（含用户场景、验收标准草案）
- 使用大模型辅助生成测试数据（如构造异常数据集、边界值数据）
- 使用大模型辅助分析测试失败原因、生成 Bug 报告初稿
- 使用 AI 工具辅助自动化测试脚本编写与调试

**必须遵守的规则**：

| 规则编号 | 要求 | 违反后果 |
| --- | --- | --- |
| AI-R1 | **来源标注**：每条测试用例必须标注来源——`[AI生成]`、`[AI生成-人工修改]`、`[手写]` 三者之一 | 该测试类型扣 5 分 |
| AI-R2 | **提示词归档**：所有使用大模型生成测试内容的提示词（Prompt）必须完整保存，按测试类型归档提交 | 该测试类型扣 3 分 |
| AI-R3 | **人工审核义务**：AI 生成的测试用例必须经人工审核和验证后才能纳入最终交付。直接提交未经审核的 AI 原始输出视为不合格 | 该测试类型计 0 分 |
| AI-R4 | **核心断言人工把关**：涉及业务核心逻辑的断言（如预测结果准确性、金额计算、权限控制）必须由人工编写或人工逐条复核 | 扣 5 分 |
| AI-R5 | **不可替代性边界**：系统测试计划/总结、验收测试方案/结论必须人工撰写，不可由 AI 直接生成 | 该部分计 0 分 |

## 二、单元测试（25 分）

### 2.1 测试要求

**测试对象**：后端服务中的核心函数和方法，重点是缺陷预测模型的预测逻辑、数据预处理、特征提取等模块；前端组件中的纯函数工具方法。

**具体要求**：

- 每个核心函数/方法至少 3 条测试用例，覆盖正常输入、边界输入、异常输入
- 使用等价类划分 + 边界值分析方法设计用例，不允许随机凑数
- 外部依赖（数据库、模型文件、第三方 API）必须用 Mock/Stub 隔离
- 测试框架统一：Python 用 pytest，Java 用 JUnit 5
- 测试必须能独立运行，不依赖执行顺序，不依赖特定环境配置
- 断言必须针对业务逻辑的核心输出，禁止 `assert True` 类无意义断言
- 单条用例执行时间应在毫秒级，整个测试套件不超过 1 分钟

**AI 辅助专项要求**：

- 可使用大模型批量生成测试方法骨架、参数化测试数据、Mock 对象配置
- 每个测试文件头部需用注释标注用例来源比例，格式如下：

```python
# === AI 辅助说明 ===
# 本文件共 12 条测试用例
# [AI生成]：7 条（经人工审核修改后采纳）
# [AI生成-人工修改]：3 条（AI 生成骨架，人工补充核心断言）
# [手写]：2 条（核心业务断言由人工编写）
# 使用工具：通义灵码 / GitHub Copilot
# 提示词见：prompts/unit_test_predict.md
```

- 核心预测逻辑的断言（如 `assert result.defect_probability >= 0 and result.defect_probability <= 1`）必须人工编写或逐条复核，不可直接采用 AI 生成的断言

### 2.2 质量度量与评分细则（25 分）

| 评分维度 | 分值 | 评分标准 |
| --- | --- | --- |
| 覆盖率 | 8 | 行覆盖率 ≥80% 得 8 分；60%-79% 得 5 分；40%-59% 得 2 分；低于 40% 得 0 分。分支覆盖率 ≥70% 可加 2 分（加分项，最多不超过 8 分） |
| 用例质量 | 7 | 优秀（7 分）：正常/边界/异常三类场景完整，断言精准针对核心逻辑；良好（5 分）：覆盖两类场景，断言基本有效；中等（3 分）：只测正常路径，断言较弱；不合格（0 分）：断言无效或大量冗余用例 |
| 用例设计规范性 | 4 | 命名清晰（如 `test_predict_with_null_input`）、结构遵循 AAA 模式（Arrange-Act-Assert）、使用参数化测试减少重复 |
| 依赖隔离 | 3 | 完全隔离外部依赖得 3 分；有 1-2 处未隔离扣 2 分；直接连接真实数据库/网络得 0 分 |
| 可执行性 | 3 | 一键运行全部通过得 3 分；需手动配置环境扣 1 分；存在不稳定测试（flaky test）扣 2 分 |

### 2.3 交付物

| 交付物 | 说明 | 格式要求 |
| --- | --- | --- |
| 单元测试代码文件 | `test_*.py` 或 `*Test.java`，含 AI 来源标注注释 | 代码文件 |
| 覆盖率报告 | pytest-cov / JaCoCo 生成 | HTML 报告 + PDF 截图 |
| 单元测试说明文档 | 测试模块、用例数量、覆盖率数值、运行命令、AI/手写用例比例统计 | Markdown 文档 |
| **AI 提示词归档** | 所有用于生成测试的提示词完整保存，按测试模块分文件 | Markdown 文件，存放于 `prompts/` 目录 |

## 三、集成测试（25 分）

### 3.1 测试要求

**测试对象**：前后端分离架构中的接口层——后端 API（如 `/api/predict`、`/api/upload`、`/api/history`）与前端的对接，后端服务内部模块间的协作（如模型推理模块、数据库访问层、API 控制层之间的联调）。

**具体要求**：

- 覆盖所有 RESTful API 端点，每个接口至少设计正常调用、参数缺失、参数非法、边界值四类场景
- 前后端联调测试：前端发起真实 HTTP 请求到后端 Mock 或真实服务，验证请求/响应契约（状态码、数据结构、字段类型）
- 接口测试需验证业务断言，不能只验证状态码 200——比如预测接口返回的 `defect_probability` 字段是否在 [0,1] 范围内
- 跨模块集成测试：模型加载 → 数据预处理 → 预测推理 → 结果返回的完整链路
- 工具建议：Postman/HttpRunner 做接口测试，pytest + requests 做编程式集成测试，前端可用 Jest + MSW（Mock Service Worker）
- 需包含并发场景的基本验证（如同时提交多个预测请求）

**AI 辅助专项要求**：

- 可使用大模型根据 API 文档/Swagger 自动生成接口测试脚本骨架、参数组合、异常场景列表
- 可使用大模型辅助生成 Postman Collection 或 pytest + requests 测试代码
- 每个接口测试文件/Postman 请求需在描述字段标注来源（`[AI生成]` / `[AI生成-人工修改]` / `[手写]`）
- 业务断言（如响应字段值范围、数据一致性校验）必须人工编写或逐条复核，AI 只负责生成请求骨架和参数
- 提示词需完整保存，包含提供给大模型的 API 文档内容或接口定义

### 3.2 质量度量与评分细则（25 分）

| 评分维度 | 分值 | 评分标准 |
| --- | --- | --- |
| 接口覆盖率 | 7 | 所有 API 端点 100% 覆盖得 7 分；覆盖率 ≥80% 得 5 分；≥60% 得 3 分；低于 60% 得 0 分 |
| 测试场景完整性 | 7 | 每接口覆盖正常/参数缺失/参数非法/边界值四类场景得 7 分；缺一类扣 2 分；只测正常路径得 2 分 |
| 业务断言有效性 | 5 | 断言覆盖响应数据结构、字段值范围、业务逻辑正确性得 5 分；只断言状态码得 2 分；无断言得 0 分 |
| 跨模块链路验证 | 3 | 完整验证模型加载→预处理→推理→返回链路得 3 分；部分链路验证得 2 分；无链路测试得 0 分 |
| 测试数据与文档 | 3 | 测试数据构造合理（含正常/异常数据集）、接口文档清晰得 3 分；数据随意、文档缺失得 0-1 分 |

### 3.3 交付物

| 交付物 | 说明 | 格式要求 |
| --- | --- | --- |
| 接口测试用例集 | Postman Collection 导出文件或 pytest 测试代码，含来源标注 | Postman JSON / 代码文件 |
| 集成测试脚本 | 编程式集成测试代码（如 `test_integration_*.py`） | 代码文件 |
| 接口测试报告 | 接口清单、测试结果汇总表（通过/失败数）、异常接口说明、AI/手写用例比例 | Markdown 报告 |
| 前后端联调记录 | 前端调用后端接口的测试截图或录屏，证明数据契约匹配 | 截图/录屏 |
| **AI 提示词归档** | 生成接口测试使用的全部提示词，含提供给大模型的 API 文档 | Markdown 文件，存放于 `prompts/` 目录 |

## 四、系统测试（30 分）

### 4.1 测试要求

**测试对象**：完整的软件缺陷预测 Web 系统，从前端页面到后端服务到模型推理的端到端全链路，以黑盒测试为主。

#### 功能测试要求

- 基于需求规格说明书编写系统测试用例，覆盖所有用户可见功能（用户登录、数据上传、缺陷预测、结果展示、历史记录查询、报告导出等）
- 每个功能点至少覆盖正常流程、异常流程、边界场景
- 反向用例占比不低于 30%（如上传非法格式文件、超大数据量、空数据等）
- 重点测试用例需标注（如涉及预测结果准确性的核心场景） 

#### 非功能测试要求

- **性能测试**：使用 JMeter 或 Locust 对核心接口做负载测试，记录并发用户数、响应时间、吞吐量、错误率
- **兼容性测试**：至少覆盖 Chrome、Edge、Firefox 三个浏览器，验证页面渲染和功能正常
- **安全测试**：验证身份认证、越权访问（普通用户访问管理员接口）、SQL 注入防护、文件上传安全（如上传恶意文件）
- **易用性测试**：验证页面加载流畅性、提示信息清晰度、错误反馈友好性

#### 缺陷管理要求

- 发现的 Bug 需按规范记录：Bug ID、标题、严重级别（致命/严重/一般/轻微）、复现步骤、预期结果、实际结果、截图
- Bug 需跟踪到关闭，形成闭环

#### AI 辅助专项要求

- 可使用大模型辅助生成系统测试用例初稿（含正向/反向/边界场景的设计建议）
- 可使用大模型辅助生成性能测试脚本（如 JMeter Test Plan XML、Locust 脚本）
- 可使用大模型辅助分析测试失败日志、生成 Bug 报告初稿
- **测试用例文档中每条用例需标注来源**（`[AI生成]` / `[AI生成-人工修改]` / `[手写]`），在用例表格中新增"来源"列
- **测试计划和测试总结报告必须人工撰写**，不可由 AI 直接生成；AI 可辅助润色格式，但核心结论、风险评估、发布建议须人工判断
- Bug 报告可由 AI 生成初稿，但复现步骤须经人工验证确认，截图必须人工采集

### 4.2 质量度量与评分细则（30 分）

| 评分维度 | 分值 | 评分标准 |
| --- | --- | --- |
| 测试用例设计 | 10 | 优秀（10 分）：用例覆盖全部功能点，正常/异常/边界完整，反向用例 ≥30%，重点用例标注清晰；良好（7 分）：覆盖全部功能但异常场景略有不足；中等（5 分）：只覆盖正常流程；不合格（0 分）：大量功能点遗漏 |
| Bug 发现与记录 | 7 | 发现并规范记录 Bug 数量：≥8 个得 7 分；5-7 个得 5 分；3-4 个得 3 分；少于 3 个得 1 分。Bug 描述规范（含复现步骤、截图）加 2 分；发现重点/高危 Bug 每个加 1 分（最多加 2 分） |
| 非功能测试 | 6 | 性能测试（2 分）：有负载测试数据和分析；兼容性测试（2 分）：覆盖 ≥3 浏览器；安全测试（1 分）：含越权/注入/上传安全验证；易用性测试（1 分）：有易用性问题记录 |
| 测试执行与结果 | 4 | 测试全部执行，结果记录完整（通过/失败/跳过统计清晰）得 4 分；部分执行或记录不完整扣 2 分 |
| 测试报告质量 | 3 | 报告结构完整（概述、范围、环境、结果汇总、Bug 清单、结论与建议）、结论明确（通过/有条件通过/不通过）、数据真实可追溯得 3 分；结构缺失或结论模糊扣 1-2 分 |

### 4.3 交付物

| 交付物 | 说明 | 格式要求 |
| --- | --- | --- |
| 系统测试计划 | 测试范围、策略、环境、资源分配、进度安排、风险评估（**人工撰写**） | Markdown 文档 |
| 系统测试用例文档 | 含用例编号、模块、前置条件、操作步骤、输入数据、预期结果、优先级、**来源标注** | Excel 或 Markdown |
| Bug 清单 | 含 Bug ID、标题、严重级别、复现步骤、预期/实际结果、截图、状态、**来源标注** | Excel |
| 性能测试报告 | JMeter/Locust 测试结果截图 + 关键指标分析 | Markdown + 截图 |
| 系统测试总结报告 | 测试概述、用例汇总、Bug 汇总、遗留问题、结论与建议（**人工撰写**） | Markdown 文档 |
| **AI 提示词归档** | 生成系统测试用例、性能脚本、Bug 分析等使用的全部提示词 | Markdown 文件，存放于 `prompts/` 目录 |

## 五、验收测试（20 分）

### 5.1 测试要求

**测试对象**：软件缺陷预测 Web 系统的最终交付版本，从前端用户界面到后端预测服务的完整系统，站在最终用户角度验证系统是否满足业务需求和验收标准。

**测试定位**：验收测试是系统测试通过后、正式交付前进行的最终确认测试。区别于系统测试的"找 Bug"导向，验收测试的核心是"确认系统满足用户需求，可以交付"。由学生扮演"用户+验收方"角色，基于需求规格说明书中的验收标准逐项确认。

#### 验收内容

| 验收类别 | 验收项 | 说明 |
| --- | --- | --- |
| **功能验收** | 核心业务流程验收 | 用户登录 → 数据上传 → 选择预测模型 → 执行预测 → 查看结果 → 导出报告的完整业务闭环 |
|  | 需求覆盖率 | 需求规格说明书中列出的每条功能需求是否均已实现且可正常使用 |
|  | 缺陷预测准确性验证 | 使用已知缺陷数据集验证预测结果的准确率/召回率是否达到需求中定义的指标 |
| **数据验收** | 数据完整性 | 上传数据→预处理→预测→结果存储全链路中数据无丢失、无篡改 |
|  | 数据展示一致性 | 前端展示的预测结果与后端 API 返回的原始数据完全一致 |
| **用户界面验收** | 页面展示完整性 | 所有页面元素正确渲染，无缺失、错位、乱码 |
|  | 交互流程合理性 | 用户操作路径符合直觉，提示信息清晰，错误反馈友好 |
| **文档验收** | 用户手册完整性 | 系统使用说明、部署说明、API 文档是否齐全 |
|  | 测试文档完整性 | 四类测试的全部交付物是否齐备且规范 |

#### 验收测试用例要求

- **用例来源**：基于需求规格说明书中的验收标准逐条编写验收用例，每条验收标准至少对应 1 条验收用例
- **用例数量**：不少于 15 条，覆盖功能验收、数据验收、界面验收、文档验收四个类别
- **用例格式**：含验收编号、验收类别、对应需求条目、操作步骤、预期结果、实际结果、验收结论（通过/不通过）、来源标注
- **通过标准**：每条验收用例需明确标注"通过"或"不通过"，不允许"部分通过"或"待定"
- **角色模拟**：验收用例应从"最终用户"视角编写，而非"开发者测试"视角——描述用户要做的事和期望看到的结果，而非代码层面的断言

#### 验收通过标准

| 条件 | 要求 |
| --- | --- |
| 功能验收 | 所有核心功能验收项 100% 通过；非核心功能验收项通过率 ≥90% |
| 缺陷预测准确性 | 使用标准测试数据集的预测准确率达到需求文档中规定的阈值（如 ≥80%） |
| 无致命/严重缺陷遗留 | 系统测试中发现的致命和严重级别 Bug 必须全部修复并回归验证通过 |
| 一般缺陷遗留 | 遗留的一般级别 Bug 不超过 3 个，且有明确的修复计划和影响评估 |
| 文档完整 | 用户手册、API 文档、部署说明、全部测试交付物齐备 |
| 验收结论明确 | 给出"验收通过"或"验收不通过"的明确结论，不通过时列出不通过项和整改要求 |

#### AI 辅助专项要求

- 可使用大模型辅助生成验收用例初稿（基于需求规格说明书自动提取验收点并生成操作步骤）
- 可使用大模型辅助编写验收测试检查清单（checklist）
- **验收方案和验收结论必须人工撰写**，不可由 AI 直接生成——验收结论涉及是否接受系统交付的判断，必须由人工做出
- 验收用例需标注来源（`[AI生成]` / `[AI生成-人工修改]` / `[手写]`）
- 预测准确性验证的判定标准必须人工确认，不可直接采用 AI 建议的阈值

### 5.2 质量度量与评分细则（20 分）

| 评分维度 | 分值 | 评分标准 |
| --- | --- | --- |
| 验收用例覆盖度 | 6 | 优秀（6 分）：验收用例覆盖全部验收类别，每条需求验收标准至少对应 1 条用例，用例数量 ≥15；良好（4 分）：覆盖全部验收类别但部分需求条目无对应用例，用例数量 10-14；中等（2 分）：只覆盖功能验收，其他类别缺失；不合格（0 分）：验收用例数量 <10 或大量验收项遗漏 |
| 验收标准明确性 | 4 | 优秀（4 分）：每条验收用例有明确的通过/不通过判定标准，验收阈值量化（如准确率 ≥80%）；良好（3 分）：大部分用例有明确标准，少数用例标准模糊；不合格（0 分）：大量用例用"基本正常""大致符合"等模糊表述 |
| 验收执行与结果记录 | 5 | 全部验收用例执行完毕，结果记录完整（通过/不通过/原因说明），不通过项有整改建议得 5 分；部分执行或记录不完整扣 2-3 分；未实际执行仅提交文档得 0 分 |
| 验收报告质量 | 3 | 报告结构完整（验收概述、验收范围、验收标准、用例执行汇总、缺陷遗留情况、验收结论）、结论明确（验收通过/不通过）、结论有数据支撑得 3 分；结构缺失或结论模糊扣 1-2 分 |
| 用户视角合理性 | 2 | 验收用例从最终用户视角编写，描述用户操作和期望结果而非代码断言得 2 分；用例偏向开发者测试视角扣 1 分；完全照搬系统测试用例得 0 分 |

## 六、AI 辅助测试评分说明

### 6.1 来源标注格式

所有测试用例（无论单元、集成、系统、验收）必须标注来源，使用以下三种标签之一：

| 标签 | 含义 | 适用场景 |
| --- | --- | --- |
| `[AI生成]` | 大模型生成后直接采纳，人工仅做了格式调整 | 测试方法骨架、参数化数据、Mock 配置等非核心断言代码 |
| `[AI生成-人工修改]` | 大模型生成初稿，人工修改了断言逻辑、补充了业务场景或调整了测试数据 | AI 生成骨架 + 人工补核心断言 |
| `[手写]` | 完全由人工编写，未使用 AI 辅助 | 核心业务断言、测试计划、验收结论 |

### 6.2 提示词归档要求

- 每个提示词保存为独立的 Markdown 文件，文件名格式：`{测试类型}_{模块/功能}_{序号}.md`
- 每个提示词文件需包含以下内容：

```
# 提示词：{简要描述}

## 基本信息
- 使用工具：{如 通义灵码 / GitHub Copilot / ChatGPT}
- 使用日期：{YYYY-MM-DD}
- 关联测试文件：{如 test_predict.py}

## 提示词原文
{完整的提示词内容}

## 大模型输出摘要
{简要描述大模型返回的内容}

## 人工审核与修改记录
- 审核结果：{直接采纳 / 修改后采纳 / 弃用}
- 修改内容：{如有修改，列出具体修改点}
- 弃用原因：{如弃用，说明原因}
```

### 6.3 评分加减分规则

| 项目 | 说明 | 分值影响 |
| --- | --- | --- |
| AI 用例采纳率合理 | AI 生成用例经审核后采纳率在 40%-70% 之间（说明有选择性采纳，非盲目接受） | 加 2 分（加分项，总分不超过 100） |
| 提示词质量高 | 提示词包含角色设定、业务背景、约束条件、输出格式，结构化程度高 | 加 2 分（加分项，总分不超过 100） |
| AI/人工协作模式清晰 | 文档中能清晰看出"AI 生成 + 人工审核修改"的协作过程，修改记录详实 | 加 1 分（加分项，总分不超过 100） |
| AI 用例采纳率过低或过高 | 采纳率 <20%（说明 AI 输出质量差或提示词不当）或 >90%（说明盲目采纳，缺乏人工审核） | 扣 2 分 |
| 未标注来源 | 测试用例缺失来源标注 | 按 AI-R1 规则扣 5 分 |
| 未保存提示词 | 使用了 AI 但未归档提示词 | 按 AI-R2 规则扣 3 分 |

## 七、红线规则

以下情况不分测试类型，一旦触犯直接扣分或判定该部分不合格：

| 红线行为 | 后果 |
| --- | --- |
| 测试数据造假、覆盖率报告伪造 | 该测试类型计 0 分 |
| 测试用例全部复制粘贴、无实际差异 | 该测试类型计 0 分 |
| 单元测试连接真实数据库或外部 API（未隔离） | 扣 10 分 |
| 系统测试只测"系统能打开"无实质验证 | 计 0 分 |
| 验收测试未实际执行、仅提交纸质文档 | 计 0 分 |
| Bug 报告无法复现 | 每个 Bug 扣 2 分 |
| 测试报告/验收结论为"基本没问题"等模糊表述 | 扣 5 分 |
| **AI 生成的测试用例未经人工审核直接提交** | 该测试类型计 0 分 |
| **核心业务断言完全由 AI 生成且未人工复核** | 扣 5 分 |
| **测试计划/验收方案/验收结论由 AI 直接生成未人工撰写** | 该部分计 0 分 |
