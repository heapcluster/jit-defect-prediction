# 软件缺陷预测系统测试考核对照与执行清单

> 依据：用户提供的《软件缺陷预测系统测试考核说明》截图（可见总框架、AI 规则、单元与集成测试细则）和《规格驱动开发 SDD 与 OpenSpec》讲义。项目具体测试范围与执行状态以 `docs/common/test-plan.md` 为准；本文件只把考核要求映射到现有仓库，不把计划写成已通过。

## 1. 考核结构与证据原则

| 类型 | 分值 | 考核目标 | 本项目主要证据入口 |
|---|---:|---|---|
| 单元测试 | 25 | 核心函数和纯逻辑的正确性、边界与异常 | `backend/tests/`、`data_model/tests/`、`frontend/tests/` |
| 集成测试 | 25 | API、数据库、模型和前端之间的契约与链路 | `backend/tests/`、`docs/frontend/integration-log.md` |
| 系统测试 | 30 | 端到端业务流程与非功能质量 | `docs/common/test-plan.md`、`backend/scripts/evidence/` |
| 验收测试 | 20 | 用户视角确认业务需求 | `docs/common/acceptance-overview.md`、各线验收记录 |

四类均要按**测试要求、质量度量、交付物、评分细则**检查。截图未展示系统测试和验收测试的具体评分子项，不能臆造分值；这两类先按项目测试方案执行，正式评分时补齐课程原文核对。

OpenSpec 讲义强调先写可测试的 Requirement 和 Scenario，再实现、验证、归档。每条测试证据应能反查到 `openspec/specs/` 或相应 change 的 SHALL/MUST 与 WHEN/THEN；`tasks.md` 勾选不等于验收通过。

## 2. AI 辅助测试的硬规则

| 规则 | 要求 | 执行方式 |
|---|---|---|
| AI-R1 来源标注 | 每条测试用例标 `[AI生成]`、`[AI生成-人工修改]` 或 `[手写]`，漏标按截图扣 5 分 | 在测试函数旁或用例记录中标注；不要只给整个文件标一次 |
| AI-R2 提示词归档 | 用大模型生成的测试内容须保留完整 Prompt，按测试类型归档，漏交按截图扣 3 分 | 记录工具、原始提示词、生成日期、人工修改与审阅结论；不要存密钥或个人数据 |
| AI-R3 人工审核 | AI 生成的测试用例须经人工审核、验证后才可验收；未经审核的原始输出直接提交不合格 | 审阅输入、期望结果、边界和断言；确有修改时标 `[AI生成-人工修改]`，未修改时仍如实标 `[AI生成]` 并留人工复核记录 |
| AI-R4 核心断言 | 预测概率、鉴权、数据一致性等核心业务断言必须由人编写或逐条复核，违反按截图扣 5 分 | 禁止只断言 HTTP 200、非空或 `assert True` |
| AI-R5 不可替代边界 | 系统测试计划/总结、验收方案/报告必须由人编写，不可让 AI 直接代交 | AI 可辅助整理材料，负责人须做场景判断、实测和签字 |

建议在测试文件或用例表中使用以下记录格式；已有存量用例应按实际来源补录，无法确认时标“来源待核”，不能倒填成手写：

```text
用例编号：T-BE-01
来源：[手写] / [AI生成-人工修改] / [AI生成]
关联规格：openspec/specs/<capability>/spec.md 的 Requirement / Scenario
输入与前置：...
预期与核心断言：...
运行命令与结果：...
Prompt 记录：<使用 AI 时填写仓库内相对路径>
人工复核：<姓名、日期、具体修改点>
```

## 3. 单元测试（25 分）

**范围。** 后端预测逻辑、数据处理、特征抽取、鉴权与参数校验；前端纯函数和工具方法；模型线 14 项特征和训练口径。每个核心函数或方法至少 3 条用例，覆盖正常、边界、异常。使用等价类划分和边界值分析；数据库、模型文件、第三方 API 等外部依赖用 Mock/Stub 隔离。单测须能独立运行，不依赖执行顺序或特定环境，单个用例原则上不超过 1 分钟。

**断言。** 针对业务结果写精确断言，例如缺少 `X-API-Key` 返回 40100、非法参数返回 40001、风险概率位于 `[0,1]` 且与模型输出一致、14 维特征顺序与契约一致。不能以 `assert True` 或仅检查“没有抛错”代替。

| 评分维度 | 分值 | 截图可见判据 |
|---|---:|---|
| 覆盖率 | 8 | 行覆盖率 ≥80% 得 8；60%–79% 得 5；40%–59% 得 2；<40% 得 0；分支覆盖率 ≥70% 可加 2，但该维度总分不超过 8 |
| 用例质量 | 7 | 正常、边界、异常完整且断言精准；只有正常路径或无效断言会降分 |
| 用例设计规范性 | 4 | 命名清晰、AAA 结构、参数化/复用合理 |
| 依赖隔离 | 3 | 外部依赖可控，避免直接依赖真实数据库或网络 |
| 可执行性 | 3 | 一键运行、无需手动配置、无不稳定 flaky 用例 |

**交付物。** 测试代码、覆盖率 HTML 报告与 PDF 截图、单元测试说明 Markdown、AI 提示词归档（使用 AI 时）。本仓库现有 `backend/tests/`、`data_model/tests/`、`frontend/tests/`；覆盖率报告、提示词归档和所有核心函数“三例”覆盖需按当前提交重新核对，不能直接沿用历史百分比。

**复现入口。** 在对应目录运行 `python -m pytest -q`（后端/模型）或 `npm run test:unit`（前端）。后端测试需隔离 MySQL 测试库；详细前置以 `infra/ci.md` 为准。需要覆盖率时，在有 `pytest-cov` 的环境于 `backend/` 运行 `python -m pytest --cov=app --cov-branch --cov-report=html --cov-report=term-missing`，保存当前提交的输出。前端目前没有 `test:coverage` 脚本，不能宣称已提供前端覆盖率报告。

## 4. 集成测试（25 分）

**范围。** 覆盖当前系统实际存在的 API；正常、缺参数、非法参数、边界值四类场景；前端真实 HTTP 请求与后端响应包络、状态码、字段类型的一致性；特征抽取 → 模型推理 → 数据库写入 → API 查询的跨模块链路；至少一个并发场景。可用 pytest + HTTP 客户端或 Postman Collection；前端网络层可用 MSW，但真实联调证据仍需实跑。

截图中的 `/api/upload` 和 `/api/history` 是通用示例，**本项目当前没有这两条路由**，不得为凑覆盖率写不存在的接口。接口清单以运行时 `/openapi.json` 和 `docs/backend/api-spec.md` 为准；核心示例是 `GET /api/commits`、`GET /api/commits/{hash}`、`POST /api/predict`、`GET /api/trends`，以及现有的同步、PR、质量和反馈接口。

| 评分维度 | 分值 | 截图可见判据 |
|---|---:|---|
| 接口覆盖率 | 7 | 实际 API 端点 100% 得 7；≥80% 得 5；≥60% 得 3；<60% 得 0 |
| 测试场景完整性 | 7 | 每接口正常、缺参、非法参数、边界值四类齐全；缺一类扣 2 分 |
| 业务断言有效性 | 5 | 覆盖状态码、响应结构、字段范围、业务逻辑，而非只检查请求成功 |
| 跨模块链路验证 | 3 | 模型加载 → 数据预处理 → 推理 → 返回完整链路 |
| 测试数据与文档 | 3 | 有正常/异常数据集，文档清楚、数据脱敏 |

**交付物。** 接口测试用例集（Postman JSON 或 pytest 代码）、集成测试脚本、接口测试报告、前后端联调截图或录屏、AI 提示词归档（使用 AI 时）。报告要列接口清单、通过/失败数、异常结果及复现条件。`docs/frontend/integration-log.md` 是现有联调记录；它的历史结果不能直接代表本次测试通过。

## 5. 系统与验收测试：本项目执行映射

以下是依据 `docs/common/test-plan.md` 的项目执行要求，并非截图未显示部分的官方评分细则。

| 层级 | 最小现场场景 | 证据与责任 |
|---|---|---|
| 系统测试 30 分 | 从同步真实提交或 PR、生成特征、选择已交付模型预测，到风险列表/详情/趋势/质量页面展示；再测空库、无效令牌、非法参数、缺失权重和失败恢复 | 人工撰写计划、用例、缺陷单和总结；浏览器截图/录屏及运行日志由实际操作者留存 |
| 验收测试 20 分 | 逐条核对 OpenSpec Scenario 与用户可见功能；评审员能看到风险排序、解释或明确的无归因状态，能区分“尚未预测”和系统错误 | 由负责人组织真实演示并记录通过、失败、未执行，缺口进 `docs/repo/defect-records.md` |

性能、安全、可靠性与易用性按契约及 `docs/design/non-functional.md` 实测。CI 绿灯仅证明自动化用例与构建通过，不能代替上述人工验收。

## 6. 交付整理与当前待补

保持现有仓库分包，测试代码分别归各线 `tests/`；报告索引归 `docs/common/test-report-sprint2.md`，联调归 `docs/frontend/integration-log.md`，性能证据归 `backend/scripts/evidence/`，缺陷归 `docs/repo/defect-records.md`。若使用 AI 生成测试，再在所属测试线内建立 `prompts/`，按单元、集成分类保存原始提示词和人工修改记录。不要把真实密钥、模型权重或数据集放入仓库。

| 待补项 | 不能直接宣称完成的原因 | 核对方式 |

| 实机证据 | 模型权重不入库，浏览器和真实 MySQL 场景不能由 CI 代测 | 按 `docs/common/test-plan.md` 留运行日志、截图和人工结论 |
