## 0. 这份文档管什么

四个人往同一个仓库提交，不先约定的话最早出事的一定是这四件：

1. 两个人在同一个文件上互相覆盖 —— 因为不知道谁在改什么
2. `main` 被直接推送，改坏了没有回退点
3. 看不懂别人的提交在干什么，评审变成走过场盖章
4. 同一份代码四种写法，联调时才发现对不上

**第一次提交代码前读完即可，大约 8 分钟。** 第 1–3 节管前三条，第 4 节管第四条。

**本文的邻居**（同一套规范的另外三份，本文不重复它们的内容）：

| 想知道 | 读 |
|---|---|
| 谁做什么、什么时候交、怎么沟通、任务怎么认领 | **`docs/team-charter.md`** |
| 文档怎么命名、注释怎么写、**周报怎么填** | **`docs/writing-norms.md`** |
| 缺陷（Bug）怎么记、谁修、优先级怎么定 | **`docs/defect-management.md`** |

分工一块看：本文管「**提交、分支、PR、代码规范**」，`team-charter.md` 管「**人、时间、沟通**」，`writing-norms.md` 管「**怎么写文档**」，`defect-management.md` 管「**出错怎么记**」。

## 1. 分支规范

### 1.1 命名规则

| 项 | 规则 |
|---|---|
| 主干 | `main`，受保护，**禁止直接推送** |
| 工作分支 | 从 `main` 切出，命名 `<类型>/<线>/<简述>` |
| 类型 | `feat` 新功能 / `fix` 修缺陷 / `docs` 文档 / `refactor` 重构 / `test` 测试 / `chore` 杂务 |
| 线 | `model` / `backend` / `frontend` / `infra` / `docs` / `spec` |
| 生命周期 | PR 合入后**立即删除**，远端与本地都删（见 §1.6） |

示例：

```
feat/model/szz-labeling          数据与模型线：SZZ 打标
feat/backend/predict-api         后端线：预测接口
fix/frontend/risk-list-paging    前端线：修风险列表分页
docs/contracts/api-format        文档线：接口格式契约
```

**为什么分支名里要带「线」**：出问题时一眼看出改动归属，评审时也知道该找谁。四个人各管一条线，这个信息在合并冲突时最有用。

### 1.2 日常操作（六步）

```bash
# ① 开工前先同步 main —— 拿着三天前的代码开新分支，等于给自己预埋冲突
git checkout main
git pull

# ② 从 main 切工作分支
git checkout -b feat/backend/predict-api

# ③ 干活，分多次小提交（提交信息格式见第 2 节）
git add backend/app/api/predict.py     # 加具体文件，不要 git add .
git commit -m "feat(backend): 新增预测接口"

# ④ 推分支（首次带 -u，之后直接 git push）
git push -u origin feat/backend/predict-api

# ⑤ 网页开 PR，描述按模板写四件事，找审阅人（见第 3 节）
# ⑥ Squash merge 合入后删分支：远端在 PR 页面点 Delete branch，本地执行下面三行（见 §1.6）
git checkout main
git pull
git branch -d feat/backend/predict-api
```

三个容易忽略的点：

- **`git add` 加具体文件，不要 `git add .`** —— 点号会把你的临时脚本、日志、随手存的 csv 一起带上。误提交数据集就是这么做出来的。
- **⑥ 的 `git pull` 不能省** —— 不合入远端的新提交，你下一次开工拿到的还是旧 `main`。
- **一个分支只做一件事**。中途想做别的，从 `main` 另切一个分支，不要把两件事塞进同一个 PR。

### 1.3 分支落后于 `main` 了怎么办

```bash
# 在自己的工作分支上执行
git merge origin/main
```

**用 `merge`，不要用 `rebase` + `git push --force`。** 理由：`rebase` 会重写已经推上去的提交，之后必须强推；强推会把别人的提交冲掉，新手很难判断什么时候安全。`merge` 只多一个合并提交，而这个提交在 PR 被 Squash merge 时就消失了，没有任何代价。

> 例外：分支**从未推送到远端**（只在本机），此时 `git rebase origin/main` 是安全且更干净的。拿不准就用 merge。

**分支落后了不要硬扛着合并** —— 冲突放得越久越难解，因为两边的改动都在往前跑。

### 1.4 遇到冲突

1. **只在自己的工作分支上解冲突**，绝不在 `main` 上解。
2. 解完**跑一遍该线的自检命令**（第 4.7 节）—— 冲突解决的正确性只有测试能证明，肉眼看不出。
3. **不确定就问对方**。冲突段落里是别人的代码，凭猜测删掉是最糟的处理方式。
4. 冲突解完照常 `git add` + `git commit` + `git push`，PR 会自动更新。

### 1.5 分支相关的禁止事项

- 直接向 `main` 提交或推送（会被分支保护拒绝 —— 这是设计如此，不是配置错了）
- `git push --force`（分支只有你一个人在推、且还没开 PR 时除外）
- 把别人的分支删掉
- 明明有未完成的改动，却切到别的分支接着干

### 1.6 合并之后：分支要不要删

**要删，而且远端和本地都删。** 规则写在 §1.1 的「生命周期」一行，这一节说清理由和操作。

**谁来删**：**分支作者自己删**。审阅人只管合，不动别人的分支（见 §1.5）。

**为什么删**

分支名里带「线」，是给冲突处理和评审用的**临时标记**，不是要长期保存的资产。按四个 Sprint 的节奏，每人会开出十几条分支；不删的话 GitHub 的分支列表和 `git branch -a` 会变成一张读不懂的清单 —— 到那时没人能一眼看出「哪条还活着、哪条已经把改动交出去了」。

而 **Squash merge 之后，分支上的改动已经以一个新提交的形式进了 `main`**，那条分支只剩一个指向旧提交的指针，没有任何东西需要靠它保存。

**远端怎么删**

PR 合并后，页面上会出现 **Delete branch** 按钮，点掉即可。

想省这一步，可以让仓库管理员去 Settings → General → Pull Requests 勾上 **Automatically delete head branches**。GitHub 新仓库默认**不勾**，所以别默认「网页会自己删」。无论勾没勾，规则都是**合完就删**，差别只是手动一次还是自动。

**本地怎么删**

```bash
git checkout main
git pull
git branch -d feat/backend/predict-api   # 分支名换成你自己的
```

两件事要注意：

- **用 `-d`，不要用 `-D`。** `-d` 是安全删除：只有确认该分支的改动已经进了 `main` 才会成功，没合会直接报错拦住你。`-D` 不检查，直接抹掉。
- **报 `not fully merged` 时不要立刻改用 `-D`。** 先判断是两种情况中的哪一种：① PR 还没合 —— 那就不该删；② PR 是 Squash merge 合入的 —— 这种情况 `main` 上的提交是**重新压出来的新提交**、哈希与分支上的不同，`-d` 会误以为「没合并」。确认 PR 已经合入，再 `git branch -D`（这是唯一允许用 `-D` 的场合）。

远端分支删掉后，本地还会残留一个 `origin/xxx` 的跟踪引用，用这条命令清掉：

```bash
git fetch --prune
```

**PR 被关闭、没有合并，分支怎么办**

同样删掉。改动没进 `main`，分支留着不会自己变得有用。真需要那份代码，从 PR 页面点 **Restore branch** 能恢复 —— 但这个恢复窗口不是永久的，所以**不要在没有 PR 记录的情况下删分支**（那种分支删了就真找不回来）。

**哪些分支不能删**

- `main`
- 别人的分支（§1.5）
- 还没合并的 PR 对应的分支

## 2. 提交信息（commit message）规范

格式：

```
<类型>(<范围>): <中文简述>

<正文：为什么这么改，可选>
<关联：Closes #12 / change-id: add-szz-labeling，可选>
```

- **类型和范围用英文**。沿用了业界通行的 Conventional Commits 写法（工具能解析），取值与第 1 节相同。
- **简述用中文写**。这是本组约定、不是通用标准 —— 组内交流用中文，看 `git log` 更快。
- 标题一行不超过 72 字符，不要堆无关信息。
- 一次提交只做一件事。

好 / 坏对照：

| 不好 | 问题出在哪 | 改成 |
|---|---|---|
| `update` | 看不出改了什么 | `fix(backend): 修正预测接口空输入返回 500 的问题` |
| `修改代码` | 没有范围，不知道影响了谁 | `refactor(model): 抽出特征抽取的公共函数` |
| `feat: 大改一通，做了很多东西` | 一次混了多件事 | 拆成多个提交，一个提交一件事 |

**为什么强调「一次只做一件事」**：出问题时能单独回退那一个提交；评审时能单独看懂。混在一起，回退要连累无关改动，评审也只能囫囵看过。

## 3. PR（合并请求）流程

### 3.1 什么时候开

**不要攒。** 一件可以独立验证的小改动就开一个 PR。攒到 Sprint 末尾才提，评审就变成盖章 —— 一次看几百行，谁也不会真看。

### 3.2 PR 描述必须写清四件事

1. **改了什么** —— 一两句话
2. **为什么改** —— 对应哪个需求 / 哪个 OpenSpec change
3. **怎么验证** —— 跑了什么命令、看到什么结果、或截图
4. **关联编号** —— Issue 号与 change id

仓库放了一份模板在 `.github/pull_request_template.md`，新建 PR 时自动带出这四项。

### 3.3 谁来审（2026-09-16 简化）

**所有 PR 统一由 infra 线负责人（苏哲勋）审。**

| 谁开的 PR | 审阅人 |
|---|---|
| 吕建江 / 刘帅华 / 蒋励 | **苏哲勋** |
| 苏哲勋 | **蒋励** |

- 课程只要求「至少 1 位非作者审阅」，上表满足。
- **为什么不再按人两两配对**：四个人四条线、每条线各一人，配对矩阵要每人记两个名字，规则一长就容易记错、也容易互相以为对方在看。统一一人审，规则只需记一句：**提了 PR 找苏哲勋**。审阅本来就是 infra 线管仓库规范的固有职责。
- **明知代价**：苏哲勋成了合并单点，他不在线时 PR 会停。处理办法 —— 临时请在线的蒋励代审，并在 PR 评论里说明一句；**不要因为「审的人不在」就自己把自己的 PR 合掉**（那样等于没有评审，而且分支保护也拦不住）。

审阅纪律：

- 审阅者要**真看 diff**，不是点「同意」就走。
- 发现问题直接留在 PR 评论里 —— 不要私聊。评论留在 PR 里才是可留痕的评审证据，课程要这个。
- 审阅者的责任不是「保证没问题」，而是「我看过了，我理解这个改动」。

### 3.4 怎么合并

**Squash merge**（把分支上的多个提交压成一个再合入）。理由：`main` 历史保持线性，一条 PR 对应一个提交，回溯和查问题时好定位。

合完记得**回飞书看板更新状态** —— 见第 5 节。

### 3.5 PR 相关的禁止事项

- 自己合并自己**未经审阅**的 PR（含苏哲勋）
- PR 里包含数据集、模型文件、`.env` 或任何密钥
- 一个 PR 里夹带「顺手重构」—— 另开 PR
- 绕过分支保护直接推 `main`

### 3.6 审阅人检查清单

课程要求「使用 Pull Request 协作，合并前应至少有一位**非作者**成员**审阅**；审阅意见及修改记录保留在 Git 平台」。所以**审阅不是盖章** —— 审阅人要对下面六项逐项给结论，意见写在 PR 评论里（不是私聊）。

| # | 检查项 | 不合格怎么办 |
|---|---|---|
| 1 | **范围**：这个 PR 只做了一件事，没有夹带「顺手重构」或无关文件 | 要求拆 PR |
| 2 | **关联**：描述写清「改了什么 / 为什么改 / 怎么验证 / 关联编号」四项（§3.2） | 要求补描述 |
| 3 | **规格同步**：改代码的同时改了对应规格（OpenSpec change 或 `docs/contracts/`）—— **规格与代码不一致即缺陷** | 要求补 change |
| 4 | **契约一致**：字段名、列名、接口格式与 `docs/contracts/` 逐字一致，没有自创叫法 | 要求改回契约口径 |
| 5 | **可验证**：PR 里有能复现的验证方式（命令 + 期望输出），不接受「我本地跑过了」 | 要求附命令与结果 |
| 6 | **不含敏感物**：没有数据集、模型文件、`.env`、密钥（§3.5） | 直接打回 |
| 7 | **跨 PR 共存性**：本 PR 与**当前其他待合 PR** 是否改了同一文件？ | 见下方「怎么测两两共存」 |

#### 怎么测「两两能共存」（与「本 PR 干净」是两件事）

`git diff --name-only --diff-filter=U` 只能证明「rebase 后没留未合并路径」，**测不出两个 PR 合到一起会不会撞**。

**「各自与 `main` 无冲突」推不出「彼此能共存」** —— 两个 PR 改同一文件的相邻位置时，各自都是干净的，合到一起必冲突。用前者当证据，会得出一个比实际更强的结论。

**测法**：拿两个待合分支的**同一份文件做三方合并**，而不是各自与 `main` 比。

```bash
# 比较 A、B 两个待合分支（共同基准取 merge-base）
git merge-tree $(git merge-base origin/main origin/A) origin/A origin/B | grep -c '<<<<<<<'
# 0 = 这两个分支可共存；非 0 = 会撞，必须在合并顺序里排先后
```

**测出会撞之后怎么办**：把两者**排成先后**（后合的那个负责 rebase 解冲突），并把这个依赖写进合并顺序说明里 —— 不是等 maintainer 在网页上一个个点着试。

**审阅结论只有三种，都要留文字：**

| 结论 | 什么时候用 |
|---|---|
| **Approve** | 六项全过 —— 可以合并 |
| **Request changes** | 有不合格项 —— **必须写清是哪一项、怎么改**，不能只点按钮 |
| **Comment** | 有疑问但不确定是否阻断 —— 写问题，等作者回 |

**时限**：收到请求后 **1 个工作日内**给结论（`docs/team-charter.md` §4.2）。当天没空，也要回一句「收到，明天给」。

**一条硬规矩：审阅意见与回应必须留在 PR 里。** 课程明确要求「审阅意见及修改记录保留在 Git 平台」—— 只在群里说「我看过了」，等于没有审阅记录。

## 4. 项目开发规范

这一节管「代码怎么写」。红线（不能做什么）在 `AGENTS.md`，两条线各自的技术细节在 `<线>/README.md`，本文只写**全组统一**的部分，三处不重复。

### 4.1 代码风格

| 语言 | 工具 | 命令 | 说明 |
|---|---|---|---|
| Python | **ruff** | `ruff check .` / `ruff format .` | 已列进两份 `requirements.txt`。**不引入** black / flake8 / isort —— ruff 一个顶三个，工具越多越没人跑 |
| 前端 | Vue 脚手架默认（ESLint + Prettier） | `npm run lint` | 跟着脚手架走，不自己配规则 |
| Markdown | 不强制 | — | 但同一份文档内格式保持一致 |

**不手工调整别人的代码格式。** 纯格式的改动会产生大量无意义 diff，把真正的改动淹没掉，评审时是最费眼的一种 PR。

### 4.2 命名与注释

- **标识符一律英文**：变量、函数、类、数据库字段名、接口路径、特征列名，都用英文。
- **注释与提交信息用中文。** 组内交流用中文，看得快。
- **注释只写「为什么」，不写「是什么」** —— 代码本身说明了是什么，重复一遍只会跟着代码一起过期。

```python
# 好：解释了一个不显然的决定
# 必须按时间序切分，随机会引入时序数据泄漏
train, test = split_by_time(X, y)

# 差：把代码翻译了一遍
# 按时间切分数据
train, test = split_by_time(X, y)
```

### 4.3 配置与密钥

- **`.env` 本地创建，不入库**；**`.env.example` 必须入库**，列出所有键名、不含真实值。
- **谁引入新配置项，谁负责同步 `.env.example`** —— 忘记同步，别人 clone 后起不来，而且报错信息通常指不到真正的原因。
- 数据库连接串、令牌、密码一律走 `.env`，**不写死在代码里**（写死在代码里的一定会进 git 历史）。
- **密钥误提交后，删文件不算解决。** 文件删了，git 历史里还在，谁 clone 都能翻出来。正确做法：立刻在群里说一声，改掉那串密钥（重新生成），再处理历史。不要沉默地 `git rm` 了事。

### 4.4 错误处理与日志

- **禁止静默吞异常**：`except: pass`、空 `catch`、只 `print` 不抛出 —— 出错就让它出错，不要盖住。
- **对外**：错误码只用 `docs/contracts/api-format.md` 里那 5 个，不自造；`50000` 的 `message` 不得回显堆栈、SQL 语句、文件路径（课程明确要求「非法输入不泄露内部信息」）。
- **对内**：服务端日志要记全（含堆栈），用 `logging` 模块，不用 `print`。对外少说、对内说清，这两件事不矛盾。
- 前端的三态与错误码处理，见 `frontend/README.md` 的七条通用约定。

### 4.5 依赖管理

- **加依赖 = 改清单文件**：Python 改 `<线>/requirements.txt`，前端改 `frontend/package.json`。**并在 PR 描述里说明为什么加**。
- **装之前先看清单里有没有能用的。** 四个 `pip install` 八个功能重叠的包，是项目后期最容易被诟病的一点。
- **版本策略：现阶段不钉死版本号**，跑通后回填 `==x.y.z`。理由：这些包的可用版本还没实测过，现在乱钉会让人装不上；等各线跑通了再锁，锁的才是真跑通的那一版。
- 不装只为自己方便、与项目无关的包。

### 4.6 测试的最低要求

**不做覆盖率门禁**（见第 7 节），但有两条底线：

1. **修缺陷必须带一个能复现该缺陷的测试。** 没有回归测试，同一个缺陷一定会再犯一次。这条是四条底线里最值钱的一条。
2. **新增接口至少一条正常路径 + 一条异常路径测试**（异常路径至少覆盖「参数非法」）。

测试放各线的 `tests/` 目录，Python 用 pytest（已在 `requirements.txt` 里）。

> 数据与模型线另有一条更高的要求：「**可复现**」优先于单元测试 —— 必须能出示 `docs/data-pipeline.md` 要求的固定版本与统计表。别人跑不出同一份结果，代码写得再干净也没有意义。

### 4.7 提交前自检

```bash
ruff check .                  # Python：改过哪条线就在那条线跑
pytest                        # 有测试就跑（没有测试就跳过）
npm run lint                  # 前端
git status --short            # 确认没有数据集 / .env / 模型文件被误加
git diff --cached             # 提交前看一遍，确认没有调试代码、print、注释掉的死代码
```

**有一条不过就不要提交，更不要「先推上去再说」。** 推上去之后别人也要看这段代码，成本只是转移了，没有消失。

### 4.8 测试由谁负责

课程评分里「软件测试实践」与「软件开发过程实践」**并列最高（各 40 分）**，但本组不单独设测试线 —— 四个人四条线，测试按线分摊，**谁写的谁测**：

| 线 | 测试内容 |
|---|---|
| 数据与模型 | 数据可复现性（固定版本 + 统计表）、模型评估指标（Effort-unaware 与 Effort-aware 两类）的算法正确性 |
| 后端与接口 | 接口单元测试（正常 + 异常路径）、压测脚本、两组安全用例 |
| 前端与可视化 | 页面三态（加载中 / 空数据 / 请求失败）与错误码处理、字段映射是否与 `docs/contracts/` 一致 |
| 工程化 | `pytest` 与 `ruff` / `npm run lint` 接进提交前自检与（后续）CI |

**Sprint 0 不派人、不排期** —— 这个阶段还没有可测代码，硬凑测试是空转。

**Sprint 1 起设测试协调人**，由组长在 Sprint 1 启动时指定，负责汇总各线测试结果、维护缺陷记录、对齐课程要求的测试交付物。

> **为什么是 Sprint 1 而不是 Sprint 2**（审查方 2026-09-17 要求对着课程 Sprint 划分核对后确定）：课程《项目要求》里 **Sprint 1 的交付物**已含「OpenSpec：已实现 change 的规格、**任务勾选与测试**」—— Sprint 1 就要出测试材料，协调人若放到 Sprint 2，Sprint 1 会处于「有测试要求、无协调人」的空档。再往后：**Sprint 2** 明确要求「**单元测试报告**」，**Sprint 3** 要求「功能、集成、系统等测试 + 问题/缺陷处置记录 + 至少两项已验证的非功能需求测试」。三个阶段都要人管，所以从 Sprint 1 起设。

> 为什么现在就要写清归属：课程《分组》一页给出的职责示例原文含「测试」，这件事不能一直悬空。

## 5. Issue 与看板

### 5.1 Issue

- **一个 Issue = 一件可验收的事**（一个交付物或一个缺陷），不是「今天干了什么」。
- 标签约定：

| 标签 | 用途 |
|---|---|
| `type:feat` `type:bug` `type:docs` `type:test` `type:chore` | 类型（`chore` 用于仓库设置、看板搭建一类的工程杂务） |
| `line:model` `line:backend` `line:frontend` `line:infra` `line:docs` | 归属哪条线 |
| `sprint:0` `sprint:1` … | 属于哪个 Sprint |

> **`type:fix` 已废弃，不要使用。** 它原先在仓库里存在、但在全仓库文档中**零引用**，且与 `type:bug` 语义重叠 —— 一条缺陷 Issue 到底挂哪个没有答案。缺陷统一用 **`type:bug`**（它已在文档与 Issue 模板里被引用）。仓库里那个标签需由 infra 线删掉。

### 5.2 看板（飞书多维表格）字段定义

**先定字段再录数据。** 字段一旦开始录数据再改，已录的行要逐条返工，所以字段口径写在代码仓库里，看板本体在飞书。

看板名：`JIT 缺陷预测 · 项目看板`　｜　表名：`任务`

| 字段 | 类型 | 取值 | 说明 |
|---|---|---|---|
| **任务** | 文本（主字段） | — | 一句话说清做什么，与飞书周报「重要工作事项」对应 |
| **迭代** | 单选 | `Sprint 0` `Sprint 1` `Sprint 2` `Sprint 3` | 课程按 4 个 Sprint 推进 |
| **规格变更或任务** | 文本 | OpenSpec 的 change id；无则填 `—` | 课程要求「看板任务须对应到 Sprint 与 OpenSpec 的 change/task」。**纯飞书产物（如需求文档）没有 change，填 `—`，不要硬凑** |
| **类型** | 单选 | `type:feat` `type:bug` `type:docs` `type:test` `type:chore` | 与 5.1 的标签取值一致，便于将来同步回 GitHub Issue |
| **负责人** | 单选 | `蒋励` `苏哲勋` `吕建江` `刘帅华` | 用单选而非人员字段：本期一人一线，姓名即唯一标识；人员字段需要维护 open_id 映射，现阶段是纯成本 |
| **状态** | 单选 | `未开始` `进行中` `待审阅` `已完成` `已延期` | **只有这五个取值**，不得自造（如「差不多完了」）。`待审阅` = 代码已完成但 PR 未合入 |
| **优先级** | 单选 | `高` `中` `低` | `高` = 卡住别人开工或有关键时间点；`中` = 本 Sprint 内应完成；`低` = 有余力再做 |
| **关联链接** | 超链接 | — | 指向 Issue、PR 或 change 的地址。**这一列能点开，课程要求的「可追溯」才算落地** |

**明确不设的两个字段**：`归属线`（一人一线，负责人已唯一确定归属）、`截止时间`（时间点写在飞书周报里，同一件事两处记日期一定会不一致）。

#### 状态判定：五个取值什么时候用

取值本身好记，容易出问题的是**判定** —— 同一条任务，有人标「进行中」有人标「待审阅」，两处一对账就说不清。判定依据只有一条：**交付物现在在哪。**

| 状态 | 什么时候用 | 判定依据 |
|---|---|---|
| 未开始 | 还没有任何交付物，也没人动手 | 无产物、无分支、无 PR |
| 进行中 | 有人在干，但交付物还不齐 | 有产物或分支，但**关键交付物缺项** |
| 待审阅 | 交付物已齐，**在 PR 上等评审合并** | 交付物在分支或 PR 上，**尚未进 `main`** |
| 已完成 | 交付物**已经在 `main`**，别人 clone 就能拿到 | 能在 `main` 上查到该产物 |
| 已延期 | 过了约定截止仍未达到「已完成」 | 有明确截止且已超期 |

**两处最容易搞错：**

- **「待审阅」不等于「有人在审」** —— 只要东西在 PR 上还没合，就是待审阅，哪怕审阅人今天没看。
- **「已完成」以 `main` 为准，不以「我干完了」为准** —— 停在本地或分支上的一律不算。这条与 `docs/dev-handbook.md` 第 10 节完成定义第 4 条一致。

**同一件事出现在两处时（例如飞书周报「本周计划」表与看板「任务」表），必须用同一口径判定，且每次更新周报前先对一次账** —— 两处打架会被当成过程证据不一致。

### 5.3 与周报、OpenSpec 的对应

- 周报「本周计划」表的一行 → 看板的一行，`任务` 字段逐条对应
- 看板的 `规格变更或任务` 能点回 OpenSpec change 或 GitHub Issue/PR
- **合完 PR 记得回看板更新状态** —— 不更新，看板就是摆设，而且这部分是课程评分点

## 6. 与 OpenSpec 规格的对应关系

- **顺序：先有 change 提案，后有代码。** 开 PR 时对应的 change 应已通过评审。反过来（代码写完了再补提案）等于没走规格驱动开发。
- PR 描述里必须写明关联的 change id。
- **改代码必须同步改规格。** 规格与代码不一致，课程判定为缺陷。
- CLI 版本统一 1.11.0、`init` 只能在仓库根目录跑等约定，见 `infra/README.md`（本文不重复，避免两处说法不一致）。

### 6.1 一个 change 从创建到归档怎么走

课程要求「使用 OpenSpec 框架实践**规范驱动开发（SDD）**」，其标准工作流是 **propose → apply → archive**。落到本项目：

| 阶段 | 什么时候做 | 谁做 | 产出 | 约束 |
|---|---|---|---|---|
| **propose** | 要做一个**新能力**或**改动既有规格**时 —— **写码之前** | 提出人（任何一条线） | `openspec/changes/<change-id>/`：`proposal.md` + `specs/` + `design.md` + `tasks.md` | 顺序：**先有提案，后有代码**。需求变更也走这里，不得只改代码 |
| **规范评审** | 提案写完、写码之前 | 苏哲勋（**提案人与审阅人不得同一人**）+ 相关线确认接口口径 | PR 上的审阅意见 | 评审对象是**规格**，不是代码 —— 这是 SDD 与传统流程最大的区别 |
| **apply** | 提案通过后 | 提案人 | 按 `tasks.md` 逐条实现并勾选；跑 `openspec validate` | 每个任务要有**可验收的交付单元**；勾选不等于合格（见 §4.6） |
| **PR + 审阅** | 实现完成 | 作者 + 苏哲勋 | PR（描述里写 change id） | 走 §3 全部流程 |
| **archive** | PR 合并后 | 提案人 | `openspec archive <change-id>`，规格并入 `openspec/specs/` | **归档后当前规格必须与产品一致**（课程 Final Release 验收项） |

**三条最容易违反的：**

- **代码写完了再补提案** = 没走 SDD。顺序错了，评审就没有意义。
- **change 里的任务勾了但功能不合格** —— 课程原文：「OpenSpec change 中的任务完成**不等于**功能合格，必须有实际运行或验收测试等证据支撑」。
- **改了需求只改代码、不改规格** —— 课程判定为缺陷，走 `docs/defect-management.md`。

**当前有哪些 change**：`openspec list`。

## 8. 团队节奏（Scrum 仪式）

课程要求「使用 Scrum 敏捷开发框架」。角色已在根 `README.md` 定好（PO 苏哲勋 / SM 蒋励），这里补上**节奏** —— 没有节奏，Scrum 就只是两个头衔。

| 仪式 | 频次 | 谁组织 | 产出 |
|---|---|---|---|
| 每日站会 | 每个工作日，10 分钟内 | SM（蒋励） | 三句话：昨天做了什么 / 今天做什么 / 卡在哪 |
| 迭代评审 | 每个 Sprint 末 | PO（苏哲勋） | 演示可运行的增量 —— 对应课程「每个 Sprint 都必须交付一个可演示、可运行的产品增量」 |
| 回顾会 | 每个 Sprint 末，评审之后 | SM（蒋励） | 一条「继续」+ 一条「改进」，写进下个 Sprint 的约定 |
| 课程进展汇报 | 每周五课上 | 组长（蒋励） | 当周完成情况 —— 对应课程「每组每周五课上需进行一次简短进展汇报」 |

**三条约定：**

- **站会只同步信息，不做技术讨论。** 10 分钟内没结论的事，会后单独拉人 —— 否则站会会变成最长的那场会。
- **允许异步。** 站会形态写死为「10 分钟内、只答三个问题」，但**允许用群里文字同步代替开会**，**频次仍是「每个工作日」**（审查方 2026-09-17 裁定）。理由：课程明确要求使用 Scrum，把频次降成「每周 2–3 次」在答辩时不好解释；而「每日同步 + 允许异步」既守住仪式、又不给组员添会。
- **站会内容不写进仓库文档。** 任务与进度以飞书周报和看板为准（见 `AGENTS.md` 开头一节），站会只是推进它们的日常手段，不另开一份记录。
