# 测试侧人工协助清单

> **本清单的边界**：只列**测试人员需要人工协助完成、超出自动化能力**的事项——也就是"机器判不了、或必须由人在真实设备/账号上留证"的部分。
> **不含开发修复任务**：修 BUG-01/02/03/05、修 #222/#226 等属于模块 owner 的工作，不写在这里（见 [`system_test/bug_list.md`](system_test/bug_list.md) 的「修复归属」列）。
>
> 每条都标了 **【需人工协助的环节】**，说明卡在哪一步、为什么自动化过不去、谁来做、做完怎么算完。
> 标记含义：`需判断` = 业务/口径判断；`需操作` = 必须真人在真实界面/设备上做；`需签字` = 责任签署；`需确认` = 环境事实核对。

自动化已完成的部分（供对照）：494 条单测全绿、35 条接口 34 通过、18 条安全、13 条异常场景、4 档负载、25 模型矩阵 23/25、7 张浏览器截图、137 条 Scenario 自动子集 10/10。

## A · 需判断 / 需业务确认（自动化判不了）

### A1 `需判断` 验收结论由谁签、签什么

- **【需人工协助的环节】**：结论措辞与接受与否。
- **为什么自动化做不了**：AI-R5 明确「验收结论涉及是否接受交付，必须人工做出」；模型无法承担交付责任。
- **人工动作**：通读 [`acceptance_test/acceptance_report.md`](acceptance_test/acceptance_report.md) §5，确认「验收不通过」是否符合你的判断；不同意就改结论并写明理由。
- **完成判据**：报告末尾有复验人、日期、结论、签名。

### A2 `需判断` 预测准确性的阈值与口径

- **【需人工协助的环节】**：阈值定多少、用哪个指标。
- **为什么自动化做不了**：25 个模型 accuracy 0.834~0.864 都过 80%，但 recall 只有 ≈0.26——"高准确率、低召回"是否可接受是业务取舍，不是脚本能定的。
- **人工动作**：看 [`acceptance_test/model-accuracy-evidence.md`](acceptance_test/model-accuracy-evidence.md)，在验收方案里写死「用 accuracy / AP / recall 中的哪个，阈值多少，谁确认的」。
- **完成判据**：验收方案 §2 的阈值表由人工确认签署，`acceptance_cases.md` A-03 据此重判。

### A3 `需判断` A-14「返回后筛选条件丢失」按哪条路走

- **【需人工协助的环节】**：判定这是缺陷还是设计。
- **为什么自动化做不了**：实测事实清楚（筛选 `CAMEL-20333` 进详情再返回，输入框清空、列表回到 20 条），但"要不要保留筛选"是产品口径。
- **人工动作**：二选一并记录：① 视为缺陷 → 交前端改（筛选进 URL 或 keep-alive 缓存）；② 视为设计 → 修改验收标准表述，A-14 改判通过。
- **完成判据**：`acceptance_cases.md` A-14 的结论与依据更新，或生成一条新缺陷单。

### A4 `需确认` 已关闭但可能没修的 issue 怎么定性

- **【需人工协助的环节】**：与 owner 确认关闭口径。
- **为什么自动化做不了**：核对代码可以自动化，但"关闭是否合理"需要 owner 说明。
- **事实**：#219 已关闭，但 `backend/Dockerfile` 仍未装 `transformers`；#220 已关闭，但 D-03、D-06 本轮仍复现。
- **人工动作**：找 owner 确认「容器不承载 e2e」是否成立；不成立就在 #219 / #228 里 reopen 或补说明。
- **完成判据**：两个单里有明确口径评论，`bug_list.md` 的「已关闭但需留意」段同步更新。

### A5 `需判断` 缺陷级别与是否计入缺陷数

- **【需人工协助的环节】**：级别确认。
- **为什么自动化做不了**：测试方只能"建议级别"，级别影响交付判断，需 owner / 评审确认。
- **人工动作**：对 `bug_list.md` 汇总表的 12 条逐条确认级别（当前建议：严重 4 / 一般 5 / 轻微 3）。
- **完成判据**：汇总表「级别」列有确认痕迹（评论或评审记录）。
