# 缺陷处理边界与职责

> 适用范围：本仓库四类测试（单元 / 集成 / 系统 / 验收）执行过程中发现的一切问题。
> 一句话口径：**测试方只负责把缺陷说清楚并提 issue，不负责修**；修复归模块 owner，裁定归评审，验收结论归人工。

## 1 · 职责划分

| 环节 | 测试方（neon / 测试文档负责人） | 开发方（模块 owner） | 产品 / 评审 |
|---|---|---|---|
| 发现与复现 | ✅ 必做：在真实环境复现，记录实际结果 | — | — |
| 写清缺陷 | ✅ 必做：现象、复现步骤、预期、实际、影响范围五要素齐全 | — | — |
| 提交 issue | ✅ 必做：在代码仓库建单，贴证据与环境 | — | — |
| 定级与归属 | ✅ 建议级别 + 影响模块 | 确认或调整 | 争议时裁定 |
| 修复 | ❌ **不做**：不改 `backend/`、`frontend/`、`data_model/` 产品代码，也不改他人测试断言来"让自己通过" | ✅ 实现修复 | — |
| 口径裁定（改文档 or 改代码） | ❌ 不裁定，只提供实测证据 | 提方案 | ✅ 决定 |
| 回归验证 | ✅ 修复后按原步骤复跑并回填结果 | 提供修复提交号 | — |
| 关闭 issue | ✅ 回归通过后关闭；重复项合并后关闭 | 可自行关闭已修项 | — |
| 验收结论 | ❌ 不代替（AI-R5） | — | ✅ 人工签署 |

**边界补充**：

- 测试方可以提交**测试脚本**的修复（如 `backend/scripts/*.py` 的空库前置），但必须在缺陷清单里留痕（BUG-06 即此类），不能"悄悄修掉"。
- 测试方不为了凑 Bug 数量编造问题；无法复现的只进「候选观察」，不进缺陷清单。
- issue 是唯一真源；`docs/test` 里的 Bug 清单是**快照 + 证据索引**，两边冲突时以 issue 状态为准。

## 2 · Issue 必含内容（缺一项即视为不合格）

```markdown
## 现象
一句话说清用户/调用方看到了什么（含状态码、错误文案、页面表现）。

## 复现步骤
1. 前置：环境、启动命令、数据前提（提交哈希 / 模型名 / 令牌）
2. 操作：可复制的命令或页面路径
3. 频率：必现 / 偶现（偶现需给出现次数）

## 预期结果
按 `docs/api/`、`openspec/specs/` 或产品口径应发生什么。

## 实际结果
实际返回的响应体 / 截图 / 日志片段（脱敏后贴原文，不要只写"报错了"）。

## 影响范围
影响哪些端点 / 页面 / 模型 / 环境（本机 / 容器 / 干净检出），是否阻断验收。
```

附：**证据**（记录文件路径、截图文件名）、**被测提交 SHA**、**建议级别**、**建议归属模块**。不含密钥、令牌、个人数据、真实用户信息。

## 3 · 级别定义

| 级别 | 判据 | 处置要求 |
|---|---|---|
| 致命 | 系统不可用、数据错误或丢失、安全漏洞 | 立即修，阻断交付 |
| 严重 | 核心功能不可用（页面核心内容空白、核心接口恒定失败），或有可复现的错误结论 | 交付前必修 + 回归 |
| 一般 | 局部功能异常、错误码/文案误导、需绕过才能用 | 排期修，验收前评估 |
| 轻微 | 文档与实现不符、体验瑕疵，不影响功能 | 可随版本修 |

级别由测试方**建议**，开发方确认；口径冲突时由评审裁定，测试方不自行降级。

## 4 · 状态流转

```text
新建（测试方） → 已确认（owner 认领） → 修复中 → 待验证（owner 给出修复提交）
      ↑                                              ↓
      └──────── 回归不通过，退回并补充证据 ←──── 待验证（测试方回归）
                                                    ↓
                                              已关闭（测试方或 owner）
```

- 测试方负责「新建 → 已确认」的举证，以及「待验证 → 已关闭 / 退回」的回归。
- 关闭必须附**回归证据**（同一 SHA 上的命令与输出），不允许"应该好了"就关。
- 长时间无响应的单，测试方在周报里点名，不代改代码。

## 5 · 重复 issue 的判定与合并

**判定为重复的三个条件**（满足任一即合并）：

1. 同一代码位置 / 同一文件同一行导致；
2. 同一根因的产物缺失或配置错误（例：两张输入表未按布局生成，被拆成"语义表"和"文本表"两单）；
3. 同一现象在同类入口重复登记（例：同一错误码在多个端点各开一单）。

**合并动作**：

1. 选定保留单：优先保留**证据最全、复现步骤最具体**的一条；其次保留编号最小的一条；
2. 在保留单正文补一节「合并记录」，列出被合并单号与各自独有的信息（不丢事实）；
3. 被合并单追加评论说明「与 #X 同根因，已合并」，再关闭（标记 `duplicate`）；
4. 测试方发起的合并须由保留单 owner 确认，避免误并。
