## 为什么要按人分包

之前的问题不是文档少，而是**同一个问题有多种说法、没人知道该看哪一份**：联调库/token 各写一份（导致 T-FE-01 取到错库）、计划散在两条线各一份、"这活该谁做"每次都要现问。所以按人切开：每个人一页，写清「能改什么、不能碰什么、交付什么、按什么原则决策、谁有权签字」。

## 四条共同规矩（所有人适用，违反就不合）

1. **提交前 CI 必绿。** 红着推等于把问题转给别人；`ruff` / `pytest` / `openspec validate --specs --strict` / `check_spec_references links` 四道门禁本地先跑一遍。
2. **联调只认 `docs/frontend/integration-log.md` §0。** 库、`API_TOKEN`、`MODEL_DIR`、端口都在那一张表；个人 `.env.local` 是它的下游，不是它的替代。
3. **不写个人绝对路径进任何入库文件。** 写了的人能跑，别人必然 `50000`。
4. **一个 PR 只做一件事。** 代码和台账不同时动；改口径必须同一 PR 同步下游 `.env.example`，描述标作用域标签（`[联调基线]` / `[契约]` / `[归档]`）。

## 分包怎么写（模板）

每份必须回答五个问题，少一个都算没写：

1. **负责范围**：有权直接改哪些文件/目录；
2. **不越界**：哪些活必须找别人（写明找谁）；
3. **交付物**：这条线交什么东西、验收看什么；
4. **原则**：做判断时的取舍依据（不是流程，是价值判断）；
5. **签字权**：哪类 PR 只有你能批。

## 变更

- 新增/调整分工：改本目录 + `docs/common/team-charter.md` §1 分工表，**同一 PR**；
- 人的原则变化（比如换了取舍标准）：本人提交，组长在 PR 里确认。
