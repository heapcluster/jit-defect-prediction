# 文档写作规范

> 版本 1.2 ｜ 创建 2026-09-17 ｜ 更新 2026-09-22 ｜ 主笔 蒋励 ｜ 审核 苏哲勋

**适用范围**：仓库内全部 Markdown 文档 + 飞书上的《产品需求文档》《产品设计文档》《工作周报》。

## 0. 为什么单独定这份

课程把「技术设计文档」列进 **40 分**的「软件开发过程实践」维度，同时要求「需求变更必须同步新增或修改管理工具及 OpenSpec change 记录」。文档一旦命名混乱、格式各异，评审人找不到、对不上，等于白写。

## 1. 文档命名规则

### 1.1 仓库文档（文件名）

| 规则 | 说明 | 例 |
|---|---|---|
| 全小写，单词间用 `-` | 不用下划线、不用空格、不用驼峰 | `data-pipeline.md` |
| 一律 `.md` | 不交 `.docx` / `.txt` / 无后缀 | — |
| 一文件一主题，名字即主题 | 看名字能猜到内容 | `sprint0-scope.md` |
| **不放日期**（导出件除外） | 文档是活的，日期进变更日志 | — |
| 导出件带日期 | 只有归档用的导出件才带 | `report-20260918.md` |
| 目录说明固定用 `README.md` | 每个目录的说明一律这个名 | `backend/README.md` |

**禁止**：`新建文档.md`、`临时.md`、`草稿.md`、`xxx_final_v2.md`、中文文件名。

### 1.2 飞书文档（标题）

| 文档 | 标题格式 | 例 |
|---|---|---|
| 工作周报 | **`工作周报-日期`**（课程指定，不得自创） | `工作周报-20260911` |
| 需求文档 | `产品需求文档` | — |
| 设计文档 | `产品设计文档` | — |
| 看板 | `JIT 缺陷预测 · 项目看板` | — |

### 1.3 分支名与文件名对应

分支名用 `docs/<线或主题>/<简述>`，简述一般就是文档名去掉 `.md`。完整规则见 `docs/collaboration.md` §1.1。

## 2. 注释格式要求

### 2.1 三个层次，只写该写的

| 层次 | 写什么 |
|---|---|
| **文件头** | 这个文件干什么、**输入 / 输出 / 怎么跑**、有什么坑 |
| **函数 / 方法** | 参数含义、返回值、异常、**为什么这么做**（做法不直观时） |
| **行内** | 只写「**为什么**」，不写「做了什么」 |

### 2.2 Python

```python
"""从 Git 提交记录中抽取 Kamei 14 项特征。

输入  : data_model/data/commits.csv（02 步产出的提交清单与标签）
输出  : data_model/data/features.csv
运行  : python 03_extract_features.py --since 2023-01-01
注意  : --since 只决定给哪些提交算特征，不截断历史 —— 历史类特征必须用完整历史
"""

def compute_rexp(history, commit):
    """按契约二（冻结版）的衰减公式 Σ count(n)/(n+1) 计算 rexp。

    对无法定位历史的提交记 0、不排除 —— 排除会让行数少于提交清单全量。
    """
```

**硬要求**：

- 公开函数**必须有** docstring（一句话说明做什么即可）
- 文件头 docstring 必须含**输入 / 输出 / 运行命令**三样
- **中文注释** —— 本项目文档与注释统一用中文（代码标识符、技术术语除外）

### 2.3 JavaScript / Vue

```js
/**
 * 拉取高风险提交列表。
 * @param {number} page 页码，从 1 开始
 * @param {string} [riskLevel] 可选风险等级过滤，取值见 docs/pages.md 三态约定
 * @returns {Promise<{items: Array, total: number}>}
 * @throws {ApiError} 后端返回非 2xx 时抛出，由调用方按页面三态展示
 */
```

- 每个 `.vue` 单文件组件在 `<script setup>` 顶部写明：**这个页面用接口的哪些字段**（指 `docs/pages.md`）
- **页面三态（加载中 / 空数据 / 请求失败）必须各有注释标明** —— 这是前端测试的最低要求

### 2.4 SQL

```sql
-- commit_label：一个提交可有多个打标方法的标签（szz / szz_lite 各一行）
-- 主键用 (commit_hash, label_method) 复合，保证同一方法不重复打标
CREATE TABLE commit_label (...)
```

- 建表语句**逐表写一行说明**；字段含义不直观的单独注
- 字段名照契约一，**不得自创**（`docs/contracts/data-fields.md`）

### 2.5 不要写的注释

- 复述代码：`i += 1  # i 加一`
- 注释掉的死代码：删掉，Git 记得住
- 与文档重复的长篇说明：指到文档，不复制
- 没有责任人的 TODO：写 `# TODO(蒋励, 9/25): ...`，否则就是永远不做

## 3. Markdown 排版规范

### 3.1 结构

- 一级标题 `#` 只有一行（文档名）；章节用 `##`，小节 `###`
- `##` 章节**不超过 10 个**，超了就拆文件
- 每份文档**开头必须有文件头**：`> 版本 X.Y ｜ 更新日期 ｜ 主笔 ｜ 审核`
- 每份文档**末尾必须有变更日志表**：日期 / 版本 / 变更人 / 主要变更

> 「末尾附变更日志」是 `docs/README.md` 第 3 节早就定下的硬要求；**版本头本次一并规范化**（此前只有部分文档有）。
>
> **迁移办法**：新文档一律照此；历史文档**在下次因别的原因改动时顺手补齐**，不单独为补版本头开 PR。
>
> **截至 2026-09-17 的实际覆盖范围（写清边界，不写「全部」）**：本 PR 补齐 6 份**已有交付文档** —— 根 `README.md`、`docs/README.md`、`data_model/` `backend/` `frontend/` `infra/` 四个目录 README；另有 **3 份新增文档**（`team-charter.md` / `writing-norms.md` / `defect-management.md`）天生带版本头，不属「补齐」。
>
> **有意未套用本规范的五类**：
>
> | 文件 | 为什么不用 |
> |---|---|
> | `AGENTS.md`、`CLAUDE.md` | AI 工具规则入口，不是交付文档；其版本由工具集成方式决定 |
> | `openspec/changes/**` 下的**全部文件**（`proposal` / `design` / `tasks` / `README` 与各能力 `spec.md`） | **规格与提案的版本由 OpenSpec change 机制管理**（change id + 归档状态），再叠一层文档版本号会两套版本打架；一张 change 一个 id，change 内所有文件同理 |
> | `.github/pull_request_template.md`、`ISSUE_TEMPLATE/*` | 模板类文件，改了就是改了，无版本概念 |
> | `data_model/reports/*.md` | **数据产物报告**，版本由产出它的脚本与`feature_version` 决定，不由文档版本号表达 |
> | `.claude/`、`.codebuddy/`、`.qoder/` 下的文件 | 第三方 AI 工具配置，不是项目文档；内容由工具自己维护，本规范覆盖不到 |
>
> 上一版这里写「仓库内全部 Markdown 已补齐」—— **不实**：实际只补了 6 份，且上面五类本就不该套用。**写「全部」等于给复核人留一个一查就破的坑。**（本表行数与「五类」逐一对齐，避免出现 §4.2 那种「正文说五项、表里六行」的同类错误。）
>
> **主笔与审核都要写真人名**，不写「全体」；且**审核人不得与主笔同一人**（课程要求「合并前应至少有一位非作者成员审阅」）。

### 3.2 表格与代码

- 表格用于**可枚举的对照关系**（谁做什么、字段取值、状态口径）；叙述性内容用列表
- 命令一律用代码块，**给可直接复制执行的完整命令**
- 命令里的路径用仓库**相对路径**

### 3.3 版本号怎么走

| 改动 | 版本 |
|---|---|
| 小改 / 加章节 / 改口径 | 0.1 步进 |
| 整体重构 | 1.0 步进 |

**跨分支并行修改同一份文档时，版本号按「合并顺序」预留。** 三步，缺一不可：

1. 先看 `main` 上该文档的当前版本，再看**预计会先合入的其他 PR** 占了哪些号
2. 本分支取「排在它们之后」的号，**并在变更日志那一行写明预留给了哪个 PR**
3. **合并后核对实际占用的版本号** —— 若前面的 PR 没按预期占号、或合并顺序变了，本条目要改号并同步文件头

> **这条是从一次实际问题里补出来的**：`docs/collaboration.md` 曾从 1.1 直接跳到 1.5，只在 PR 描述里说明「1.3 归 PR #3、1.4 归 PR #22」。**描述里的说明过期就没人看** —— 后来读文件的人只看到跳号，无从判断是预留还是随手写的。**预留理由必须写进变更日志本身。**

4. **重编号一个文件的版本后，必须全仓扫一遍引用点。** 至少要扫这五处：契约索引表（`docs/contracts/README.md` 的状态表）、各线 README、`docs/` 下的规范与链路文档、`openspec/changes/**` 的规格与 tasks、以及**已发出的 PR 描述**。

> **这条是从一次真实事故补出来的**：`docs/contracts/data-fields.md` 重排变更日志后文件头由 1.0 变为 1.4，但 `docs/contracts/README.md` 状态表还写 1.2 —— 结果**后端线照那张表把「契约一 v1.2」抄进了他的 change 提案**。版本号写错不是笔误，是**会顺着引用链传播**的，而且传播到别人手里就变成别人的错。
>
> 扫描命令示例（PowerShell）：在仓库根跑 `Select-String -Path (Get-ChildItem -Recurse -Filter *.md).FullName -Pattern "契约[一二三].*v\d+\.\d+"`，逐条判定「当前版本」还是「历史陈述」——**历史陈述（变更日志里的旧版本号）不要改**，改了反而失真。

**改口径必须同时在变更日志里写明「改了什么、为什么改」。** 只改正文不写变更日志，视为未完成 —— 课程要求「审阅意见及修改记录保留在 Git 平台」，变更日志就是这条要求的最小落地。

## 4. 工作周报模板使用规范

### 4.1 命名与提交（课程硬要求）

课程《课程要求及日程安排》原文：

| 项 | 要求 |
|---|---|
| 关键产出物 | 工作周报（via 飞书共享文档） |
| **提交时间** | **每周五晚上**（放假除外） |
| **提交格式** | **`工作周报-日期`**，如 `工作周报-20260911` |
| 谁提交 | 各组组长以**组名**建立飞书共享文件夹，周报放在里面 |
| 缺勤 | **无故缺勤 3 次，取消成绩** |

### 4.2 模板结构不得改动（硬规矩）

**周报有既定模板：只能往既有表格里填内容，不得增删表格、不得改表头、不得改列数、不得新增章节。**

| 允许 | 不允许 |
|---|---|
| 在既有表格的单元格里填写内容 | 新增 / 删除表格、增删列、改列名 |
| 按需在单元格内换行、加序号 | 调整表格顺序、改表头的措辞 |
| 首次按模板新建一份周报 | 把模板替换成自己设计的格式 |
| 在模板自带的三张表里把内容写具体 | 改动三张表**上方那三段说明文字**、新增章节、调整三张表的顺序 |

**判据（可执行版）**：比对基线是 **`docs/templates/weekly-report-template.md`（模板骨架快照 1.0）** —— 模板只存在于飞书，仓库里没有副本就没法复核，所以先把骨架固化入库，判据才有得比。

**合并前逐项打勾，六项全过才算「没改模板」：**

| # | 检查项 | 怎么查 | 不合格即打回 |
|---|---|---|---|
| 1 | **三节都在、顺序不变** | 对照快照的「模板骨架」三节 | 缺表 / 换序 |
| 2 | **三节上方的说明文字未被改动** | 逐字对照快照里引用的三段说明原文 | 改说明文字 |
| 3 | **表头逐字一致** | 本周总结 3 列；本周计划与下周计划的列/字段按快照 | 增删列、改列名 |
| 4 | **没有新增章节** | 章节列表与快照一致 | 加章 |
| 5 | **块类型未变**（`sheet` / `table` / `bitable`） | 见快照标注 | 换块类型（如 sheet 换成普通表格） |
| 6 | **填的是内容、不是格式** | 单元格里有实质内容；空模板仍是快照里的空行形状 | 把模板替换成自设计格式 |

> **第 2 项与第 4、5 项是本轮补的** —— 上一版判据只查三张表的表头，把「丢表 / 加章 / 改说明文字 / 换块类型」这几件**一律放行**了，而它们同样算改模板。

**留痕**：把「比对基线版本 + 结论」写进当周周报的「证明材料」格（例如 `周报模板 1.0 比对通过：三节齐、说明文字未动、表头一致`）。**没有留痕的比对等于没做** —— 这也是上一版判据的缺口：「逐字比一遍」是个动作，不是产物。

### 4.3 三张表怎么填

模板自带三张表，每张表上方都有一段说明，**那段说明就是填写口径**：

| 表 | 模板说明（原文摘） | 谁填 | 注意 |
|---|---|---|---|
| **本周计划** | 「在每周伊始写下当周工作计划，需要细化到**当周具体要做的事儿，具体哪位同学负责**。在上次周报的『下周计划』的基础上制定，性质：**承诺、执行与兑现**，颗粒度较细」 | 组长汇总（各人供稿） | 状态用五个固定取值之一（`docs/collaboration.md` §5.2），**不得自造** |
| **本周总结** | 「在每周结束工作前几分钟或结束工作后总结本周工作，由负责各个具体工作事项的同学独立填写，或由**组长汇总后统一填写**。均需**提供佐证材料**证明任务完成的有效性」 | **组长统稿** | 数字必须是**实测值**；没做完的**如实写进「待改进内容」**，不要藏 |
| **下周计划** | 「在本周工作结束时及时安排下周计划。性质：**规划与启动**，颗粒度相对**较粗**（准备做什么，重点在方向），注意与本周计划的区别」 | 组长汇总 | 与看板未完成项对齐 |

**「本周计划」与「下周计划」的区别是模板明确定死的**：前者细到「谁做哪件事」（承诺），后者粗到方向（规划）。不要把两张表写成一样。

### 4.4 禁止事项

- **不要把周报当聊天记录**：写「进展顺利」等于没写。要写**交付物 + 证据**（PR 号、commit、报告路径、文档章节）
- **不要只写自己的部分**：组长统稿时必须把四个人的内容都收进来
- **不要改模板**：见 §4.2
- **不要漏交**：每周五晚上是硬时间点
- **不要把仓库文档全文粘进周报**：指路径，不复制内容
