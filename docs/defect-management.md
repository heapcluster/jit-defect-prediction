# 缺陷管理规范

> 版本 1.0 ｜ 创建 2026-09-17 ｜ 主笔 蒋励 ｜ 审核 苏哲勋

课程《项目要求》原文要求两件事：

1. 「项目需使用**缺陷管理**工具（项目管理工具通常支持缺陷管理）」
2. 「缺陷使用 Issue 或等价记录管理，**至少记录现象、复现条件、优先级、处理状态和关联提交/change**」
3. 「OpenSpec change 中的任务完成**不等于**功能合格，必须有实际运行或验收测试等证据支撑」

## 0. 工具选型：为什么就是 GitHub Issue

本项目**以 GitHub Issue 为缺陷管理工具**，不另装禅道一类的第三方工具。

| 理由 | 说明 |
|---|---|
| 证据集中 | Issue 天生带标签、评论、关闭记录，且能直接关联 commit / PR —— 正好覆盖课程要的五项，不必在两处维护同一件事 |
| 课程认可 | 课程原文明确「缺陷使用 **Issue** 或等价记录管理」，Issue 即合规答案 |
| 已就位 | `.github/ISSUE_TEMPLATE/bug.md` 已入库，且已按课程要求补齐字段 |

> 「项目管理工具通常支持缺陷管理」是课程对工具的说明，不是指定工具。选 Issue 不违反要求，且比另装工具更利于「证据集中在一处」这条更重要的原则。

## 1. 什么算缺陷

| 情况 | 算不算 | 走什么 |
|---|---|---|
| 功能与规格不符（页面行为、接口返回） | ✅ 缺陷 | **Bug Issue** |
| 接口 / 数据与契约不一致 | ✅ 缺陷 | Bug Issue，**并同时**提 OpenSpec change |
| 运行时报错、崩溃、数据算错 | ✅ 缺陷 | Bug Issue |
| 两项非功能要求（性能 / 安全）不达标 | ✅ 缺陷 | Bug Issue，证据附评论 |
| 文档笔误、措辞优化 | ❌ 不算 | 直接开 PR 修 |
| 新功能、功能增强 | ❌ 不算 | 任务 Issue（`type:feat`） |

**「规格与代码不一致视为缺陷」** 这一条来自根 `README.md` 第 1.4 节的硬规矩；课程原文也要求「需求变更必须通过同步新增或修改管理工具及 OpenSpec change 记录，不得只改代码而不更新规格」。所以这类缺陷**修代码还不够，必须同时提 change**。

## 2. 缺陷记录必填五项（课程硬要求）

用 `.github/ISSUE_TEMPLATE/bug.md` 提。这五项**缺一项，Issue 视为未提完**，审阅人可以直接打回补充。

| # | 字段 | 要求 | 反例 |
|---|---|---|---|
| 1 | **现象** | 看到的实际情况 + 期望情况 | 「接口有问题」 |
| 2 | **复现条件** | 命令 / 请求 / 操作步骤，**别人照做能重现** | 「有时候会」 |
| 3 | **优先级** | 五档之一（见 §3） | 空着，或写「急」 |
| 4 | **处理状态** | 由 Issue 的 open / closed + 看板状态共同体现 | 只在群里说「修好了」 |
| 5 | **关联提交 / change** | 修复的 PR 或 commit 哈希；涉及规格的挂 change id | 空着 |

`bug.md` 模板里已含课程需要的三个补充字段（现象、复现条件、优先级），其余两项在 Issue 正文或评论中补齐。

## 3. 优先级怎么定

课程要求缺陷记录含「优先级」，但没给档位，本项目自定五档：

| 档 | 判据 | 响应 |
|---|---|---|
| **P0 阻断** | 主链路走不通（登录不了、页面白屏、接口 500） | 当天修，站会当场升级 |
| **P1 严重** | 核心功能结果错（预测结果错、趋势图数据错） | 本 Sprint 内必修，进下次站会 |
| **P2 一般** | 非核心路径出错、边界情况未处理 | 本 Sprint 内排期 |
| **P3 轻微** | 界面错位、文案错误、体验问题 | 有余力再做，可延到下个 Sprint |
| **P4 建议** | 优化建议，本身不是缺陷 | 记录即可，不排期 |

## 4. 流转与责任

```
发现 → 提 Bug Issue（五项齐全）→ 打标签 → 定优先级
    → 负责人在看板认领 → 修 → 开 PR（描述里写「修复 #编号」）
    → 非作者审阅 → 合并 → 关 Issue → 看板状态改「已完成」
```

| 环节 | 谁 |
|---|---|
| 提 Issue | **任何人** —— 发现者提，不必自己修 |
| 定优先级 | PO（苏哲勋）；P0 由 SM（蒋励）当场定 |
| 修 | 缺陷所属线的负责人（由 `line:*` 标签指定） |
| 审阅 | 苏哲勋；他自己的 PR 由蒋励审（`docs/collaboration.md` §3.3） |
| 关 Issue | 修复 PR 合并后，由**提出人**确认再关 —— 提的人说「好了」才算好 |

**一条纪律**：修复必须走 PR，**不得直接推 `main`**（分支保护也会拦）。缺陷修完不留痕迹，「处理状态」这项就没有证据。
