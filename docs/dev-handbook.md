# 代码项目开工手册

> 版本 2.2 ｜ 更新 2026-09-16 ｜ 维护：全员公共（蒋励统稿）｜ 审核 苏哲勋
> **本手册只讲代码项目怎么干。** 本周做什么、谁做、做到哪了 —— 看飞书《工作周报》。

## 0. 边界与用法

| 你想知道 | 去哪看 |
|---|---|
| 这周我该做什么、什么时候交、做到什么程度 | **飞书《工作周报-YYYYMMDD》「本周计划」表** |
| 需求是什么、功能怎么描述、页面长什么样 | 飞书《产品需求文档》 |
| 系统怎么设计、API 清单、库表设计 | 飞书《产品设计文档》 |
| **这件事在代码里具体怎么做、跑什么命令、验收什么** | **本手册** |

飞书周报表的「相关文档」列指向本手册的章节。**任务分配以周报表为准，本手册不重复排期、不列负责人、不做验收打勾表。**

### 怎么用

1. 先在飞书周报表找到你负责的那一行；
2. 按它「相关文档」列的指引跳到本手册对应章节；
3. 照「动作」做，按「验收」自查，卡住看该节的「常见坑」。

## 3. 仓库工程基线

对应飞书周报任务 2 ｜ 负责人 苏哲勋

**模板文件已入库**（`.github/pull_request_template.md`、`.github/ISSUE_TEMPLATE/task.md`、`.github/ISSUE_TEMPLATE/bug.md`），本项重点是 **GitHub 网页端设置** —— 这部分没有任何文件能替代。逐项清单见 `infra/README.md` 的「仓库设置清单」节：

- `main` 分支保护：禁止直接推送、禁止强制推送、合并前至少 1 位非作者审阅
- Squash merge 设为唯一合并方式
- 开启 Automatically delete head branches
- **标签建全**：`type:feat` `type:bug` `type:docs` `type:test`、`line:model` `line:backend` `line:frontend` `line:infra` `line:docs`、`sprint:0`
- 三位组员加入协作者并给写权限

**验收**

- [ ] 直接向 `main` 推送会被拒绝（这是设计如此）
- [ ] 新建 PR 时自动带出模板四项
- [ ] 新建 Issue 时可选「任务」「缺陷」两个模板
- [ ] **标签已建全** —— 缺标签时模板不报错，只是静默不挂上，很容易误以为没问题
- [ ] 用一个试跑 PR（改一处错字即可）验证模板与保护都生效，并由非作者审阅合入

**给 AI 的提示词要点**

> 让 AI 核对 `.github/` 下三个模板与 `docs/collaboration.md` 第 3、5 节是否一致（字段名、标签名、审阅规则）。**网页端设置 AI 做不了**，必须自己点。

## 4. OpenSpec 变更流程

对应飞书周报任务 3 ｜ 负责人 蒋励

`openspec/` 与三套工具目录（`.codebuddy/`、`.claude/`、`.qoder/`）**已初始化并入库，`openspec init` 不要重跑**。`openspec/config.yaml` 的 `context:` 已填写技术栈与团队约定；**技术栈变更时要同步改它**，AI 起草规范时读的是这一段。

**动作**

1. 在项目根目录启动 AI，敲：
   ```
   /opsx:propose 数据采集与 SZZ 打标
   ```
   它会在 `openspec/changes/` 下生成 `proposal.md`、`tasks.md` 与 `specs/` 下的规格增量。
2. 用 `openspec validate` 校验格式，然后提交 PR。
3. 完整链路是 `proposal → specs → design → tasks → apply → archive`，**归档后规格必须与产品实际一致**。

**验收**

- [ ] `openspec list` 能看到该 change
- [ ] `openspec validate <change>` 通过
- [ ] change 的 tasks 能对应到飞书看板上的任务（课程明确要求「看板任务须对应到 Sprint 与 OpenSpec 的 change/task」）
- [ ] `context:` 非空且与实际技术栈一致

**给 AI 的提示词要点**

> 直接在项目根目录启动 AI，敲 `/opsx:propose <变更名>`。
> 若 AI 生成的规格不符合实际，**改规格而不是改代码** —— 这是 SDD 的核心。
>
> ⚠️ **绝对不要在 `backend/`、`frontend/`、`data_model/` 等子目录执行 `openspec init`** —— 会在该目录生成第二份规范，评审与追溯立刻失效。

## 6. 拉通数据链路

对应飞书周报任务 6 ｜ 负责人 蒋励 ｜ 协作：苏哲勋

**这是全项目最关键的前置**：不通，后端拿不到数据、前端拿不到接口。

**动作**

1. 克隆 ActiveMQ 仓库，**固定到一个 tag 或 commit**（不许用浮动的 `main`）—— 固定值回填进 `docs/data-pipeline.md` 第 2 节的登记表。
2. 抽取提交记录（GitPython），过滤合并提交。
3. SZZ 打标，**PySZZ 与自研简化版都跑一遍**做对照校验。
4. 计算 Kamei 14 项特征。
5. 汇总成可训练样本集，**打印 7 项统计**（含正样本比例）。
6. 落盘：数据放 `data_model/data/`、结果放 `data_model/reports/`（前者被 gitignore 排除，后者可入库当证据）。

**验收**

- [ ] 数据固定在某个 tag 或 commit，且值已登记（不是「大概用了某个版本」）
- [ ] 报出样本总数、正样本数、负样本数、**正样本比例**、打标方法（`szz` / `szz_lite`，见契约的 `label_method`）
- [ ] **正样本比例合理** —— JIT 数据集通常是个位数到十几百分点。若接近 50%，先查打标逻辑，不要往下走
- [ ] 别人按你写的命令序列能跑出同一份结果

> ⚠️ **触发条件写死**：若 PySZZ 在 Sprint 0 结束前仍跑不通，**直接切自研简化版，不再等待**。不让整条链路卡在一个工具上 —— 这是本项目最容易踩的进度陷阱。

**给 AI 的提示词要点**

> 提示 AI：**训练/检验集必须按 `committed_at` 时间序切分（前 70% / 后 30%），禁止随机切分**。
> 这条写进了 `AGENTS.md` 硬红线 —— `EXP`、`NUC` 等特征与时间相关，随机切分等于让模型提前看到未来，准确率是假的。
> 若 AI 用了 `train_test_split(shuffle=True)` 或未指定 `shuffle=False`，**这是缺陷，必须打回**。

## 7. 库表与接口落地

对应飞书周报任务 7 ｜ 负责人 吕建江 ｜ 协作：刘帅华

**动作**

1. 按 `docs/contracts/data-fields.md` 建**四张表**：`commit` / `commit_label` / `commit_feature` / `prediction`。字段名、类型、索引（`commit_hash` 唯一索引、`committed_at` 普通索引）都照契约。**`commit_feature` 最容易漏** —— 它在 ER 图里是第四张表，字段清单在 `feature-columns.md`，而提交详情接口必须读它才拿得到那 14 项特征。
2. **ER 图的源在契约**（`docs/contracts/data-fields.md` 第四节，Mermaid 鸦爪法）。课程《产品设计文档》要求「数据库 ER 图（陈氏法 或 鸦爪法）」—— 飞书设计文档里引用同一张图，**不要在飞书与契约各画一份**。
3. 决定建表方式（Alembic 或建表 SQL 脚本都行），但必须满足：**别人 clone 后一条命令能把库建好**。
4. 接口按 `docs/contracts/api-format.md` 落地。**课程明确要求 API 优先用 OpenAPI (Swagger) 规范作为载体** —— 后端写完后用 FastAPI 自动生成的 Swagger 作为**实现镜像**，与契约比对是否偏离；偏离就改代码，不要改契约。
5. **实现模型加载**（`docs/sprint0-scope.md` 第 4 节的跨线接口已结清，定方案 A + C）：后端启动时从 `data_model/models/` 加载 `.pkl`，供 `POST /api/predict` 实时推理；同时读 `prediction` 表里数据线预置的批量结果，供三个查询接口用。**特征顺序以 `feature-columns.md` 为准** —— 顺序错了模型不报错，只会静默给出错误答案。

**接口路径速查**（细节以契约为准）

| 接口 | 用途 |
|---|---|
| `GET /api/commits` | 风险列表（分页、按 `risk_score` 降序） |
| `GET /api/commits/{commit_hash}` | 提交详情（含 14 项特征与 `explanation`） |
| `GET /api/trends` | 缺陷引入趋势（按周期聚合） |
| `POST /api/predict` | 在线预测（传 `commit_hash`，实时推理返回概率与解释） |

> 第四个接口是 2026-09-16 冻结前补上的，依据是课程《项目要求》「对外提供在线预测服务」与「预测与解释模块」。**它同时是性能压测的靶子** —— 别拿查询接口代替。

**验收**

- [ ] **四张**表字段名与 `data-fields.md` **逐字一致**（含 `commit_feature`）
- [ ] 有 ER 图（不是纯文字描述），且与契约是同一张
- [ ] 别人 clone 后一条命令建好库
- [ ] `50000` 的 message 不回显堆栈、SQL 语句、文件路径

**给 AI 的提示词要点**

> 让 AI 读 `docs/contracts/data-fields.md`，生成 SQLAlchemy 模型与建表脚本，**并要求它逐字段对照契约、列出任何偏离**。
> ER 图可以让 AI 画 Mermaid `erDiagram`，但**记得记一行 LLM 工具名 + 提示词**（课程硬要求，见第 10 节）。

## 9. 非功能要求的证据

对应飞书周报任务 10 ｜ 负责人 吕建江 ｜ 协作：蒋励

两项要求（讨论0915 已定）：

- **性能**：预测接口 95% 的请求 < 500ms
- **安全**：接口需鉴权；非法或缺失参数返回明确错误，**不泄露内部信息**

验证方式与证据形式已写进 `docs/contracts/api-format.md` 第四节，本项是**把脚本写出来并跑出结果**：

- 性能：`backend/scripts/` 下循环发 100 次请求的脚本 + 响应时间分位数输出
- 安全：① 不带令牌请求 → 应返回 401；② 发送畸形参数 → 返回中不得含堆栈 / SQL / 路径

**验收**

- [ ] **只写「已实现」不算证据** —— 必须有脚本、有输出、有截图
- [ ] 性能结果给出**分位数**（不是平均值 —— 95% 是分位数指标）
- [ ] 安全用例覆盖「缺失参数」与「参数非法」两类
- [ ] 证据放 `backend/scripts/` 与 `docs/`，答辩时能当场出示

**给 AI 的提示词要点**

> 让 AI 写压测脚本（如用 `httpx` 或 `requests` 循环 100 次，统计 p50 / p95 / p99）。
> **要求 AI 同时给出「这条指标怎么算」的说明** —— 答辩时会被问「95% 是怎么来的」，答不上来等于没做。

## 10. 代码侧完成定义与课程硬要求

### 完成定义（DoD）

一件事算「做完」，以下四条**同时**满足（完整说明见 `docs/sprint0-scope.md` 第 5 节）：

1. **代码能跑** —— 不是「写完了」。能在别人机器上按文档跑出结果。
2. **有最小验证证据** —— 跑通的输出、截图或测试结果。**这条最容易被跳过。**
3. **规格已同步** —— OpenSpec 的 spec 或对应契约文件已更新。
4. **PR 已由非作者审阅并合入 `main`** —— 停在本地分支上的代码不算交付。

### 课程硬要求（与代码直接相关）

| 要求 | 落地 |
|---|---|
| AI 生成的图必须标注来源 | 图旁记一行：`> 生成方式：<工具名 + 模型>｜提示词：<原样粘贴>`。架构图、ER 图、流程图、时序图都适用 |
| 看板任务须对应 Sprint 与 change/task | 每个交付项在飞书看板有行，且能点回 Issue 或 OpenSpec change |
| PR 合并前至少 1 位非作者审阅 | 统一由苏哲勋审；他自己的 PR 由蒋励审（见 `docs/collaboration.md` 第 3.3 节） |
| 规格与代码不一致视为缺陷 | 改了行为就必须同步 spec 或契约 |
| 需要可出示的验证证据 | 性能与安全两组证据；周报里每条「已完成」附佐证材料 |
