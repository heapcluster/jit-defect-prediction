# 团队章程 —— 分工、协作与时间

> 版本 1.0 ｜ 创建 2026-09-17 ｜ 主笔 蒋励（组长 / Scrum Master）｜ 审核 苏哲勋（PO）

**本文管三件事：谁做什么（分工）、什么时候交（截止时间）、怎么沟通（协作）。**

代码怎么写 → `docs/collaboration.md`　｜　一件事在代码里怎么做 → `docs/dev-handbook.md`　｜　文档怎么命名排版 → `docs/writing-norms.md`　｜　缺陷怎么记 → `docs/defect-management.md`

**同一件事只在一处写。** 本文不重复别人已经写过的内容。

## 0. 本文与飞书的分工

课程《项目要求》：「全体成员对产品质量共同负责，同时须**保留可核验的个人贡献记录**。」要做到「可核验」，前提是**同一件事只在一个地方是权威**。本项目分工如下：

| 内容 | 权威落点 | 为什么放这里 |
|---|---|---|
| 角色、职责范围、协作机制、时间节点 | **本文**（仓库） | 这是规范，Sprint 之间不变 |
| 每条具体任务的负责人、状态、进度 | **飞书看板 + 飞书周报** | 这是任务，每天在变 |
| 需求、功能说明、用户故事、原型 | 飞书《产品需求文档》 | 课程要求的需求载体 |
| 架构、接口清单、库表设计 | 飞书《产品设计文档》 | 同上 |
| 代码怎么写、跑什么命令、验收什么 | `docs/dev-handbook.md` | 只在仓库 |

**本文只写「谁负责哪条线、按什么规则认领、什么时候交什么」。具体任务不在此重复**，只给编号映射（见 §1.2）。

## 1. 组员分工表

### 1.1 角色与职责范围

本项目**一人一线一目录**：每个人的产出必须能被单独指认，不必事后回忆「这块是谁写的」。

| 成员 | 负责线 | 主要目录 | Scrum 角色 | 职责范围 | 必须交出的东西 | 不碰什么 |
|---|---|---|---|---|---|---|
| **蒋励**（组长） | 数据与模型 | `data_model/` | **Scrum Master** | 拉数据、SZZ 打标、Kamei 14 项特征、训 2–3 个经典模型、两类评估指标；**兼**全员公共文档与周报统稿 | 带标记样本集、特征数据、模型文件、评估报告；`docs/` 与两份飞书文档的统稿 | 不写后端接口、不写页面 |
| **苏哲勋** | 工程化与协作 | `infra/` `.github/` | **Product Owner** | 仓库配置、分支与 PR 规范、Issue / PR 模板、CI、缺陷管理、**全部 PR 的审阅**；定「做什么、先做什么、怎么算做完」 | 仓库规范与模板、CI 配置、审阅意见记录 | 不写业务代码 |
| **吕建江** | 后端与接口 | `backend/` | 开发（RD） | 建库表、预测与查询接口、解释模块、鉴权与输入校验；两项质量要求的证据（压测 + 安全用例） | 接口实现、数据库表、鉴权与校验代码、性能与安全证据 | 不写页面、不改特征定义 |
| **刘帅华** | 前端与可视化 | `frontend/` | 开发（RD） | 三个页面（风险列表 / 提交详情 / 趋势看板）、图表、对接后端 | 页面、图表、联调记录 | 不改接口格式、不改后端逻辑 |

**公共部分**：`docs/` 与 `openspec/` 是**全员公共** —— 任何人都可以改，**但同样走 PR**。公共是所有权，不是免审权。

### 1.2 Scrum 角色的职责映射

课程《敏捷-Scrum》给了三个角色的定义，本项目按 4 人配置做了裁剪：

| 角色 | 课程定义的职责 | 本项目谁担任 | 落到哪个动作上 |
|---|---|---|---|
| **Product Owner** | 创建并维护产品需求规划清单（Product Backlog）；梳理需求、确定优先级；决定产品目标与功能范围 | **苏哲勋** | 维护飞书看板与需求文档第五章；每条任务写清「怎么算做完」 |
| **Scrum Master** | 确保团队遵循敏捷原则与 Scrum 实践；组织并推动每日站会、评审会、总结反思会 | **蒋励** | 每日站会、Sprint 评审、回顾会；卡住的事由他推到有结论 |
| **Scrum 团队（RD）** | 采用 Sprint 迭代；**根据 Backlog 分配任务** | **全体 4 人** | 见 §2 任务认领机制 |

**站会三问**（课程原文）：昨天你做了什么？今天你将要做什么？你有需要帮助的地方吗？—— 本项目写进 `docs/collaboration.md` §8，允许用群里文字异步回答。

> 看板：飞书《JIT 缺陷预测 · 项目看板》。**每周更新周报前先对一次账** —— 周报与看板必须读同一份状态口径（`docs/collaboration.md` §5.2「状态判定」）。

### 1.4 个人贡献怎么留痕（课程硬要求）

课程原文：「须保留**可核验的个人贡献记录**」，并明确「Git 记录、项目管理看板、OpenSpec tasks、PR 审阅、Sprint 周报记录」都是评分依据。所以每做一件事，**必须留下痕迹**：

| 做的事 | 留痕方式 | 谁看得到 |
|---|---|---|
| 写代码 | 提交（`git log` 里的作者名） | Git 记录 |
| 开一件事 | **飞书看板**新增一行（挂 `type:*` 标签、填 `关联链接`）；缺陷与需讨论的条目另开 GitHub Issue（挂 `line:*` / `sprint:*` 标签） | 看板 / Git 平台 |
| 交一件事 | PR（作者 + 非作者审阅记录） | Git 平台 |
| 干完一件事 | 飞书看板状态 + 周报「本周计划」表 | 周报 |

**不认「我做了但没留痕」。** 课程按证据打分，没证据等于没做。

**一条禁令**：提交、PR、Issue、看板操作**一律用本人账号**，不得代提交 —— 课程按 Git 记录核对个人贡献，代提交等于抹掉被代的人的记录，两个人的分都受影响。

## 2. 任务认领机制

### 2.1 任务从哪来

任务只有三个来源，**不在别处临时加**：

1. **飞书看板**里状态为 `未开始` 的行
2. **OpenSpec change 的 `tasks.md`** 里未勾选的条目（课程要求任务可追踪）
3. **Sprint 末回顾会**新增的改进项

需求变更不在此列 —— 那要先走 OpenSpec change（课程原文：「需求变更必须通过同步新增或修改管理工具及 OpenSpec change 记录，**不得只改代码而不更新规格**」）。

### 2.2 怎么认领（两步）

```
① 看板「负责人」字段写上自己，状态改「进行中」
        ↓
② 看板「关联链接」填上对应产物的地址（OpenSpec change / PR / Issue，有则填）
```

**第 ② 步是课程评分点** —— 看板那一列能点开，「可追溯」才算落地。

**关于 GitHub Issue：本项目不要求「一条任务配一个 Issue」。** 任务的主工具是**飞书看板** —— 课程原文即写「使用飞书多维表格 / 华为云 CodeArts / 禅道进行项目管理」，Issue 只用于两种情况：

| 什么时候开 Issue | 依据 |
|---|---|
| **缺陷（Bug）** | 课程原文「缺陷使用 Issue 或等价记录管理」，走 `docs/defect-management.md` |
| 需要**跨线讨论**、有争议或要留讨论记录的条目 | `docs/collaboration.md` §5.1 |

纯实现类任务**只有看板一条即可**，不必两头维护同一件事 —— 两处都写，一周后必然出现两套说法。

### 2.3 四条硬规矩

- **一条任务只能有一个负责人。** 需要两人一起做，就拆成两条、各自认领。
- **认领即承诺。** 认领后到期没完成，看板状态改 `已延期` 并在站会说明原因。**不标 `已延期` 而默默挂着，比延期本身更严重。**
- **不许替别人认领。** 需要别人做什么，在站会上提，由对方自己认领。
- **跨线的事走契约。** 需要改别人的接口或字段，不在群里说一句就算，走 `docs/contracts/` 的变更流程。

## 3. 截止时间管理

### 3.1 Sprint 日历（课程硬节点）

课程把开发周期按 **4 个 Sprint** 组织（《项目要求》实训计划）。**以第 1 周 = 9/7 起算**：

| 阶段 | 周次 | 日期（按第 1 周 = 9/7 推算） | 该阶段必须交的（课程原文摘） |
|---|---|---|---|
| **Sprint 0** 需求分析与产品设计 | 第 1–3 周 | **9/7 – 9/25** | 团队协作约定；产品需求与设计文档初版（含用户/场景、竞品或替代方案说明、技术架构、数据库设计、核心流程图&时序图、低保真原型）；项目管理看板；OpenSpec 初始化（proposal、核心能力规格、任务清单.md） |
| **Sprint 1** 首个 MVP | 第 4–6 周 | **9/28 – 10/16** | 工作周报；OpenSpec 已实现 change 的规格、任务勾选与测试；**MVP 至少 1 条从界面/入口到业务/数据层的完整流程**；更新后的产品文档 |
| **Sprint 2** 核心功能与集成 | 第 7–9 周 | **10/19 – 11/6** | 工作周报；新增或修改的 change 与更新后的当前规格；可演示的核心功能增量；需求/接口变更的设计说明（如有）；**单元测试报告**等 |
| **Sprint 3** 测试与验证 | 第 10–14 周 | **11/9 – 12/11** | 工作周报；所有范围内 change 的任务完成与校验；功能/集成/系统测试与**问题/缺陷处置记录**；至少**两项已验证的非功能需求测试**；完整产品文档 |
| **Final Release** 验收与展示 | 第 15–16 周 | **12/14 – 12/25** | 最终可运行系统；全部 OpenSpec 变更归档且当前规格与产品一致；测试报告；展示 PPT 等结题材料 |

> ⚠️ **日期是按课程「第 1 周 = 9/7」推算的，需在课上向老师确认一次**（飞书周报任务 12）。老师一旦给出确切周历，本表以老师口径为准并更新。

### 3.2 每周固定节点

课程《课程要求及日程安排》原文要求：

| 时间 | 必须做的事 | 谁负责 | 依据 |
|---|---|---|---|
| **每周五晚上** | **提交工作周报**，命名 `工作周报-日期`（如 `工作周报-20260911`） | 组长（蒋励） | 课程硬要求；**无故缺勤 3 次取消成绩** |
| **每周五课上** | 简短进展汇报：已完成 / 下一步 / 存在问题 | 组长（蒋励） | 课程《项目要求》 |
| **每周三前** | 可约任课教师课外讨论一次（限时 30 分钟） | 有议题的人提，组长约 | 课程《项目要求》 |
| **每工作日** | 站会同步（10 分钟内，可异步） | SM（蒋励）组织 | `docs/collaboration.md` §8 |
| **每个 Sprint 末** | 迭代评审 + 回顾会 | PO（苏哲勋）/ SM（蒋励） | 同上 |

**个人供稿截止**：每周**周五 17:00 前**，各人把自己那栏（做了什么 / 证明材料 / 待改进）发给组长，组长当晚统稿提交。**晚于 17:00 的当周不列入**。

### 3.3 逾期怎么处理

| 情况 | 处理 |
|---|---|
| 站会上发现某任务当天没动 | 负责人当场说明卡在哪；SM 记下，当场定「谁在什么时候解决」 |
| 任务到期未完成 | 看板标 `已延期` + 站会说明原因 + 定「继续 / 降范围 / 换人」 |
| **卡住超过 1 个工作日** | **必须升级**：站会提出，由 SM（蒋励）推到有结论；推不动就报 PO，必要时周三约老师 |
| Sprint 末交付物没交齐 | 回顾会第一项议题；下个 Sprint 重新估算并**缩范围** |

**默认原则：宁可缩范围，不可拖交付物。** 课程按每个 Sprint 的交付物打分，缺一项就是缺一项 —— 而课程本身也写明「项目范围过大、无法在各 Sprint 验收的会被要求缩减或调整」，主动缩范围是被认可的。

## 4. 沟通方式与频率

### 4.1 渠道分工（一个用途一个渠道）

| 渠道 | 只用来做什么 | 不用来做什么 |
|---|---|---|
| **飞书群** | 日常同步、站会异步发言、卡住的求助、约会议 | 需求讨论的最终定论（定论必须落文档） |
| **GitHub Issue / PR 评论** | 与具体代码、规格、缺陷有关的讨论 | 聊天、临时通知 |
| **飞书周报** | 每周进展的正式记录 | 日常沟通 |
| **飞书看板** | 任务状态 | 讨论 |
| **站会（含异步）** | 三句话同步：昨天做了什么 / 今天做什么 / 卡在哪 | 技术讨论（10 分钟内没结论的，会后单独拉人） |

**一条硬规矩：任何结论都要落到某个文档或 Issue 里。** 只在聊天里说过的决定，等于没定 —— 课程明确要求需求变更必须同步到管理工具与 OpenSpec change。

### 4.2 响应时限

| 事项 | 频率 | 响应时限 |
|---|---|---|
| 站会 | 每工作日（可异步） | 当天内 |
| 群里 @ 到本人的问题 | 即时 | **1 个工作日内必须回**，哪怕是「收到了，明天给」 |
| PR 审阅请求 | 随时 | **1 个工作日内**给结论（`docs/collaboration.md` §3.3） |
| 迭代评审 + 回顾会 | 每 Sprint 末 | — |
| 需求 / 接口变更 | 随时提出 | **当周内**登记进 OpenSpec change |

### 4.3 沟通纪律

- **对事不对人**：审阅意见与站会提问只谈交付物，不评价人。
- **卡住要早说**：卡住 1 个工作日就升级，不要憋到 Sprint 末。
- **不越线沟通**：需要改别人目录的东西，走契约与 Issue，不在群里让对方「顺手改一下」。
- **不用私聊替代记录**：私聊达成的决定，回头补到 Issue 或文档里。

## 5. 出勤与纪律（课程硬要求）

课程原文：**「无故缺勤 3 次，取消成绩」**。

| 条文 | 内容 |
|---|---|
| 出勤 | 每周五课上的进展汇报为必到项。无故缺勤按课程规则累计，**满 3 次取消成绩** |
| 请假 | 提前在飞书群说明，并在看板上把自己名下任务的状态更新到最新 |
| 周报 | **每周五晚上**提交（放假除外），由组长统一提交；个人供稿周五 17:00 前给组长 |
| 署名 | 提交、PR、Issue、看板操作**一律用本人账号**，不得代提交 |
| OpenSpec | **改代码必须同步改规格** —— 规格与代码不一致，视为缺陷（课程原文） |
