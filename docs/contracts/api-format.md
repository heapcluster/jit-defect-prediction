# 契约三：接口格式

> 状态：**已冻结** ｜ 版本 1.4
> 定稿人 吕建江 ｜ 冻结人 吕建江、蒋励 ｜ 冻结日期 2026-09-19（原计划 9/23，定稿人提前冻结；冻结后改动走变更流程）
> 1.1 版为**冻结前补齐课程硬要求**：新增 `POST /api/predict`。由吕建江提出问题、蒋励对照课程原文裁定，改动记录见变更日志。

## 管什么

后端线要按这个格式返回，前端线要按这个格式渲染。**这是本项目改动最频繁的一条契约** —— 前端一抱怨「数据不够画图」，就容易临时改接口，改一次前端要跟着改一次。

## 一、通用约定

| 项 | 约定 | 理由 |
|---|---|---|
| 前缀 | 一律 `/api` | 便于将来与静态资源分开代理 |
| 响应包络 | `{ "code": 0, "message": "ok", "data": {...} }` | 成功失败结构一致，前端一套逻辑处理完 |
| 时间格式 | ISO 8601 带时区，例 `2026-09-16T08:30:00Z` | 前端 `new Date()` 可直接解析 |
| 概率字段 | 取值 `0.0` ~ `1.0` 的小数 | **前端自己转百分比**，后端不返回 `"85%"` 这种字符串 |
| 分页参数 | `page`（从 1 开始）、`size`（默认 20，上限 100） | 上限 100 是防止前端一次拉全表把接口拖慢 |
| 鉴权 | 固定令牌，请求头 `X-API-Key`；未通过返回 401 | 对应课程「接口鉴权」要求，细则见下方。**四个接口一律适用，预测接口不例外** |

### 鉴权细则（2026-09-23 冻结）

| 项 | 约定 |
|---|---|
| 方案 | **固定令牌（API Key）**，不做 JWT |
| 传递方式 | 请求头 `X-API-Key: <token>` |
| 令牌来源 | 服务端从 `.env` 读取，**不入库、不写死在代码里**（见 `docs/collaboration.md` 第 4.3 节） |
| 失败响应 | 缺失或不匹配 → HTTP 401 + `code = 40100`，message 固定为 `missing or invalid token`；**不提示「令牌哪一位错了」** |
| 前端 | 从构建期环境变量注入，不得硬编码在源码里 |
| 为什么不用 JWT | 本项目无多用户、无权限分级、无跨服务调用；JWT 的签发、刷新、验签流程没有收益，只会增加出错的环节。课程要求的是「接口需鉴权」，固定令牌满足 |
| 已接受的代价 | ① 无过期与轮换机制；② 令牌会随前端构建产物下发到浏览器，做不到真正保密。**接受理由**：演示环境仅内网、数据不敏感。答辩被问到「你的鉴权安全吗」，这是标准答案 —— 承认边界，比假称安全更可信 |

## 二、错误码表

| code | HTTP | 含义 | message 示例 |
|---|---|---|---|
| 0 | 200 | 成功 | `ok` |
| 40001 | 400 | 参数非法（类型错、越界、枚举值不存在） | `size 超过上限 100` |
| 40100 | 401 | 未通过鉴权 | `missing or invalid token` |
| 40400 | 404 | 目标不存在 | `commit not found` |
| 50000 | 500 | 服务内部错误 | `internal error` |

> **安全要求**：`50000` 的 message **不得回显异常堆栈、SQL 语句、文件路径**。课程明确要求「非法输入不泄露内部信息」。内部细节写进服务端日志，不返回给调用方。

## 三、接口清单

**本契约共四个接口**：三个查询接口（1–3）读库里已落盘的结果，一个预测接口（4）按需触发实时推理。第四个接口的依据见第六节冻结结论。

### 1. `GET /api/commits` —— 风险列表

按风险概率从高到低返回提交列表。对应前端「风险列表」页面。

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `page` | int | 否 | 默认 1 |
| `size` | int | 否 | 默认 20，上限 100 |
| `min_risk` | float | 否 | 只看风险概率不低于此值的提交，如 `0.5` |
| `model_name` | string | 否 | 指定模型版本，默认用最新 |
| `start_time` / `end_time` | string | 否 | ISO 8601 时间范围 |

**响应 `data`**

```json
{
  "total": 1284,
  "page": 1,
  "size": 20,
  "items": [
    {
      "commit_hash": "a1b2c3d4e5f6...",
      "author_name": "jdoe",
      "committed_at": "2026-08-14T09:12:33Z",
      "message": "AMQ-8123 fix NPE in broker shutdown",
      "risk_score": 0.8732,
      "model_name": "xgb_v1"
    }
  ]
}
```

### 2. `GET /api/commits/{commit_hash}` —— 提交详情

对应前端「提交详情」页面。回答「这一次提交为什么被判为高风险」。

**响应 `data`**

```json
{
  "commit_hash": "a1b2c3d4e5f6...",
  "author_name": "jdoe",
  "committed_at": "2026-08-14T09:12:33Z",
  "message": "AMQ-8123 fix NPE in broker shutdown",
  "risk_score": 0.8732,
  "model_name": "xgb_v1",
  "features": {
    "ns": 1.0986, "nd": 1.6094, "nf": 1.9459, "entropy": 1.42,
    "la": -4.2720, "ld": -5.2753, "lt": 7.1136,
    "fix": 1,
    "ndev": 1.3863, "age": 2.5257, "nuc": 0.2513,
    "exp": 5.7683, "rexp": 3.8114, "sexp": 2.8904
  },
  "explanation": [
    { "feature": "entropy", "contribution": 0.21, "direction": "increase" },
    { "feature": "nuc",     "contribution": 0.14, "direction": "increase" },
    { "feature": "exp",     "contribution": 0.09, "direction": "decrease" }
  ]
}
```

**字段说明**：`features` 的键名必须与 `feature-columns.md` 完全一致。`explanation` 是模型解释（哪几项特征把风险推高、哪几项压低），供页面画特征贡献图。

> **本响应不返回「真实标签 / 模型判对了没有」。** 理由见第六节冻结结论。

> **提交存在、但 `prediction` 表还没有对应行时**（模型尚未跑该批次，或该提交不在本 `model_name` 的批次内）：返回 `code = 0`，`risk_score` 与 `model_name` 为 `null`、`explanation` 为 `[]`。**这不是错误** —— 与 `docs/pages.md` 第 5 节「空数据不是错误」同口径，前端按 `null` 渲染「尚未预测」。后端 **MUST NOT** 为此返回 `40400`，也 **MUST NOT** 用 `0.0` 冒充一个分数：`0.0` 是「模型判定为低风险」的合法取值，两者不能混。

> **提交存在、但 `commit_feature` 表无对应行时**：返回 `code = 0`、`features` 为 `null`（若同时无预测行，一并按上一条口径）。**这不是错误** —— 与 `docs/pages.md` 第 5 节「空数据不是错误」同口径；后端 **MUST NOT** 为此返回 `40400`，也 **MUST NOT** 以 0 填充特征值（PR #30 审 7 补记）。

### 3. `GET /api/trends` —— 缺陷引入趋势

对应前端「趋势看板」页面。

**请求参数**

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `granularity` | string | 否 | `week`（默认）/ `month` |
| `start_time` / `end_time` | string | 否 | 时间范围 |
| `model_name` | string | 否 | 指定模型版本 |

**响应 `data`**

```json
{
  "granularity": "week",
  "model_name": "xgb_v1",
  "series": [
    { "period": "2026-W30", "commit_count": 42, "avg_risk": 0.31, "high_risk_count": 7 },
    { "period": "2026-W31", "commit_count": 55, "avg_risk": 0.36, "high_risk_count": 11 }
  ]
}
```

**「高风险」的阈值是服务端常量，不开放为请求参数。** 判定口径为 `risk_score >= 0.5`，由后端算好 `high_risk_count` 后随 `series` 返回 —— 这样「高风险」全项目只有一处定义。**前端 MUST NOT 用 `0.5` 自己再算一遍**（两处各写一个数，早晚不一致）。要把它变成可配置（新增请求参数或配置项），走 `docs/contracts/README.md` 的契约变更流程，不在此处直接加参数。

> `series` **只返回单个 `model_name` 的一组数据**，不做同图多模型对比；`model_name` 参数用于切换查看哪个模型，不是叠加。见第六节冻结结论。

### 4. `POST /api/predict` —— 在线预测

**这是课程明确要求的「对外提供在线预测服务」的对外入口**，也是第四节性能要求的压测靶子。

课程《项目要求》原文（第 1 页「系统主要功能模块」）把「**预测与解释模块（缺陷概率、缺陷归因/解释）**」列为系统必做模块，并在任务描述中写明「训练机器学习模型，并**对外提供在线预测服务**与可视化前端」。这两个查询接口只读历史结果，不构成「预测服务」—— 故本节接口不是可选项。

**请求体**（`Content-Type: application/json`）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `commit_hash` | string | 是 | 40 位十六进制提交哈希 |
| `model_name` | string | 否 | 指定模型版本，默认用最新 |

```json
{
  "commit_hash": "a1b2c3d4e5f6...",
  "model_name": "xgb_v1"
}
```

**响应 `data`**

```json
{
  "commit_hash": "a1b2c3d4e5f6...",
  "model_name": "xgb_v1",
  "risk_score": 0.8732,
  "predicted_at": "2026-09-16T08:30:00Z",
  "features": {
    "ns": 1.0986, "nd": 1.6094, "nf": 1.9459, "entropy": 1.42,
    "la": -4.2720, "ld": -5.2753, "lt": 7.1136,
    "fix": 1,
    "ndev": 1.3863, "age": 2.5257, "nuc": 0.2513,
    "exp": 5.7683, "rexp": 3.8114, "sexp": 2.8904
  },
  "explanation": [
    { "feature": "entropy", "contribution": 0.21, "direction": "increase" }
  ]
}
```

`features` 与 `explanation` 的结构、键名与第 2 节完全一致 —— **同一套字段，两处不许各写一份**。

> **`features` 里给的是口径处理后的值，不是原值。** 除 `fix`（布尔值，不取对数）外全部取自然对数；`la`/`ld`/`lt`/`nuc` 还要先归一化。上面两处示例都是按同一套口径换算的，原值 → 示例值：
>
> | 特征 | 原值 | 换算 | 示例值 |
> |---|---|---|---|
> | `ns` / `nd` / `nf` | 3 / 5 / 7 | 取 `ln` | 1.0986 / 1.6094 / 1.9459 |
> | `la` | 120，`lt`=8600 | `ln(120/8600)` | −4.2720 |
> | `ld` | 44，`lt`=8600 | `ln(44/8600)` | −5.2753 |
> | `lt` | 8600，`nf`=7 | `ln(8600/7)` | 7.1136 |
> | `nuc` | 9，`nf`=7 | `ln(9/7)` | 0.2513 |
> | `age` | 12.5 | 取 `ln` | 2.5257 |
>
> **为什么必须给处理后的值**：前端拿到的就是这些数，示例给原值会让人以为接口返回的是「改了几行、几个文件」。口径定义在契约二第四节，这里只保证示例与它一致。

**与第 2 节「提交详情」的分工（这是本接口存在的理由）**

| | 第 2 节 `GET /api/commits/{hash}` | 本节 `POST /api/predict` |
|---|---|---|
| 数据来源 | 读库里**已落盘**的预测结果 | **实时跑一次模型推理** |
| 何时用 | 页面渲染。11,050 条提交不可能每翻一页都实时推理 | 对库中尚无结果的提交按需预测 |
| 对应课程模块 | 可视化前端 | 预测与解释模块 / 在线预测服务 |

**错误情形**

| 情形 | 响应 |
|---|---|
| `commit_hash` 缺失、非 40 位十六进制 | `40001` |
| `commit_hash` 不在 `commit` 表 | `40400`，message `commit not found` |
| 该提交在 `commit_feature` 表无对应特征行 | `40400`，message `features not found for this commit` |
| 模型文件缺失或加载失败 | `50000`，**只写服务端日志，不回显文件路径** |

**幂等性**：同一 `(commit_hash, model_name)` 重复调用，**库里只保留最新一行**（覆盖或先删后插，由后端定），不得累积重复行 —— 否则风险列表会翻出同一提交的多条重复项。

**是否要有页面对应**：MVP 不绑定任何页面。三个页面读的是已落盘结果（第 1、2、3 节接口）。若前端后续想加「对某次提交重新预测」的按钮，直接调本接口即可，**不需要改本契约**。

## 四、非功能要求与验证方式

| 要求 | 指标 | 怎么验证 | 证据形式 |
|---|---|---|---|
| 性能 | **`POST /api/predict`** 95% 的请求在 500ms 内返回 | 用脚本循环发 100 次请求，统计响应时间分位数 | 脚本 + 输出结果截图，放 `backend/` 或 `docs/` |
| 安全 | 四个接口均需鉴权；非法输入不泄露内部信息 | ① 不带令牌请求，应返回 401；② 发送畸形参数，返回信息中不得含堆栈、SQL、路径 | 两组请求的返回结果截图 |

**这两条是课程明确的非功能要求，必须有可出示的证据。** 只写「已实现」不算。

> 性能指标的靶子在 1.0 版里指向「预测接口」，但当时接口清单中没有这个接口 —— **要验证的东西不在契约里**。1.1 版补上接口后，这条指标才有了明确对象。**压测请针对 `POST /api/predict`，不要拿查询接口代替**：查询接口读的是索引，快是自然的，证明不了模型推理的性能。

## 五、不写进契约的

- 后端用什么 Web 框架、怎么组织路由
- 前端用什么请求库、怎么做状态管理
- 接口的部署地址与端口（属于运行配置）
- 内部模块之间怎么调用
- **模型文件放在哪、怎么加载** —— 属跨线交付方式，已裁定方案「A + C」，见 `docs/sprint0-scope.md` 第 4 节与 `data_model/README.md` 末节

## 冻结结论（原「待确认」，2026-09-16 结清；同日补记新增预测接口；2026-09-18 补记两处接口口径）

| 原待确认项 | 结论 |
|---|---|
| 三个查询接口是否够画三个页面（尤其趋势看板是否需要按作者 / 子系统分组） | **画三个页面够 —— 但「够画页面」不等于「够满足课程要求」，此处 1.0 版曾误推为「全项目只有三个接口」**。页面侧的三条定论仍然有效：① **趋势看板不做按作者/子系统分组** —— MVP 固定为「风险随时间变化」单一维度，分组要同时改请求参数、响应结构与前端联动，课程未要求；② **不做同图多模型对比** —— `series` 保持单模型一组数据，`model_name` 只用于切换查看；③ **模型下拉的选项来源：MVP 由前端维护已知模型版本清单**（本期只有 2–3 个且极少变动），不为此新增 `GET /api/models`。若 Sprint 1 模型数量增长到需要动态获取，届时按契约变更流程新增接口 |
| 鉴权方式：固定令牌 / JWT / 其他 | **固定令牌（API Key），请求头 `X-API-Key`**。细则与已接受的代价见第一节「鉴权细则」，不再复述 |
| `explanation` 的具体算法 | **SHAP**（按模型类型选对应 Explainer，树模型用 TreeExplainer）。理由：本契约要求 `contribution` 逐特征且带 `direction`（推高/降低），SHAP 天然满足；全局特征重要性既没有方向、也不是逐样本的，满足不了这个结构。**代价**：数据与模型线需新增 `shap` 依赖，须同步 `data_model/requirements.txt`。前端不解释数值含义、只说「推高/降低」，所以更换解释算法不影响页面结构 |

### 补记：为什么 1.0 版漏了预测接口（2026-09-16）

1.0 版写下「本契约共三个接口，**不再新增第四个**」，是一个**论证范围不全导致的过早封闭结论**：当时只论证了「趋势看板要不要分组」和「模型下拉从哪来」，**没有把课程原文纳入考虑**，就顺手把接口总数一起锁死了。

后端线在冻结前对照课程原文提出后，重新核对确认漏项：

| 证据来源 | 原文 |
|---|---|
| 课程《项目要求》第 1 页 | 「训练机器学习模型，并**对外提供在线预测服务**与可视化前端」 |
| 课程《项目要求》第 1 页 | 「**预测与解释模块（缺陷概率、缺陷归因/解释）**」列为系统主要功能模块 |
| 《讨论0915》第 4 节数据流 | 「模型文件 → **预测接口** → 前端三个页面」 |
| 本契约第四节 | 性能要求写作「**预测接口** 95% 的请求 < 500ms」—— 却无此接口 |

**教训**：写「不新增」这类封闭式结论时，必须说明**在什么范围内封闭**。本条的正确表述从来是「画三个页面不需要第四个接口」，而不是「本项目只有三个接口」。

### 补记：冻结前由后端线提出的两处接口口径（2026-09-18）

契约三定稿后、9/23 冻结前，后端线（吕建江）对照实现提出两处口径未定。两处裁定均已写进正文，此处只登记结论与来源，避免只活在评论区里：

| 议题 | 结论 | 正文位置 |
|---|---|---|
| 提交在 `commit` 表存在、但 `prediction` 表无对应行时返回什么 | `code = 0`；`risk_score` / `model_name` 为 `null`、`explanation` 为 `[]`。**空数据不是错误**，前端渲染「尚未预测」；后端不得返回 `40400`、也不得用 `0.0` 冒充 | §2 |
| 「高风险」的判定阈值放前端还是后端 | **服务端常量 `0.5`，不开放请求参数**；后端算 `high_risk_count` 返回，前端不重算。要改走契约变更 | §3 |
| 提交存在、但 `commit_feature` 表无对应行时返回什么 | `code = 0`、`features` 为 `null`，**不是错误**；后端不得返回 `40400`、不得以 0 填充 | §2 |

两处都不新增接口、不改任何字段名与错误码，只是把原先「未定」的口径写死成可判定的一句；**因为正文的判定口径变了**，版本由 **1.2 升到 1.3**（`docs/contracts/README.md` 状态表已同步）。

**1.4（2026-09-19）**：补记 `commit_feature` 无行口径（§2 与冻结结论表，PR #30 审 7）；状态改 **已冻结**、冻结日期 2026-09-19（提前冻结，原计划 9/23）。
