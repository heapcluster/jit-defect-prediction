# 契约二：特征列名

> 状态：**已冻结** ｜ 版本 1.0 ｜ 冻结日期 2026-09-18 ｜ 冻结人 蒋励 ｜ 主笔 蒋励
> 依据：Kamei et al., *A Large-Scale Empirical Study of Just-in-Time Quality Assurance*, IEEE TSE 39(6), 2013

## 管什么

特征表是模型线与后端线之间的接口。模型线要按这些列名产出，后端线要按这些列名读取并送进模型。**列名对不上，整条链路断在中间。**

## 一、表结构约定

- 一行 = 一次提交（与 `commit.commit_hash` 一一对应）
- 表名：`commit_feature`
- 列名一律 `snake_case` 小写英文

## 二、标识列（非特征，供关联与切分用）

| 列名 | 类型 | 说明 |
|---|---|---|
| `commit_hash` | CHAR(40) | 关联 `commit.commit_hash`，**主键** |
| `committed_at` | DATETIME | 提交时间（UTC）。**时间序切分训练/检验集依赖此列，不可缺** |
| `feature_version` | VARCHAR(32) | 特征口径版本号，例：`v1`。口径一改就升版本，不覆盖旧的 |

## 三、14 项特征列

按 Kamei 原文的五个维度分组。**维度名保留原文含义，列名用小写缩写**（缩写是学术界的通用叫法，便于对照论文）。

### 代码分布（Diffusion）—— 改动散得越开，越容易出错

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `ns` | 改动的子系统（subsystem）数量 | DECIMAL |
| `nd` | 改动的目录（directory）数量 | DECIMAL |
| `nf` | 改动的文件数量 | DECIMAL |
| `entropy` | 改动在多个文件间的分散程度（信息熵）：集中改一个文件算简单，摊到很多文件算复杂 | DECIMAL |

### 规模（Size）

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `la` | 新增的代码行数 | DECIMAL |
| `ld` | 删除的代码行数 | DECIMAL |
| `lt` | 改动前、被改到那些文件的代码总行数 | DECIMAL |

### 目的（Purpose）

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `fix` | 这次提交是不是一个修缺陷的提交（1/0） | TINYINT(1) |

> 注意这列容易混淆：它描述的是「**这次提交的目的是修缺陷**」，不是「这次提交是否引入缺陷」。后者是标签 `is_bug_inducing`，在 `commit_label` 表里。研究结论是：修缺陷的提交反而更容易引入新缺陷。

### 历史（History）—— 被改文件的「过往记录」

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `ndev` | 改动过这些文件的开发者人数 | INT |
| `age` | 这些文件距上次被改动的时间间隔的平均值（天） | DECIMAL |
| `nuc` | 这些文件此前被改动过的独立次数 | INT |

### 开发者经验（Experience）

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `exp` | 提交者在此次提交之前的历史提交总数 | INT |
| `rexp` | 提交者近期的提交数量（按时间衰减加权） | DECIMAL |
| `sexp` | 提交者此前针对本次所改动子系统的提交数量 | INT |

## 四、取值口径（容易出分歧，必须写死）

Kamei 原文为避免量纲与相关性干扰，对部分指标做了归一化。**本组逐项照做，取值已在下表定死** —— 不写清楚，两个人数出来的 `la` 能差几个数量级。

| 项 | Kamei 原文做法 | 本组口径 |
|---|---|---|
| `la`、`ld` | 除以 `lt` | **采用** —— 实现：`la/lt`、`ld/lt` |
| `lt` | 除以 `nf` | **采用** —— 实现：`lt/nf` |
| `nuc` | 除以 `nf`（因与 `nf` 相关性高） | **采用** —— 实现：`nuc/nf` |
| 全部 14 项 | 取对数（log）变换，压缩长尾分布 | **采用** —— 实现：非 0 值取 `ln(x)`、0 值记 0（v1 已知局限见下） |
| `age` 单位 | 天 | **采用** —— 按天计算后再取对数 |
| `entropy` 时间窗口 | 两周（14 天）滚动窗口（Kamei 引用 Hassan 的定义） | **采用** —— 实现常量 `ENTROPY_WINDOW_SECONDS = 14 * 24 * 3600` |
| `rexp` 衰减公式 | `Σ count(n)/(n+1)`，`n` = 距本次提交的整年数 | 采用（Kamei 原文口径） |
| `nuc` 聚合方式 | 按文件分别计数再求和（`ndev` 数的是人、取并集，两者**故意不对称**） | 采用 |

> 建议采用原文口径。理由：本项目的模型结果要与文献对比才有说服力，口径不一致时「我们的 F1 比论文低」这个结论无法解释 —— 是模型差，还是口径不同，分不清。

> **`ln` 在 0 点不连续（v1 已知局限）**：非 0 值取 `ln(x)`、0 值记 0，`ln(x)` 在 x→0⁺ 趋于 −∞，与 0 值在 0 附近不连续。**v2 统一为 `ln(1+x)` 通算并升 `feature_version`**；v1 维持现状不改 —— 改了已产出的特征就不可比。

## 五、不写进契约的

- 特征抽取的具体算法实现（模型线自行决定）
- 具体用哪个 SZZ 工具变体
- 缺失值的填充策略
- 训练时的特征筛选与降维结果

## 冻结结论（2026-09-18 结清）

- ✅ **第四节「本组是否采用」全部表态为「采用」**（`la`/`ld`、`lt`、`nuc` 归一化、14 项取对数、`age` 单位、`entropy` 窗口）—— 与实现 `data_model/03_extract_features.py` 的第 466–486 行逐项一致
- ✅ **`entropy` 时间窗口已明确**：两周（14 天）滚动窗口，依据 Kamei 引用 Hassan 的定义。实现常量 `ENTROPY_WINDOW_SECONDS = 14 * 24 * 3600`；此前第四节未写这条，实现却在注释里引用了第四节 —— 本次补入该行，引用的出处才成立
- ✅ **不新增派生特征**：特征表实际输出即第三节那 14 项，逐字一致。日后若要新增（如 `ratio_la`），必须先登记进第三节与本表，再升 `feature_version`，不得先算后补
