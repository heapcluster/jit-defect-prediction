# 契约二：特征列名

> 状态：**已冻结** ｜ 版本 1.0 ｜ 定稿人 蒋励 ｜ 冻结日期 2026-09-18 ｜ 冻结人 蒋励
> 依据：Kamei et al., *A Large-Scale Empirical Study of Just-in-Time Quality Assurance*, IEEE TSE 39(6), 2013

## 管什么

特征表是模型线与后端线之间的接口。模型线要按这些列名产出，后端线要按这些列名读取并送进模型。**列名对不上，整条链路断在中间。**

## 一、表结构约定

- 一行 = 一次提交（与 `commit.commit_hash` 一一对应）
- 表名：`commit_feature`
- 列名一律 `snake_case` 小写英文

## 二、标识列（非特征，供关联与切分用）

| 列名 | 类型 | 说明 |
|---|---|---|
| `commit_hash` | CHAR(40) | 关联 `commit.commit_hash`，**主键** |
| `committed_at` | DATETIME | 提交时间（UTC）。**时间序切分训练/检验集依赖此列，不可缺** |
| `feature_version` | VARCHAR(32) | 特征口径版本号，例：`v1`。口径一改就升版本，不覆盖旧的 |

> **本契约冻结即对应 `feature_version = v1`。** 后续任何口径改动都升到 `v2`，不覆盖 v1 的数值。

## 三、14 项特征列

按 Kamei 原文的五个维度分组。**维度名保留原文含义，列名用小写缩写**（缩写是学术界的通用叫法，便于对照论文）。

### 代码分布（Diffusion）—— 改动散得越开，越容易出错

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `ns` | 改动的子系统（subsystem）数量 | INT |
| `nd` | 改动的目录（directory）数量 | INT |
| `nf` | 改动的文件数量 | INT |
| `entropy` | 改动在多个文件间的分散程度（信息熵）：集中改一个文件算简单，摊到很多文件算复杂 | DECIMAL |

### 规模（Size）

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `la` | 新增的代码行数 | INT |
| `ld` | 删除的代码行数 | INT |
| `lt` | 改动前、被改到那些文件的代码总行数 | INT |

### 目的（Purpose）

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `fix` | 这次提交是不是一个修缺陷的提交（1/0） | TINYINT(1) |

> 注意这列容易混淆：它描述的是「**这次提交的目的是修缺陷**」，不是「这次提交是否引入缺陷」。后者是标签 `is_bug_inducing`，在 `commit_label` 表里。研究结论是：修缺陷的提交反而更容易引入新缺陷。

### 历史（History）—— 被改文件的「过往记录」

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `ndev` | 改动过这些文件的开发者人数 | INT |
| `age` | 这些文件距上次被改动的时间间隔的平均值（天） | DECIMAL |
| `nuc` | 这些文件此前被改动过的独立次数 | INT |

### 开发者经验（Experience）

| 列名 | 中文含义 | 类型 |
|---|---|---|
| `exp` | 提交者在此次提交之前的历史提交总数 | INT |
| `rexp` | 提交者近期的提交数量（按时间衰减加权） | DECIMAL |
| `sexp` | 提交者此前针对本次所改动子系统的提交数量 | INT |

## 四、取值口径（**已定稿，2026-09-18 冻结**）

Kamei 原文为避免量纲与相关性干扰，对部分指标做了归一化与对数变换。**本组一律采用原文口径**，逐项定值如下：

| 项 | Kamei 原文做法 | **本组定稿口径** |
|---|---|---|
| `la`、`ld` | 除以 `lt` | **采用**：`la / lt`、`ld / lt` |
| `lt` | 除以 `nf` | **采用**：`lt / nf` |
| `nuc` | 除以 `nf`（因与 `nf` 相关性高） | **采用**：`nuc / nf` |
| 全部 14 项 | 取对数（log）变换，压缩长尾分布 | **采用**，但有三条补充，见下方「对数变换的三条补充」 |
| `age` 单位 | 天 | **采用**：天（按 UTC 计算的时间差） |

> 采用原文口径的理由：本项目的模型结果要与文献对比才有说服力。口径不一致时，「我们的 F1 比论文低」这个结论无法解释 —— 是模型差，还是口径不同，分不清。

### 对数变换的三条补充（本组明确，原文未细化）

1. **`fix` 不做对数变换。** 它是布尔值 0/1，取对数没有任何意义（原文同样未对其取对数）。
2. **对数值用自然对数 `ln`。**
3. **非 0 值取 `ln(x)`、0 值记 0（v1 已知局限）。** 原文公开数据集恰好没有 0 值，`ln(0)` 无定义的问题没暴露；本组数据（尤其 `nuc`、`la`、`ld` 归一化后）不保证非零。v1 的处理是**非 0 值取 `ln(x)`、0 值直接记 0**（实现 `03_extract_features.py` 的 `log_v1`），这导致 `ln` 在 0 附近不连续（`ln(x)` 在 x→0⁺ 趋于 −∞）—— **这是契约本身的已知缺陷，实现不擅自修正**。
   **v2 统一为 `ln(1+x)` 通算并升 `feature_version`**；**v1 维持现状不改** —— 特征表已按 v1 产出（`feature_version = v1`），改了口径就与已有结果不可比。此差异须在对外报告里注明，供与文献对比时解释。

### 本组明确**不做**的两件事

| 不做 | 理由 |
|---|---|
| min-max 归一化（把取值压到 0~1） | 原文是为神经网络准备的；本组模型以树模型为主，对量纲不敏感。**若最终选用逻辑回归，标准化在模型内部做，不改本契约的存储口径** —— 契约管的是落库数值，模型预处理是模型线的自由 |
| 特征筛选与降维后的结果落库 | 属模型内部过程，见第五节 |

> ⚠️ **契约只定义「落库的数值口径」，不定义模型训练时的预处理管线。** 例如模型内部对特征再做标准化是允许的；但存进 `commit_feature` 的值必须符合上表。

## 五、不写进契约的

- 特征抽取的具体算法实现（模型线自行决定）
- 具体用哪个 SZZ 工具变体
- 缺失值的填充策略
- 训练时的特征筛选与降维结果

## 冻结结论（原「待确认」，2026-09-18 结清）

| 原待确认项 | 结论 |
|---|---|
| 第四节「本组是否采用」四行需表态 | **已表态**：全部采用原文口径，另加对数变换的三条补充，见第四节 |
| `entropy` 的时间窗口口径 | **采用两周（14 天）滚动窗口**：对一条提交，取窗口 `[committed_at − 14 天, committed_at]`；`p_k` = 窗口内文件 `k` 被修改的次数 ÷ 窗口内全部文件的修改总次数；`entropy = −Σ p_k·log₂p_k`，取值 ≥ 0。窗口内无改动时记 `0`。同一窗口区间内的提交共享同一 `entropy` 值 |
| 是否新增派生特征（如 `ratio_la`） | **不新增**。派生特征会让口径偏离原文，「与文献可比」这一前提就没了。若模型线确有需要，走契约变更并升 `feature_version` 到 `v2`，不覆盖 v1 |

> 上表第二条的口径来自 Kamei 引用 Hassan 的熵定义（窗口内按文件统计改动占比），非本组自创。若后续与公开数据集比对发现窗口对齐方式不同，走契约变更修正，并同步升版本号。
