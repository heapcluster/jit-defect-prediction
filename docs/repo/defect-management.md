# 缺陷管理规范（repo 包权威）

> 合并自原 `docs/defect-management.md`（已并入本文件）v1.0 ｜ 主笔：蒋励 ｜ 审核：苏哲勋
> 课程：「项目需使用缺陷管理工具」「缺陷至少记录现象、复现条件、优先级、处理状态和关联提交/change」。

## 0. 工具选型

**以 GitHub Issue 为缺陷管理工具**（`.github/ISSUE_TEMPLATE/bug.md` 已入库）。证据集中 + 课程认可 + 已就位，优于另装禅道。

## 1. 什么算缺陷

| 情况 | 走什么 |
|---|---|
| 功能/规格不符、接口/数据与契约不一致、运行时报错、非功能不达标 | **Bug Issue** |
| 接口/数据与契约不一致 | Bug Issue **并同时提 OpenSpec change** |
| 文档笔误/措辞 | 直接开 PR 修（不算缺陷） |
| 新功能/增强 | 任务 Issue（type:feat） |

## 2. 必填五项（缺一项=未提完，可打回）

1. 现象（实际+期望）2. 复现条件（别人照做能重现）3. 优先级 4. 处理状态（open/closed+看板）5. 关联提交/change。

## 3. 优先级五档

| 档 | 判据 | 响应 |
|---|---|---|
| P0 阻断 | 主链路走不通 | 当天修，站会升级 |
| P1 严重 | 核心结果错 | 本 Sprint 内必修 |
| P2 一般 | 非核心/边界 | 本 Sprint 排期 |
| P3 轻微 | 界面/文案 | 有余力 |
| P4 建议 | 优化 | 记录不排期 |

## 4. 流转

发现 → 提 Bug Issue（五项齐）→ 打标签 → 定优先级 → 看板认领 → 修 → PR（写「修复 #编号」）→ 非作者审阅 → 合并 → **提出人确认后关 Issue** → 看板「已完成」。

**纪律**：修复必须走 PR，不得直推 main；缺陷修完不留痕迹=没证据。

## 5. 与其他文档

缺陷处置记录 = 本规范产生的 Issue 列表（Sprint 3 结题按标签导出，不另做表）。规格错误→提 change（`openspec-workflow.md`）。测试要求见 `repo/collaboration.md` §4（测试底线：修缺陷带回归测试、新增接口至少 1 正常 + 1 异常路径）与 `common/test-plan.md`（四层测试总纲）。
