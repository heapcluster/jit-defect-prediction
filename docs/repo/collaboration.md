## §0 强制清单（2026-10-24 蒋励定，违反即不合）

这六条是**门槛**，不是建议。每条都有检查手段，不是靠自觉。

| # | 规矩 | 怎么检查 | 谁负责拦 |
|---|---|---|---|

## 1. 分支规范

- `main` 受保护，**禁止直接推送**。
- 工作分支 `<类型>/<线>/<简述>`：`feat/fix/docs/refactor/test/chore` × `model/backend/frontend/infra/docs/spec`。
- PR 合入后**远端+本地都删**（`git branch -d`，Squash 合入用 `-D` 仅此场合）；`git fetch --prune` 清跟踪引用。
- 仓库已开 `delete_branch_on_merge=true`（2026-10-24 核实）：**远端那半由 GitHub 自动做**，本地那半仍要自己删。判据：本地分支的提交已进 `main`（Squash 合入时 hash 不同，看文件内容或 PR 状态，别只看 `--merged`）。关闭的 PR（未合）也要删分支，内容由后续 PR 承载时在关闭评论里写明。

## 2. 提交信息

```
<类型>(<范围>): <中文简述>
<正文：为什么改>
<关联：Closes #12 / change-id: xxx>
```
一次提交只做一件事；类型/范围英文、简述中文；标题 ≤72 字符。

## 3. PR 流程

- **不要攒**，一件可独立验证的小改动就开 PR。
- 描述四件事：改了什么 / 为什么改（对应 change）/ 怎么验证 / 关联编号。
- **审阅人**：吕建江/刘帅华/蒋励 的 PR → **苏哲勋**；苏哲勋的 PR → **蒋励**。（课程要求至少 1 位非作者）
- ⚠️ **文档线（`docs/` 下）PR 走 §3.8 判据，不走无条件合入**：除 §3.8「六种必须 Request changes 的情形」外，文档线 PR 由审阅人直接 Approve 放行，不再逐条挑格式；但**不得无条件合入**——**§3.8 是硬阻断，优先于任何「文档线合入更快」的约定**。带敏感物、虚证或口径双写的文档 PR 一律按 §3.8 拦下。（`jolly326` 是**组长蒋励本人的 GitHub 账号**，不是第二位成员；docs 由蒋励统稿并以该账号提交，故一律按文档线处理）
- 合并方式：**Squash merge**。
- 审阅清单七项（§3.6）：范围单一 / 描述四项 / **openspec 格式合规** / 规格同步 / 契约一致 / 可验证 / 不含敏感物 / 跨 PR 共存。结论三种：Approve / Request changes（写清哪项）/ Comment。1 个工作日内给结论，意见留 PR 不私聊。
- **openspec 格式把关人：苏哲勋**（2026-10-13 组长指派，因其负责 PR 审阅与仓库管理）。审每个 PR 时按 `docs/common/openspec-task-template.md` §6 的检查清单逐份核，不合规 **Request changes 并写清缺哪节**，不代改、不放过。**只管增量**：2026-10-13 存量 7 份已补齐，不回头重排；仅当某份存量被再次改动时，顺带核格式。

## §3.8 审查标准与评论格式（2026-10-24 蒋励定）

§3.6 的七项是**清单**，本节是**判据**：什么算过、什么必须拦、评论写成什么样。审阅人按本节出结论，不许只写「看着没问题」。

### 一、三个维度，按序判

| 维度 | 判什么 | 不达标后果 |
|---|---|---|
| **正确性** | 逻辑是否成立、边界是否处理（空/异常/并发）、有无静默失败 | Request changes（最硬） |
| **规范** | §3.6 七项 + §0 六条强制清单（CI 绿、口径单点、个人路径、一 PR 一事） | Request changes |
| **证据** | 结论是否有可复现命令与输出；"已验证"是否指得出哪条命令 | 打回补证据，不批 |

### 二、六种必须 Request changes 的情形（不许放行）

1. **静默失败**：检查项不可用/库为空/依赖缺失时跳过而不判 FAIL（典型：#113 的 `mask_result` 作用域 bug）。
2. **证据与结论不符**：文档写"已验证"，但引用的输出是修复前的、或跑的是别的环境。
3. **口径出现第二份正文**：同一事实在别处又写一遍（§0.2 文档状态机）。
4. **个人绝对路径进库**：`.env.example`、文档、CI 里出现 `D:/Users/xxx`。
5. **CI 红着推**或**合并后无 approve 记录**（历史遗留另行登记，新 PR 不再放行）。
6. **规格与代码不符**：改了实现没同步 `openspec/specs/**` 或契约文档。

### 三、评论格式（三种结论通用的骨架）

```
审阅 head <短 sha>。

**结论：Approve / Request changes / Comment**

**已核**（逐项对应 §3.6）
- 范围：<单一/跨了几件事>
- 描述四项：改了什么 / 为什么 / 怎么验证 / 关联编号
- openspec 格式：<合规 / 缺哪节>
- 规格同步：<有/无 change，是否需要>
- 契约一致：<字段/错误码/靶子是否被改>
- 可验证：<我实跑的命令 + 结果>（没跑就写"未独立复跑"，不许写"已核"）
- 敏感物：<令牌/个人路径/大文件>

**问题**（Request changes 必填，逐条编号）
1. 现象 → 位置（文件:行）→ 修法建议

**非阻断建议**
- …
```

细则：
- **Approve 也必须写"已核"**，哪怕只有一行 —— 否则无法区分"审过"和"没看"。
- **Request changes 每条必须给"位置 + 修法"**，只说"这里不对"等于没提。
- **不许替代作者改**（除组长明示授权），指出问题后由作者自己改。
- 结论时限 1 个工作日；超时未审由组长指派第二审阅人。

## 4. 开发规范（全组统一）

- 风格：Python 用 `ruff check`（lint）与 `ruff format`（排版），配置只有仓库根一份 `ruff.toml`；前端用 ESLint（`npm run lint`，未接 Prettier，避免 Vue 模板被二次排版）；Markdown 不强制。
- 标识符英文、注释中文且只写「为什么」。
- `.env` 不入库、`.env.example` 入库；密钥误提交 = 立刻改密钥 + 历史处理，不是 `git rm` 了事。
- 禁止静默吞异常；对外错误码只用契约那 5 个，`50000` 不回显内部。
- 测试底线：修缺陷带回归测试；新增接口至少 1 正常 + 1 异常路径。
- 提交前自检：运行本次变更对应的核心测试与构建，核对 `git status --short` 和 `git diff --cached`；风格与 OpenSpec 检查按变更范围人工执行，命令见 `infra/ci.md`。

## 5. Issue 与看板

- 一个 Issue = 一件可验收的事；标签 `type:*`/`line:*`/`sprint:*`。`type:fix` 已废弃，缺陷用 `type:bug`。
- 看板字段：任务/迭代/规格变更或任务/类型/负责人/状态(五值封闭)/优先级/关联链接。详见 `kanban.md`。
- 状态判定以「交付物现在在哪」为准：`待审阅`=在 PR 等合；`已完成`=已在 `main`。

## 6. 与 OpenSpec 对应（SDD）

- **先有 change 提案，后有代码**；改代码必须同步改规格。
- 流程 propose → 规范评审（提案人≠审阅人）→ apply（勾 tasks+验证）→ PR → archive（规格并入 specs/）。
- 三条易违反：码完补提案=没走 SDD；勾 tasks≠合格；改需求只改码不改规格=缺陷。
- Sprint 节奏：开始先立提案；末归档清零；未归档=缺口。详见 `openspec-workflow.md`。

## 7. 明确不做的流程

要求 2 位以上审阅人 / 强制覆盖率门禁 / husky 前置钩子 / 统一编辑器。出现「同一问题反复发生」再补。

> **CI 不在此列**：CI 流水线已在 `design/engineering.md` §3 设计（GitHub Actions：lint → unit-test → build，任一步失败阻断合入），落地任务 E1 见 `design/README.md` §1，随 `common/test-plan.md` §7 退出准则一并验收。此处不再列为「明确不做」，避免与 `engineering.md` §3 口径冲突。

## 8. Scrum 仪式

每日站会（每工作日 10 分钟内，允许异步文字）/ 迭代评审（Sprint 末，PO）/ 回顾会（Sprint 末，SM）/ 每周五课上汇报（组长）。站会只同步不技术讨论。
