# docs/ — 代码项目的文档

**维护**：全员公共维护（蒋励统稿）｜ 任何改动同样走 PR

> **本目录只服务代码项目。** 任务分配、需求与设计正文都在飞书 —— 先读下面第 0 节。

## 0. 权威边界：内容该写在哪

> 一句话：**任务以飞书周报为准；需求与设计正文在飞书；仓库只回答「代码怎么写、怎么跑、叫什么」。**

| 内容 | 权威位置 | 仓库里有没有 |
|---|---|---|
| 本周做什么、谁做、进度、截止 | 飞书《工作周报-YYYYMMDD》「本周计划」表 | 只放指针，不复制 |
| 分工、角色、会议结论 | 飞书《讨论0915-项目启动与分工》 | 只放指针 |
| 需求：背景、范围、功能说明、用户故事 | 飞书《产品需求文档》 | 无 |
| 设计：架构、模块、API 清单、库表设计、原型与交互 | 飞书《产品设计文档》 | 无 |
| 代码怎么写、分支与 PR 怎么走 | `docs/collaboration.md` | 是 |
| 字段叫什么、接口格式、特征列名 | `docs/contracts/` | 是 |
| 页面要用接口的哪些字段 | `docs/pages.md` | 是 |
| 环境怎么装、数据怎么复现 | `docs/onboarding.md`、`docs/data-pipeline.md` | 是 |
| 系统与各线的**代码**边界 | `docs/sprint0-scope.md` | 是 |

**引用方向是单向的**：飞书文档可以指向仓库里的契约、命令与路径；**仓库不定义任务、不写需求与设计正文**。

同一件事只在一处写 —— 两处都写，一周后必然变成两套说法。这也是本目录主动交出去两类内容的原因：

| 交出去的内容 | 原来的仓库文件 | 现在在哪 |
|---|---|---|
| 用户故事 / 功能点拆解 | ~~`user-stories.md`~~ | 飞书《产品需求文档》五、需求范围 + 六、功能说明 |
| 需求与设计文档的章节与供稿分工 | ~~`requirements-design.md`~~ | 飞书那两份文档本身 |
| 页面线框与交互设计 | ~~`prototypes/`~~ | 飞书《产品需求文档》六、交互原型图 |
| Sprint 交付目标、待定项登记 | 原 `sprint0-scope.md` 第 2、7 节 | 飞书周报表与启动会记录 |
| 「十二项任务卡」式的任务手册 | ~~`task-guide.md`~~ | 任务在飞书；代码做法见 `dev-handbook.md` |

## 1. 目录索引

| 文件 | 内容 | 主笔 |
|---|---|---|
| `onboarding.md` | **新成员上手清单**：环境、OpenSpec CLI、四条自检命令、首次提交、七个已知的坑 | 蒋励 |
| **`dev-handbook.md`** | **代码项目开工手册**：每件代码活动怎么做、跑什么命令、验收标准、给 AI 的提示词要点；含「周报任务 → 本章节」对照表 | 蒋励 |
| `collaboration.md` | 协作规范：**分支操作**（命名 + 六步流程 + 落后处理 + 冲突处理 + **合并后清理**）、提交信息、PR 流程与审阅人、**项目开发规范**、Issue 与看板 | 苏哲勋 |
| `sprint0-scope.md` | **代码边界**：系统做什么不做什么、四条线各管哪些目录、跨线依赖与三个冻结点、完成定义 | 蒋励 |
| `contracts/` | 三条契约：数据表字段（含 ER 图）/ 特征列名 / 接口格式 | 蒋励（前两条）、吕建江（接口） |
| `pages.md` | 三个页面 ↔ 三个查询接口 ↔ 字段映射；三态与错误码处理（第 4 个接口 `POST /api/predict` 不绑页面，见该文第 6 节补记） | 刘帅华 |
| `data-pipeline.md` | 数据链路：数据源、**版本固定**、落盘路径、复现命令、必须报出的统计 | 蒋励 |
| `report-YYYYMMDD.md` | 工作周报归档（**飞书在线版为准**，这里是导出件）—— 当前尚无导出件 | 蒋励 |
| `user-manual.md`、`slides/` | 用户手册、答辩 PPT | 结题材料，Sprint 3 之后 |

> 「主笔」不等于「只有他能改」。`docs/` 是全员公共目录，任何人发现文档有错都可以直接改并提 PR —— 只是每份文档要有一个**统稿人**，否则会出现「四个人各写一段、拼不起来」。

## 2. 与其他目录的分工

| 内容 | 放哪 | 不放哪 |
|---|---|---|
| 协作规范、代码边界、契约、页面映射、数据链路、代码手册 | **`docs/`** | — |
| 需求 / 设计文档、用户故事、原型与交互 | **飞书** | 不在仓库留骨架或正文 |
| 任务分配、进度、周报 | **飞书** | 不在仓库复制一份 |
| AI 助手的规则入口（`AGENTS.md`、`CLAUDE.md`） | **仓库根目录** | 不放 `docs/` —— 工具不会扫 docs/，放这里等于没写 |
| 技术规格与变更提案 | `openspec/` | 不在 `docs/` 重复一份 |
| 模板与配置（PR / Issue 模板、分支保护、CI） | `.github/`、`infra/` | `docs/` 只写「怎么用」，不复制内容 |
| 各线技术约定（目录结构、启动命令） | 对应 `<线>/README.md` | 不在 `docs/` 重复 |

## 3. 硬要求

- 文档里出现的字段名、列名、接口格式，一律以 `contracts/` 为准；**不要在文档里另起一套叫法**。
- **规格与代码不一致，视为缺陷。**
- **AI 生成的图必须标注 LLM 工具名称与提示词**（课程《产品设计文档》模板的硬要求）。仓库内的示例写法见 `contracts/data-fields.md` 的 ER 图；飞书那两份文档里的图同样要标。
- 每份文档首行写清主笔与审核人，末尾附变更日志 —— 便于答辩时说明「谁改了什么」。
