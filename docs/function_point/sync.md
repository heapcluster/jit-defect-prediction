# 数据同步

**一句话**：把 Git 源仓库的提交「取下来 → 抽特征 → 打分 → 入库」。它支撑前端 **风险列表的「刷新」按钮**（按当前架构 / 模型与时间范围补算），是系统里唯一会触发计算的能力。

## 对应前端功能
| 页面 / 入口 | 用这个功能点的哪部分 |
|---|---|
| 风险列表「刷新」按钮 | 按「同步范围行」的架构 / 模型 / 时间调 `POST /api/sync`；异步轮 `/api/sync/status`，完成后按查询栏当前条件重新查询 |
| 服务启动 | `SYNC_ON_STARTUP=1` 时后台增量/补齐到 HEAD |
| （运维 / 演示） | 手动调 `/api/sync`（按架构 / 模型 / 时间区间） |

## 各层职责
| 层 | 职责 |
|---|---|
| 模型线 | 提供单条现算特征 + 推理能力 |
| 后端 | `POST /api/sync`（按架构 / 模型 / 时间区间；前端「刷新」）、`GET /api/sync/status`；catchup 逻辑仅服务启动内部使用，不暴露 HTTP |
| 数据库 | `commit` / `commit_feature` / `prediction` 写入 |

## 分工口径
- 本功能点是**唯一**会触发计算的能力。列表（`/api/commits`）、趋势（`/api/trends`）全部只读已入库结果。
- 前端「查询」不补算，「刷新」才补算，且**异步**：提交即返回，靠 `/api/sync/status` 轮进度；完成后按当前筛选条件重新查询。
- 「刷新」把当前架构 / 模型与时间范围（`line` / `model_name` / `start_time` / `end_time`）原样传给 `/api/sync`；不改动当前表格的筛选条件，同步结果不得直接拼进查询结果；搜索不参与同步范围。
- 同一时刻只允许一个同步任务（服务端串行锁），并发请求返回「已在同步中」。

## 验收
- 「刷新」带 `line` / `model_name` / `start_time` / `end_time` 时，只补该架构、该模型、该时间区间内的提交；边界外提交 MUST NOT 被算进来；
- 同一批重复触发不产生重复行；
- 状态可查、进度可订阅；异步任务在请求返回后继续跑，前端不靠超时判断成败；
- 时间范围为空时按服务端内部默认批次取最新一批；
- 单条现算耗时以实测为准（P50 ≈ 108 秒），验收文档与页面文案不得写成秒级。
