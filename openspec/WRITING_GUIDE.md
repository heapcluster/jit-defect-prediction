# OpenSpec 写作与排版规范

## 1. 先写清楚意思

- 一段只说一件事。先写用户可见的行为，再补技术条件。
- 用具体对象和动作：例如“模型不存在时返回 `40001`”，避免“进行相关处理”。
- 把**现行事实**、**计划**和**历史记录**分开。尚未执行的测试写“未执行”和原因，不写“已通过”。
- 保留 `SHALL`、`MUST`、`WHEN`、`THEN` 等规格关键词；中文句子尽量短，必要术语第一次出现时解释。
- 数字和范围说明口径与来源，例如“当前机器已加载 9 个模型”，不要把“清单 25 个”写成“25 个均可在线使用”。

## 2. 统一层级与留白

```markdown
# change-id — 简短中文标题

> 状态：待验收；负责人：某人。

## Why

一句话说明问题。

## What Changes

- 改动一。
- 改动二。

## Capabilities

- `capability-name`：一句话说明。

## Impact

- 影响的代码、文档和测试。
```

- 文件只用一个一级标题。二级标题分章节，三级标题写 Requirement 或子项，四级标题写 Scenario。
- 标题前后各留一空行；列表、表格、代码块与正文之间留一空行。
- 同一层级的列表项目用相同句式；长任务按“动作 → 交付 → 验收 → 负责人”拆开。
- 路径、命令、API、字段、状态码用反引号；可打开的证据用 Markdown 链接。
- 表格只用于并列比较。超过两句的解释移到表格下方分点写，避免横向滚动。

## 3. 规格句式

```markdown
### Requirement: 模型不可用时给出明确原因

当用户指定的模型没有在线权重时，接口 SHALL 返回 `40001` 和可理解的提示，MUST NOT 泄露文件路径。

#### Scenario: 指定模型缺少在线权重

- **WHEN** 用户提交已登记但未加载的 `model_name`
- **THEN** 接口返回 `40001`，提示该模型暂不可在线预测
```

`MODIFIED` 的 Requirement 标题必须与 `openspec/specs/<capability>/spec.md` 中的目标标题逐字相同。每个 Requirement 至少包含正常场景；存在异常或边界时一并写出。不要用不同标题重复描述同一规则。

## 4. 强调、字体与颜色

- GitHub Markdown 和 OpenSpec CLI 没有统一的字体、字号或文字颜色设置。本仓库用标题层级表达字号，用**加粗**表达重点，不嵌入 HTML 颜色或私有字体。
- 状态统一写成 **已归档**、**待验收**、**进行中**、**已撤回**。可在飞书展示版加颜色，但必须同时保留状态文字。
- 证据不足写 **未执行** 或 **待补证据**；失败写 **失败** 和复现条件。不要仅用红绿颜色表达通过与否。

## 5. 归档前的文字检查

1. `proposal.md` 的 Why、What Changes、Capabilities、Impact 与实际改动一致。
2. `specs/` 的 Requirement 可观察、可测试，没有互相冲突的口径。
3. `tasks.md` 按模板写文件头、连续编号和五节“测试与验证”。每个已勾选任务都能找到当前证据。
4. 活跃文档的链接与仓库路径可打开；历史归档保留原貌，并标明当时口径。
5. 运行 [`README.md`](README.md) 中的三项校验，再由负责人核对实现和验收结果。
