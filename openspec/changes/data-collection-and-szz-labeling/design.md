## Context

`data_model/` 目前只有 `requirements.txt` 与 `README.md`，没有任何可执行代码；`docs/data-pipeline.md` 是骨架，第 2 节的固定版本登记表、第 4 节脚本路径、第 6 节统计表全是「待回填」。契约（`docs/contracts/data-fields.md`）已有草案并定义了本 change 要落的两张表的字段，但尚未走冻结流程。

约束来自三份已成文的文档，本设计不重复它们的理由：单仓库与范围边界见 `docs/sprint0-scope.md` 第 1–2 节；落盘路径与「数据集不入库」见 `docs/data-pipeline.md` 第 3 节；时间序切分与字段命名红线见 `AGENTS.md`。

本 change 的 id 与飞书《工作周报-20260911》任务 3 的 `数据采集与 SZZ 打标` 对齐，其实现落在周报任务 6「拉通数据链路」上 —— 两者是一件事的规格面与执行面。

## Goals / Non-Goals

**Goals:**

- 交付一条从「干净 clone」到「带标签样本集 + 统计表」的可复现流水线，别人照命令序列能跑出同一份数字
- 把三个不可逆口径（固定版本、合并提交判定、打标方法）全部写成文字，不留只存在于实现里的隐含约定
- 两套 SZZ 实现的结果可对照、差异可量化，不静默取其一

**Non-Goals:**

- 不做 Kamei 14 项特征与模型训练 —— 属下一个 change，特征取值口径尚未冻结
- **不直连数据库**：入库是后端线按契约建表后的事，本 change 只产出文件
- 不做时间窗口裁剪的口径创新 —— 默认用固定版本完整历史，与文献口径保持可比
- 不引入调度、增量更新、CI 等工程机制

## Decisions

### D1. 固定版本选 `activemq-5.18.7`

| 候选 | 为何不选 / 为何选 |
|---|---|
| `main` | 浮动引用，两个月后同一脚本跑出不同数据集，不可复现 |
| 6.x 系列 | 6.x 起包名迁移到 `jakarta.*`，与 5.x 历史之间跨版本代码解析噪声大 |
| `activemq-5.17.7` | 更早已停止维护，可用的缺陷修复提交相对少 |
| **`activemq-5.18.7`（选定）** | 5.18 是 5.x 最后一条稳定线且历史连续，5.18.7 是该线最新补丁发布，缺陷修复提交量充足 |

**代价**：若 5.18.x 之后再有补丁发布，我们的基准不随之漂移 —— 这正是版本固定想要的效果。基准只认登记表里的完整哈希，不认「最新」这个概念。

### D2. 合并提交的判定用「父提交数 > 1」，不用 message 前缀

按 `Merge branch ...` 之类的前缀判断不可靠：仓库历史里存在 squash、rebase 与手工合并，message 形态不一致，会有漏网与误杀。父提交数是 git 对象自带的事实，不依赖任何约定。

### D3. 打标两套并存，兜底策略写死

只用现成库 → 库跑不通则整条链路停摆；只用自研 → 无对照，结果可信度无法自证。契约表二定义 `label_method` 本就是为了对照。兜底策略沿用 `docs/data-pipeline.md` 第 7 节：**Sprint 0 内现成库仍跑不通就切自研简化版，不再等待**，两套结果都保留。

### D4. 修缺陷提交的判据：缺陷编号 **且** 修复语义，两者同时命中

ActiveMQ 的提交规范使几乎每条提交都带 `AMQ-<数字>` 编号（含新功能、重构、文档），**编号只能当缺陷候选，不能当判据**。故判据为：message 命中缺陷编号 **且** 含修复语义（fix / bug / patch 等），两者同时满足才进入回溯。

**代价**：会漏掉没写修复关键词的修复提交。用抽样人工复核（≥30 条）估计漏判率，并在统计表注明判据原文，便于他人复算。

### D5. 回溯未命中的修复提交从样本集排除，**不当作负样本**

把「找不到引入方」的修复提交记成 0，会把本该是 1 的样本污染成负样本，既压低正样本比例又引入标签噪声。做法：只把回溯命中的提交记 1；其余未被任何修复提交命中的提交记 0；回溯失败的那批**既不入样本集也不记 0**，只在统计中单列数量。这是 JIT 文献里通行的「可判定范围内统计」口径。

**代价**：样本量比「全量记 0」小，需要在统计表中把三个数字（总数 / 打标成功数 / 未判定数）同时出示。

### D6. 不额外裁剪时间窗口，用固定版本的完整历史

裁剪窗口会改变样本量级，且需要额外解释口径，与「与文献可比」的目标冲突。体量控制改由两处实现：clone 时只取该线（`--single-branch`），落盘只保留契约要求的字段。

### D7. 中间产物与样本集用 CSV，统计表用 Markdown

CSV（UTF-8）便于人工抽查与跨工具打开；Parquet 体积更小但需额外依赖且不便肉眼核对，与本项目「证据要能当场出示」的要求相悖。

### D8. 本 change 不直连数据库

契约已把 `commit_hash` 定为跨线对接主键，**文件即可完成交接**。模型线耦合数据库会带来环境依赖与并发布表冲突，收益为零。入库由后端线建表后按契约另行灌数。

## Risks / Trade-offs

- [数万提交上做全量 blame，耗时可能超出 Sprint 0 预算] → 只对「修复提交实际改动的行区间」做 blame，不整树 blame；中间结果按提交分片落盘，支持断点续跑。实测若仍超时，则把窗口缩小到固定 tag 前的一段时间，并把裁剪口径与理由登记进 `docs/data-pipeline.md` 第 2 节
- [缺陷编号普遍存在，误把功能提交当修复提交] → D4 的双命中判据 + 抽样复核；统计表出具「识别为修复提交的总数」供横向核对
- [两套 SZZ 结果差异大，无法判断谁更可信] → 输出差异清单与抽样对照，作为报告结论出示；**不静默取其一**（这条写进了规格 `szz-labeling`）
- [样本集不含特征，下游误以为可直接训练] → 统计表内显式写明「本产物为带标签样本集，不含特征列」，并在 `docs/data-pipeline.md` 第 4 节标注下一步
- [5.18.7 之后若有新补丁发布，「最新」的说法过期] → 所有文档只用登记的完整哈希描述基准，不使用「最新」这类相对说法

## Migration Plan

不适用 —— 新增能力，不涉及既有数据或接口迁移。

回退方式：删除 `data_model/` 下新增的脚本与产物即可；版本库内只有代码与文档，没有数据产物需要清理（这也是「数据集不入库」带来的额外好处）。
