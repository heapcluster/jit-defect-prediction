# 设计：库表与查询接口

> 只记录技术决策与取舍。范围与「不做什么」见 proposal.md，任务分解见 tasks.md。

## D1 建库方式：自研 init 脚本，不引入 Alembic

手册 §7 允许 Alembic 或建表脚本二选一。选 `python -m app.db init`（SQLAlchemy `metadata.create_all` + 建后索引断言）：

- 契约一 9/18 冻结后 schema 演变概率低，迁移历史管理的收益小；
- 少一类依赖，「一条命令建好库」自明，别人 clone 后不需要学迁移工具；
- 若冻结后契约真的改字段，届时另开 change 引入 Alembic，不预付复杂度。

## D2 鉴权：固定共享令牌（Bearer），不做 JWT

- 系统无用户体系：单部署、调用方是评审员与答辩现场，课程只要求「接口鉴权」存在；
- JWT 引入密钥管理、过期与刷新逻辑，没有对应需求，反而扩大攻击面与测试面；
- 令牌从 `.env` 的 `API_TOKEN` 读取，`.env.example` 列键名；将来若换 JWT，错误码 40100 与前端处理逻辑不变，只换校验依赖。

## D3 「提交存在但无预测记录」的响应形态

契约三未写。选 `code=0`、`risk_score` 与 `model_name` 为 null、`explanation` 空数组：

- 40400 的语义是「目标不存在」，而提交本身存在，用 40400 会让前端「该提交不存在」的文案说谎；
- 与 `docs/pages.md` §5「空数据不是错误」同口径，前端按 null 渲染「尚未预测」态；
- 该口径在 9/23 冻结时回填 `api-format.md`（tasks 1.3），不在代码里私藏。

## D4 灌入幂等键：(commit_hash, model_name, feature_version)

契约一允许同一提交被多个模型各预测一次、且模型迭代不覆盖旧结果 —— 这三元组即天然业务键。灌入用 upsert：同一文件重跑不产生重复行，换模型名则新增行，历史预测可回溯。

## D5 种子数据

`backend/scripts/seed_dev_data.py` 生成小体量（数十行）、命名带 seed 的数据，仅供联调与测试；真实数据一律走灌入脚本。种子只进本地数据库、不入库，也不得混入任何统计口径或证据截图。
