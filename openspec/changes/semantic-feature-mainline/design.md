# 语义特征主线 — 设计要点

> 只记技术决策与取舍，不重复 proposal 的内容。关联：`docs/model/README.md` §9、`docs/design/addons.md` §4。

## D1：为什么 CodeBERT 是主路线，MiniLM 只是可选弱基线（2026-10-13 订正）

**初版决策错误，此处订正。** 初版把 MiniLM 设为「打底全量」、CodeBERT 设为「抽样增强」，与文献主流方向相反。

| 路线 | 定位 | 理由 |
|---|---|---|
| **CodeBERT / GraphCodeBERT** | **主路线，全量或近全量** | 课程附加功能 (4) 点名的「代码专用预训练模型」方向；DeepJIT / CC2Vec / LApredict / SimCom / JITLP 一律用代码专用预训练 |
| `all-MiniLM-L6-v2` | **可选弱基线，或直接砍掉** | **域不匹配**——它是自然语言句子编码器，不是代码模型。拿它编码代码 diff 等于用错工具 |

**订正理由（两条，都是实的）**：

1. **域不匹配**：文献之所以从通用句向量走向 CodeBERT/GraphCodeBERT，正是因为代码的语法、标识符、API 调用模式与自然语言分布不同，通用编码器的表示质量差。用 MiniLM「打底」会把主线建在弱特征上。
2. **算力判断过于悲观**：此前估「CPU 全量几十小时」不成立。按全量提交 × 约 3 个改动文件（量级为**数万条序列**），`codebert-base` CPU 单条约 50–150ms，量级是**小时级**。**先跑 100 条基准测试用实测定时限**，不靠拍脑袋。⚠️ 规模基数以 Camel 为准：固定版本 **84,461** 条提交，旧 ActiveMQ 的 11,050 条规模与耗时估算**不适用于**当前数据源。

**保留 MiniLM 的唯一价值**：作为「非代码预训练模型」的对照，证明我们理解域匹配的重要性。若进度紧张，**直接砍掉**，不影响主线成立。

## D2：独立环境 `jit-defect-prediction`，不污染主线

- 现有 `jit-defect` 环境跑着 **backend 87 条 + data_model 59 条**测试，是 Sprint 1/2 的验收基线。
- `torch` 在 Windows + conda 是 GB 级安装，且可能与既有 `scikit-learn` / `xgboost` 版本冲突。
- **决策**：语义特征全部装在 `jit-defect-prediction`；`jit-defect` 一个包都不加。语义特征的**单测**也跑在 `jit-defect-prediction`，命令写进 tasks.md 的测试板块。

## D3：代码变更文本如何构造（决定语义特征质量的关键）

预训练模型吃的是文本，JIT 的输入是「一次提交的 diff」。构造方式直接决定特征有没有信息量：

- **输入单元**：一次提交内**每个改动文件**生成一条文本（而非整个提交混成一条），因为缺陷引入往往定位到文件。
- **文本内容**：文件路径 + 变更类型（add / modify / delete）+ 被修改的行（`+`/`-` 行，去掉行首符号）+ 提交信息首行。
- **聚合**：同一提交的多个文件向量取**均值**，得该提交的语义向量。
- **截断**：单文件文本超模型上限时按行截断，**记录被截断的文件数与行数**（不静默丢数据）。

> 这条是最容易出错的地方：如果把整个提交的所有文件拼成一条超长文本，绝大多数信息会被模型截断掉，语义特征就退化成噪声。按文件聚合是必要决策。

## D4：语义向量落盘格式与契约边界

- 落盘：`data_model/data/semantic_<model>_<feature_version>.csv`，一行一个 `commit_hash`，列为 `sem_0 … sem_{d-1}`。
- **契约边界（继承 `semantic-feature` spec R1）**：新特征版本 `feature_version = v2`；**契约二既有 14 项列名与顺序一律不动**；语义列只能以附加列或独立文件存在。
- **不入库、不进交付链**：语义向量是实验产物，不是 `commit_feature` 表的新列。

## D5：切分与评估口径全部复用

- 切分：沿用 `data_model/preparation/05_split_dataset.py` 的时间序切分（前 70% / 后 30%，禁随机）与 `validate_split` 断言。
- 评估：沿用 `python -m pipelines.expert.train` / `python -m pipelines.expert.matrix` 的两类指标（Effort-unaware：AUC/F1/P/R/Acc；Effort-aware：`P_norm` 与同预算重排）。
- 8 模型框架：专家/语义/融合三组各自跑同一套模型，**不新造模型类**（`model_registry` 插件化直接复用）。

## D6：补两项论文方法论工作（Kamei et al. 2013）

1. **专家特征消融与重要性分析**：对 Kamei 14 逐项做留一法（leave-one-out）与置换重要性，输出特征效力排序。论文有系统的特征效力讨论，我们此前缺失——这同时是「我们把经典方法做扎实了」的证据。
2. **跨项目不可迁移的显式登记**：论文结论是项目内可用、跨项目不可迁移。我们只做单仓库 Apache Camel，须在报告中**显式记录这一设计选择及其文献依据**，避免答辩被问「为什么只有一个仓库」时无言以对。

## D7：降级与如实标注

- 无 GPU → CPU 推理；时间不够 → 抽样。报告中必须标注：模型名、设备（CPU/GPU）、样本量、是否全量、截断统计。
- **不声称全量 GPU 结果**。课程明确要求「只写实测结果与可验收方法，不写指标口号」。

## D8：交付模型切换的边界

三类对比若显示语义/融合更优，**本 change 不改后端加载的交付模型**。切换须另开「模型切换」提案（`model-coverage` R6），并走契约三变更流程。本条是 spec 的硬约束，不是建议。

## D9：评测协议必须对齐文献标准（2026-10-13 修正）

**已查证的安全项**：`python -m pipelines.expert.train` 中 `model.fit(X_train, y_train)`，早停的内部验证子集从**训练集内部**取，测试集只用于最终评估 —— **未在测试集上调参**，这条过关。

**先纠正一条我此前的误判（重要）**：我曾判断「我们只报自造 `P_norm`、缺文献标准 effort-aware 指标」。**核对 `model_matrix.md` 实际输出后，这个判断是错的。**

**已经具备（与文献口径对齐，无须补）**：

| 已报指标 | 位置 |
|---|---|
| Recall@20% / Recall@50%（按累计工作量截断） | §四/§五 表内 |
| 曲线下面积（累计召回 ~ 累计工作量占比） | 同上 |
| **随机基线：200 次抽样均值 ± 标准差** | 表末「基线：随机排序」行 |
| **上界：真实缺陷密度降序（上帝视角）** | 表末「上界」行 |
| **两种工作量代理**（LOC 与改动文件数） | §四 / §五 各一张表 |
| 四种排序：model / density（Kamei `R_d(x)=Y(x)/Effort(x)`）/ optimal / random | `effort_aware_metrics()` |

随机基线取**多次抽样均值**而非单次，这一点脚本注释已写清理由（工作量重尾，单次可偏到 0.62，理论期望 0.5）——**这比多数论文严谨**。

**真正缺的三件（本 change 补）**：

| # | 缺什么 | 为什么必须要 |
|---|---|---|
| 1 | **统计显著性检验**（Wilcoxon signed-rank + McNemar） | 8 模型在同一测试集上是配对的，但**两两差异没有任何检验**。「xgb 比 rf 好」目前只是单次划分的数字差，说不出是否真实 |
| 2 | **特征消融与重要性**（Kamei 14 留一法 + 置换重要性） | 论文有系统的特征效力讨论，我们此前未做（已在 §9 立任务） |
| 3 | **`P_norm` 的命名标注** | `P_norm` 是**本组自造**的归一化变体（锚点用实测随机均值与上界，比写死 0.5 严谨），但与文献的 **Popt** 不是同一个东西，易被误认。须加一句标注说明 |

**另需说清 `P_norm` 与 Recall@20% 是互补而非替代**：面积看整条曲线，Recall@20% 看截断点；一条曲线可以在前 20% 很平而面积尚可。两者都报才完整——我们本来就都报了。

**本组当前的诚实结论（`model_matrix.md` 实话）**：LOC 工作量代理下多数模型 `P_norm` 为负（-0.67 / -0.42 / -0.36 …），**不如随机排序**；换改动文件数代理后多数转正（0.17~0.25）。已登记 Issue #37。这正是语义特征要做到的方向。

## D10：形态说明 —— 我们是「特征式混合」，不是端到端

必须对答辩讲清楚，不能含糊：

| 形态 | 代表工作 | 我们是否采用 |
|---|---|---|
| 专家特征 + 经典分类器 | Kamei et al. 2013（课程 PS 所引） | ✅ 作为基线组 |
| **端到端**深度模型（diff + message → 标签） | DeepJIT（ICSE'19）、CC2Vec（ICSE'20） | ❌ 未采用 |
| 代码专用预训练模型微调 | LApredict（ICSE'21）、SimCom、JITLP | ❌ 未采用 |
| **预训练模型提特征 → 经典分类器** | —— | ✅ **我们采用这个（混合形态）** |

**理由与边界**：混合形态可辩护（迁移学习 + 复用既有 8 模型框架与两类指标，工程量可控），但**不是文献主流形态**。这一点必须写进报告与答辩表述，**不得暗示我们复现了 SOTA**。若 Sprint 3 有余量，可补一个 CodeBERT 微调的端到端小组作为形态对照。

## D12：多切分点稳健性检查（2026-10-13 补）

当前只有一个 70/30 时间序切分点，所有指标都是**单次划分的数字**——没有方差、没有置信区间。「xgb 比 rf 好」可能只是这一个切分点的偶然。

**做法**：在主切分之外，再用**第二个切分点**（如 60/40 与 80/20）各跑一遍三类设置，输出「切分点 × 设置 × 指标」的稳健性表。

**纪律**：
- 切分点仍必须**按时间序**，禁随机；
- 目的是看**结论是否随切分点翻转**，不是挑一个好切分点汇报；
- 若结论在某个切分点翻转，**如实报告翻转**，并说明可能原因（样本量、时间分布变化）。

**优先级**：低于 D9（标准指标）。D9 未完成前不做本条；Sprint 2 末至少出主切分点的完整结果，本条可延至 Sprint 3。

## D11：评测口径统一（三组设置共用）

三类设置（仅专家 / 仅语义 / 融合）MUST 用：同一切分下标、同一套 8 模型、同一套指标（Effort-unaware 全套 + D9 的标准 effort-aware 全套）、同一显著性检验方法。**任何一组换口径即视为不可比**。
